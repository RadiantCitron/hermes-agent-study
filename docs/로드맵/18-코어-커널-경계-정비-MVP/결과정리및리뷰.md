## 1. 목표와 결과

### 1-1. 목표 달성 요약
본 로드맵의 목표는 에이전트의 한가운데(메인루프)에 단단한 울타리를 쳐서, 향후 기능 확장으로 인해 시스템의 코어가 흔들리지 않도록 아키텍처 경계를 근본적으로 정비하는 것이었다:
1. **[목표 1 — 커널 순수성 격리]**: 턴 루프 본문과 핵심 계약을 외부 라이브러리 및 하위 기능 의존성이 전혀 없는 표준 라이브러리 기반 [`hermes_core.kernel`](../../../src/hermes_core/kernel/) 패키지로 추출. 루프가 압축·`LoopGuard` 등의 구체 확장을 전혀 알지 못하게 격리.
2. **[목표 2 — 메인루프 단독 검증]**: SQLite 데이터베이스, 파일 시스템, 프롬프트 조립 없이 순수 가짜 포트(`FakePorts`)만으로 0.02초 만에 메인루프 9단계 규칙을 독립 검증하는 커널 전용 테스트 슈트([`tests/test_kernel/`](../../../tests/test_kernel/)) 구축.
3. **[목표 3 — 의존 방향 래칫 안전망]**: 시스템 레이어 간 의존 규칙(R1~R5)을 정적 분석 시험([`tests/test_architecture/test_dependency_rules.py`](../../../tests/test_architecture/test_dependency_rules.py))으로 강제하고, 기존 부채는 줄어들기만 하는 래칫(`KNOWN_DEBT`)으로 통제.
4. **[목표 4 — 조립 지점 일원화 및 LLM 관문 확립]**: 기본 확장의 주입을 조립 모듈([`assembly.py`](../../../src/hermes_core/assembly.py)) 한 곳으로 일원화하고, LLM 호출 경로에 양방향 미들웨어 파이프라인([`llm_pipeline.py`](../../../src/hermes_core/kernel/llm_pipeline.py))을 도입하여 토큰 사용량 장부 누적을 단일 입구로 정비.

010단계(아키텍처 안전망)부터 020단계(계약 이동), 030단계(루프 추출), 040단계(조립 분리), 050단계(LLM 관문), 060단계(작동원리 4편 동기화), 070단계(마감)까지 전 과정을 계획대로 완주하였다.

### 1-3. 대시보드 목표 1~4 판정

1. **목표 1 (커널 패키지 분리와 루프의 기능 무지)**: **이뤘다**. `src/hermes_core/kernel/` 신설, 순수 표준 라이브러리 기반 8개 모듈 완성, 루프 내부에서 `LoopGuardExtension`이나 `ContextCompressor` import 0건 확인.

4. **목표 4 (조립 모듈 분리와 LLM 미들웨어 파이프라인)**: **이뤘다**. `assembly.py` 신설, `default_extensions`, `default_llm_middlewares`, `usage_ledger_middleware`, `connect_call_recorder` 배선 완료.

### 1-4. 실제 모델 스모크를 하지 않는 이유

18번 로드맵은 에이전트의 내부 구조와 모듈 간 의존 관계를 정비하는 순수 아키텍처 리팩토링이다. 외부 사용자 인터페이스(CLI), 도구 규약, LLM API 통신 프로토콜을 전혀 변경하지 않았다.
[ROADMAP.md §5](ROADMAP.md)에 정의된 대로 검증을 1층위(외부 의존성 없는 단위/통합/아키텍처 자동 시험)로 완전하게 설계하였으며, `OpenRouterClient` + `httpx.MockTransport` 기반의 HTTP 통신 검증이 100% 무수정으로 통과하므로 실제 과금 토큰을 소모하는 모델 호출 스모크는 수행하지 않는다.

## 2. 단계별 상세 (010~070, Why 중심 서술)

### 010단계: 아키텍처 안전망 (`435811e`)
- **Why**: 구조 정비 도중 새로운 잘못된 의존성이나 순환 참조가 발생하는 것을 방지하고, 이전에는 잡지 못했던 잠재 결함(Python 3.12 타입 힌트 오류)을 사전에 차단할 안전망이 최우선으로 필요했다.
- **What**:
  - `agent/agent.py`의 `Callable` 및 `cli.py`의 `Optional` import 누락 결함 수정.
  - 시스템 의존 방향 규칙(R1: `kernel` 순수성, R2: `tools`는 `agent` 비의존, R3: `tools`는 `tools.tools` 비의존, R4: `cli`는 `agent` 전속)을 검증하는 [`test_dependency_rules.py`](../../../tests/test_architecture/test_dependency_rules.py) 구축.
  - 기존 위반(4건)을 통제하는 `KNOWN_DEBT` 및 갚았을 때 즉시 삭제를 요구하는 래칫 검증 구현.
  - 전 모듈(33개)의 타입 힌트를 런타임에 역직렬화하여 평가하는 [`test_annotations_resolve.py`](../../../tests/test_architecture/test_annotations_resolve.py) 구축.
- **결과 및 다른 점**: 12개 아키텍처 시험 및 Python 3.12 무결성 확인 완료. 지시서 작성 전 조사에서 `cli.py`의 `Optional` 결함을 추가 발견하여 ADR-0018 D-04에 반영.

### 020단계: 커널 패키지 신설과 계약 이동 (`0158a17`)
- **Why**: 턴 루프 본문을 추출하기 전에, 루프가 의존해야 하는 데이터 계약(이벤트, 훅, 컨텍스트, 도구 호출 정의)이 먼저 커널 안에 자리 잡아야 의존 방향 역전 없이 루프를 이전할 수 있었다.
- **What**:
  - [`hermes_core.kernel`](../../../src/hermes_core/kernel/) 패키지 신설.

## 4. 아키텍처 성과와 작동원리 반영 목록

### 4-1. 시스템의 영구 사실이 된 것
1. **커널 순수성 불변식**:
   - [`hermes_core.kernel`](../../../src/hermes_core/kernel/)은 표준 라이브러리 외에 어떠한 외부 패키지나 상위 모듈(`agent`, `tools`, `cli`, `assembly`)도 참조하지 않는다.
2. **명확한 포트(Port) 규약**:
   - 턴 루프는 구체 실물 대신 포트 인터페이스([`TranscriptPort`](../../../src/hermes_core/kernel/ports.py), [`ClockPort`](../../../src/hermes_core/kernel/ports.py), [`SystemPromptPort`](../../../src/hermes_core/kernel/ports.py), [`ExtensionRunnerPort`](../../../src/hermes_core/kernel/ports.py), [`LLMClientPort`](../../../src/hermes_core/kernel/ports.py), [`CallRecordable`](../../../src/hermes_core/kernel/ports.py))만을 바라본다.
3. **조립 지점의 일원화**:
   - 어떤 확장을 기본으로 탑재할지, 어떤 LLM 미들웨어를 연결할지는 [`hermes_core.assembly`](../../../src/hermes_core/assembly.py) 한 곳에서만 결정한다.
4. **LLM 호출 파이프라인 (양방향 관문)**:
   - 턴 루프의 본 모델 호출은 [`LLMMiddleware`](../../../src/hermes_core/kernel/llm_pipeline.py) 체인을 통과하며, 요청 전처리 및 응답 후처리를 횡단 관심사로 끼울 수 있다.
5. **의존 방향 래칫 안전망**:
   - 시스템 아키텍처 규칙 R1~R5는 컴파일러처럼 정적 시험으로 강제되며, 허용된 부채(`KNOWN_DEBT`)는 상환 즉시 목록에서 지우지 않으면 테스트가 실패한다.

## 6. 새로 발견한 부분

1. **Python 3.12 타입 힌트 평가 결함 (`Optional`, `Callable`)**:
   - `from __future__ import annotations`를 쓴 파일에서 import하지 않은 타입을 타입 힌트에 쓰면, Python 3.14에서는 통과하지만 런타임에 `typing.get_type_hints`를 호출하는 라이브러리(Pydantic, Typer 등)나 Python 3.12 이하 환경에서는 `NameError`로 크래시가 발생함을 발견하고 수정함.
2. **조립 지점 순환 참조 (`assembly` ↔ `agent`)**:
   - `agent.py`가 `assembly`를 import하고 `assembly`가 구체 확장을 import할 때, 확장이 다시 `agent` 패키지를 참조하면서 순환 import 에러가 발생함을 재현함. 이를 `agent/__init__.py`의 PEP 562 지연 import로 깔끔하게 해결함.
3. **호출 기록 수집의 클라이언트 내부성**:
   - HTTP 통신 지연 시간, 상태 코드, Authorization 헤더 마스킹 등 세부 호출 기록 사전은 오직 `OpenRouterClient.chat_completion` 안에서만 완성된다는 사실을 확인하여, 루프 미들웨어로 무리하게 이전하지 않고 조립 지점 연결로 유연하게 해결함 (ADR-0018 D-08 보완).
4. **대시보드 실행 기록의 존재하지 않는 해시 2건 발견**:
   - 지시서 020 작성 행의 `d608935`(실제 `ede4037`), 지시서 030 작성 행의 `b78e24c`(실제 `4cc9d7a`)가 커밋 전 임의 생성된 해시였음을 발견하고 정정함.

1. **교훈 1: "시험이 녹색이라고 해서 코드가 안전한 것은 아니다"**:
   - 1,024개 테스트가 모두 녹색이었지만, 정작 Python 3.12 환경에서는 프로그램 실행 자체가 불가능한 결함이 숨어 있었다. 정적 주석 해석 시험과 격리된 파이썬 버전 교차 검증의 중요성을 체감함.
2. **교훈 2: "점진적 전진과 래칫이 대규모 리팩토링의 공포를 없앤다"**:
   - 메인루프 추출 같은 거대 작업도 안전망(010) → 계약 이동(020) → 루프 추출(030) → 조립 분리(040) → 관문 구축(050)으로 잘게 쪼개고, 매 단계마다 래칫 시험으로 범위를 검증하니 회귀 버그 없이 안전하게 완주할 수 있었다.
3. **교훈 3: "테스트가 구현의 은밀한 세부를 훔쳐보지 않게 하라"**:
   - `test_dispatch_single_entry.py`가 함수의 내부 소스 코드를 문자열로 검사하고 있었기 때문에, 완벽히 동일한 동작임에도 루프 추출 시 테스트가 깨지는 문제가 발생했다. 향후 테스트는 행위(Behavior)와 계약(Contract) 중심으로 작성되어야 한다.
4. **교훈 4: "이상론에 매몰되지 말고 현실의 제약을 인정하라"**:
   - 호출 기록 수집을 LLM 미들웨어로 옮기려던 이상론(가정 E)이 실제 클라이언트 구조 및 압축 요약 호출의 특성과 충돌했을 때, 억지로 땜질하지 않고 ADR D-08 보완을 통해 연결 책임만 조립 지점으로 옮긴 판단이 시스템을 단순하고 안전하게 유지시켰다.
