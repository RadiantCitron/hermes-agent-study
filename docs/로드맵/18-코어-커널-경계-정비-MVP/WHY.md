# [WHY] 18-코어-커널-경계-정비-MVP — 왜 지금 한가운데의 울타리를 치는가, 왜 이 정도로만 하는가

## 1. 왜 지금 이 로드맵인가

에이전트의 한가운데는 「모델에게 묻고 → 답을 받아 → 도구를 쓰고 → 다시 묻는」 되풀이 하나다. 15·16번에서 기능을 이 되풀이 옆에 끼우는 자리(도구 앞 관문, 턴 단계의 갈고리, 화면 알림 통로)를 만들었고, 17번은 그 자리에 반복 감지 기능을 실제로 끼워 넣어 보았다.

그런데 들여다보니 되풀이가 든 파일 자체가 아직 기능의 이름을 알고 있다. 압축과 반복 감지를 그 파일이 직접 불러와 설치한다. 그래서 기본 기능을 하나 더하거나 빼려면 한가운데 파일을 열어야 한다. 또 되풀이만 따로 시험할 방법이 없다. 시험하려고 에이전트를 만들면 대화 장부(데이터베이스), 기억 파일, 작업 폴더의 안내 파일 읽기, 스킬 목록 찾기가 줄줄이 따라온다. 되풀이의 규칙이 맞는지 보고 싶을 뿐인데 장부나 파일에서 문제가 나면 시험이 깨진다.

울타리를 지키는 장치도 글뿐이다. 「이 파일은 바깥 부품을 부르지 않는다」는 약속이 파일 머리말에만 적혀 있어서, 누군가 바쁘게 기능을 붙이다 한 줄 부르면 아무도 모른 채 깨진다. 실제로 검토 중에 시험은 모두 통과하는데 한 단계 낮은 파이썬 버전에서는 프로그램이 아예 켜지지 않는 결함이 숨어 있는 것을 찾았다. 「시험이 녹색」이 「정말 괜찮다」를 보장하지 못한 사례다.

사용자는 「나중에 구조는 못 바꾼다, 한 번 검증된 코드는 기능 추가로 흔들리면 안 된다」고 했다. 기능이 더 쌓이기 전인 지금이 울타리를 칠 수 있는 마지막으로 싼 시점이다. 원래 이 자리에 오려던 「단일 제어판」도 결국 바깥에서 붙는 부품이라, 울타리 없이 먼저 붙이면 한가운데를 직접 만지는 제어판이 된다.

## 2. 왜 이 정도로만 하는가 (비목표)

| 하지 않는 것 | 이유 | 언제 하나 |
|---|---|---|
| 파일 쓰기 기록(체크포인트)·사람 승인을 도구 앞 관문 방식으로 옮기기 | 이미 검증된 기능의 동작을 건드린다. 울타리 공사와 섞으면 무엇이 깨뜨렸는지 가릴 수 없다 | 울타리가 굳은 뒤 따로 |
| 에이전트와 도구 배달부의 주인 관계 정리 | 배달부를 누가 만드는지 바꾸면 기존 시험 수백 곳의 준비 과정이 흔들린다 | 19번 제어판(조립 정비)과 함께 |
| 화면이 「멈춘 이유」 글자를 보고 갈라지는 부분 정리 | 화면 쪽 문제이고 한가운데와 무관하다 | 19번 이후 |
| 모든 안내 문구가 한 파일에 몰린 것 나누기 | 자주 바뀌는 파일이지만 한가운데 문제는 아니다 | 별도 계획 |
| 예전 이름을 계속 받아 주는 호환 장치 지우기 | 아직 그 이름을 쓰는 시험이 있다 | 쓰는 곳이 0이 될 때 |
| 에이전트를 아무 설정 없이 만들면 진짜 장부 파일이 생기는 기본값 없애기 | 기존 시험 수백 곳이 그 기본값에 기대고 있다. 되풀이 단독 시험은 에이전트를 거치지 않으므로 이번 목표에 필요 없다 | 19번 |
| 갈고리마다 대화 전체를 복사하는 비용 줄이기 | 지금 느리지 않다 | 측정으로 문제가 보일 때 |
| 턴 시작·끝 갈고리 추가 | 지금 쓸 기능이 없다. 쓰는 곳 없는 자리를 미리 만들지 않는다 | 체크포인트를 옮길 때 |
| 디렉터리 전체를 새 층 이름으로 재배치 | 한꺼번에 모든 것이 흔들리는 빅뱅이다 | 하지 않는다 |

## 3. 왜 이 순서, 왜 이 단계 수인가

1. **안전망 먼저(010)**: 울타리 규칙을 시험으로 만들어 두고, 지금 있는 위반은 「갚을 빚 목록」으로 적는다. 이후 단계가 새로 더럽히면 바로 알 수 있고, 갚은 빚은 목록에서 지워야만 통과한다. 숨은 버전 결함도 여기서 고친다.
2. **약속(계약)을 먼저 울타리 안으로(020)**: 되풀이를 옮기려면 되풀이가 쓰는 약속들이 먼저 울타리 안에 있어야 한다. 약속이 기능 쪽 폴더에 있는 채로 되풀이를 옮기면 첫날부터 규칙을 어긴다. 이 단계는 이사만 하고 동작은 하나도 바꾸지 않는다.
3. **되풀이를 옮기고 혼자 시험(030)**: 가장 중요한 단계라 따로 둔다. 기존 시험 전부를 「바뀐 게 없다」의 증인으로 쓰고, 새 단독 시험으로 되풀이 규칙을 직접 확인한다.
4. **기본 기능 목록을 바깥으로(040)**: 되풀이가 옮겨진 뒤에야 「어떤 기능을 기본으로 끼울지」를 조립하는 곳 한 군데로 모을 수 있다.
5. **모델 호출의 관문(050)**: 모델에게 묻는 길에도 도구 앞처럼 관문 줄을 둔다. 지금 되풀이 안에 박혀 있는 사용량 기록과 호출 기록이 첫 입주자다.
6. **마감(060)**.

한 단계에 한 가지 걱정만 두어, 깨지면 어디서 깨졌는지 바로 알게 했다.

## 4. 왜 이 방식을 택하고 무엇을 배척했나

- **택한 것**: 작은 울타리 안 폴더 하나, 시험으로 지키는 규칙 세 개, 줄어들기만 하는 빚 목록, 겉모습(에이전트를 만드는 방법)은 그대로 둔 채 속만 옮기기.
- **배척한 것**:
  - *제어판 먼저*: 붙을 자리가 없다.
  - *전체 재배치*: 사용자가 겪은 대규모 되돌리기의 전형이다. 모든 것이 한 번에 흔들려 원인을 못 가린다.
  - *도메인 주도 설계의 형식(엔티티·저장소 같은 틀) 들여오기*: 틀의 이름만 늘고 규칙은 여전히 흩어진다. 이번에 가져오는 것은 「규칙은 한 곳에서만 정한다」와 「의존은 한 방향으로만」 두 가지뿐이다.
  - *규칙을 글로만 선언*: 이미 그렇게 해서 깨진 적이 있다.
  - *예전 이름을 쓰는 시험을 한꺼번에 고치기*: 검증된 시험을 건드리면 「이사가 아무것도 안 바꿨다」는 증거가 약해진다.
  - *기능들이 모델 호출 관문을 바로 쓰게 열기*: 아직 쓸 기능이 없고, 약속을 바꾸면 그 약속을 따르는 모든 곳이 영향을 받는다.

## 5. 성공 판단 기준과 검증할 가정 목록

| 번호 | 가정 |
|---|---|
| **A** | 되풀이의 규칙(정상 종료, 최대 횟수, 모델 오류, 기능의 정지 요청, 도구 쌍 맞춤, 대화 교체 실패 시 원상 유지)을 장부 데이터베이스·파일·안내문 조립 없이 혼자 실행되는 시험으로 모두 확인할 수 있다 |
| **B** | 울타리 안 폴더가 바깥 부품을 부르면 시험이 즉시 실패하고, 빚 목록에 적힌 위반을 갚으면 목록에서 지우기 전까지 시험이 실패한다 |
| **C** | 이사(020)와 되풀이 옮기기(030)를 하는 동안 기존 시험은 한 줄도 고치지 않고 전부 통과한다 |
| **D** | 기본 기능 하나를 빼거나 더하는 일이 조립하는 곳 한 군데의 목록 수정으로 끝나고, 되풀이 파일과 에이전트 겉면 파일은 바뀌지 않는다 |
| **E** | 모델 호출 사용량 기록과 호출 기록이 되풀이 본문에서 사라진 뒤에도 장부에 남는 값은 이전과 같다 |
| **F** | 한 단계 낮은 파이썬 버전(3.12)에서도 프로그램이 켜지고, 같은 종류의 결함(불러오지 않은 이름을 타입 표시에 쓰기)이 다시 생기면 현재 환경의 시험이 잡는다 |
| **G** | 18번이 끝난 뒤 빚 목록과 호환 장치 목록이 시작 때보다 늘지 않았다 |

## 6. 알려진 위험과 아직 확인하지 못한 것

- 되풀이를 옮길 때 장부에 적는 시점이나 정지 확인 시점이 미묘하게 바뀔 수 있다. 기존 시험이 이것을 다 잡는지는 **미확인**이다. 030 지시서에 순서 시나리오를 따로 적는다.
- 에이전트 겉면과 옮겨진 되풀이 사이에 「직전 토큰 수 추정값」 같은 상태를 주고받아야 한다. 기존 시험이 에이전트 속 이 값을 직접 읽으므로 동기화가 빠지면 깨진다.
- 타입 표시 해석 시험이 정당한 예외(일부러 늦게 해석하는 이름 등) 때문에 잡음이 많을지는 **미확인**이다.
- 3.12 확인에는 네트워크 라이브러리를 설치한 3.12 환경이 필요하다. 이 기기에 그런 환경이 없어 검토 때는 대역 모듈로 재현했다. 010에서 확인 방법을 정한다.
- 과거 대규모 되돌리기가 정확히 무엇 때문이었는지는 이 레포에 기록이 없어 **미확인**이다. 일반적인 실패 유형(빅뱅, 틀만 들여오기)을 피하는 것으로 대신한다.
