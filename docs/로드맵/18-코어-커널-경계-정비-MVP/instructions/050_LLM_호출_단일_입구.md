## 0. 착수 전 점검 (코드 변경 전에 수행하고 결과를 대시보드 실행 기록에 남긴다)

1. **기준 코드 대조** (기준: `main` `852d5ea`): 아래 사실이 지금 코드와 같은지 연다. 다르면 멈추고 보고한다.
   - [`kernel/loop.py`](../../../../src/hermes_core/kernel/loop.py)의 `run_turn`이 바퀴마다 `llm.chat_completion(messages=messages, tools=schema_list)`를 **키워드로** 직접 부르고, `except LLMError`로 감싼다.
   - 같은 함수에서 호출 직후 `usage = getattr(resp, "usage", None)` → `usage`가 사전이면 `in_tok = usage.get("input_tokens") or 0`, `out_tok = usage.get("output_tokens") or 0` → 둘 중 하나라도 0이 아니면 `store.update_token_counts(scope.session_id, input_tokens=in_tok, output_tokens=out_tok)` → `in_tok`이 0이 아니면 `estimate.input_tokens = in_tok`, `estimate.message_count = msgs_len_before_call` → 그다음 assistant 메시지 추가·원장 기록 순서다.
   - `_replace_transcript`에도 `store.update_token_counts` 호출이 있다(압축 요약 호출의 `usage`, 키 `prompt_tokens`/`input_tokens`·`completion_tokens`/`output_tokens`). **이 단계는 이것을 건드리지 않는다**(§5).
   - [`agent/agent.py`](../../../../src/hermes_core/agent/agent.py) 생성자에서 `self.llm_client` 대입 → 모델명·모드 판정 → `if hasattr(self.llm_client, "set_call_recorder") and callable(getattr(self.llm_client, "set_call_recorder")):` → `self.llm_client.set_call_recorder(lambda record: self.session_db.record_llm_call(session_id=self.session_id, **record))` → 기억 디스크 로드 → 세션 생성/재개 순서다. 이 파일의 `hasattr`은 이 한 곳뿐이다.
   - [`llm_client.py`](../../../../src/hermes_core/llm_client.py)의 `OpenRouterClient`는 `set_call_recorder(fn)`과 생성자 `on_call`을 가지며, 기록 사전(`model`·`request`(키 가림)·`response`·`status_code`·`input_tokens`·`output_tokens`·`latency_ms`·`error_kind`·`error_message`)을 `chat_completion`의 `finally`에서 만든다. `MockLLMClient`에는 `set_call_recorder`가 없다.
   - [`agent/compression.py`](../../../../src/hermes_core/agent/compression.py)의 요약 호출은 `llm_client.chat_completion(messages, tools=None)`으로 **클라이언트를 직접** 부른다(루프를 거치지 않는다). 그 클라이언트는 `assembly.compression_config_of`가 넘긴 `agent.llm_client`다.
   - [`assembly.py`](../../../../src/hermes_core/assembly.py)에는 `compression_config_of`·`default_extensions` 두 함수뿐이다.
2. **소비자 전수 (2026-10-31 확인값과 대조)**: 다르면 멈추고 보고한다.
   - `src`에서 `set_call_recorder`·`record_llm_call`을 부르는 곳: `agent/agent.py` 한 곳(정의는 `llm_client.py`·`session_db.py`).

## 1. 구현 내용 명세

루프의 LLM 호출을 커널의 미들웨어 체인 하나로 바꾸고, 루프 본문의 세션 토큰 합계 누적을 조립 지점이 등록하는 미들웨어로 **옮긴다**. 호출 기록은 내용 생성 위치(어댑터)를 그대로 두고 **연결만** 겉면에서 조립 지점으로 옮긴다(ADR D-08 보완). 원장의 `sessions.input_tokens`·`output_tokens`, `llm_calls` 행, 직전 토큰 추정값, 원장 기록 순서는 하나도 바꾸지 않는다.

### 1-1. `src/hermes_core/kernel/llm_pipeline.py` (신규) — LLM 미들웨어 체인

표준 라이브러리와 `hermes_core.kernel.*`만 import한다(R1).

| 이름 | 내용 |
|---|---|
| `LLMRequest` | `@dataclass(frozen=True)`. 필드 `messages: list[dict[str, Any]]`, `tools: Optional[list[dict[str, Any]]]`, `scope: TurnScope`. `messages`는 루프의 **살아 있는 대화 목록 그 객체**다(사본을 만들지 않는다 — 지금 LLM이 받는 객체와 같아야 하므로) |
| `LLMNext` | `Callable[[LLMRequest], LLMReply]` (`LLMReply`는 `kernel/ports.py`의 것) |
| `LLMMiddleware` | `Callable[[LLMRequest, LLMNext], LLMReply]` |
| `build_llm_chain(llm: LLMPort, middlewares: Sequence[LLMMiddleware]) -> LLMNext` | 만들 때 `tuple(middlewares)`로 한 번 고정한다. 맨 안쪽은 `llm.chat_completion(messages=request.messages, tools=request.tools)`(키워드 호출, 지금과 같음). `middlewares[0]`이 가장 바깥이다(등록 순서 = 들어가는 순서) |

- 계약(모듈 docstring에 적는다): 미들웨어는 `next`를 한 번 불러 그 결과(또는 다른 응답)를 돌려주거나, 부르지 않고 응답을 돌려줄 수 있다(단락). 예외는 바꾸지 않고 그대로 올려 보낸다(체인은 아무것도 잡지 않는다). 요청의 `messages`를 고치면 안 된다 — 커널은 이를 검사하지 않으며, 등록 창구는 조립 지점뿐이다(ADR D-08: `ExtensionHost`에 창구를 열지 않음).

### 1-2. `kernel/loop.py` (변경) — 체인만 부른다

- import: `from hermes_core.kernel.llm_pipeline import LLMMiddleware, LLMRequest, build_llm_chain`, `collections.abc`의 `Sequence`. (모듈이 `from __future__ import annotations`이므로 주석에 쓰는 이름은 실제로 import해야 010 주석 해석 시험이 통과한다.)
- `run_turn`에 키워드 인자 `llm_middlewares: Sequence[LLMMiddleware] = ()`를 `max_iterations` 바로 뒤에 더한다(전부 키워드 전용이므로 위치는 호환에 영향 없음). 기존 인자는 바꾸지 않는다.
- `while` 앞에서 `call_llm = build_llm_chain(llm, llm_middlewares)` 한 번. 바퀴마다 `resp = call_llm(LLMRequest(messages=messages, tools=schema_list, scope=scope))`. `except LLMError` 처리와 그 결과(`stopped_reason`·`error`·로그)는 그대로.
- 호출 뒤 `usage` 처리에서 **`store.update_token_counts` 호출 블록만 지운다**. 직전 토큰 추정값 갱신(`input_tokens`가 0이 아닐 때 `estimate` 두 칸)은 그대로 남긴다(ADR D-08: 턴 데이터). 결과적으로 `run_turn` 본문에는 `update_token_counts`가 없다.
- `_replace_transcript`, `_execute_tool_calls`, 정지 확인 시점, 원장 기록 순서는 바꾸지 않는다.

### 1-3. `kernel/ports.py` (변경) — 호출 기록 연결 계약

- `@runtime_checkable class CallRecordable(Protocol)`: `def set_call_recorder(self, fn: Callable[[dict[str, Any]], None]) -> None`. docstring: 「호출 기록을 스스로 만들 수 있는 LLM 어댑터. 기록 내용(상태 코드·지연 시간·키를 가린 요청)은 어댑터만 안다. 커널 루프는 이 계약을 쓰지 않고, 조립 지점이 기록처를 연결할 때 쓴다」.
- `Callable`은 `collections.abc`에서 import한다. 기존 이름(`LLMError`·`LLMReply`·`LLMPort`·`TranscriptStore`·`ToolExecutor`)은 바꾸지 않는다.

### 1-4. `assembly.py` (변경) — 기본 LLM 미들웨어와 기록처 연결

| 이름 | 내용 |
|---|---|
| `usage_ledger_middleware(store: TranscriptStore) -> LLMMiddleware` | 돌려주는 미들웨어: `resp = next(request)` → `usage = getattr(resp, "usage", None)` → 사전이면 `in_tok = usage.get("input_tokens") or 0`, `out_tok = usage.get("output_tokens") or 0` → 둘 중 하나라도 0이 아니면 `store.update_token_counts(request.scope.session_id, input_tokens=in_tok, output_tokens=out_tok)` → `resp`를 그대로 반환. 지금 루프 본문의 판정을 **글자 그대로** 옮긴 것이다(`prompt_tokens` 키는 보지 않는다 — 본 호출 경로는 지금도 보지 않는다). `next`가 예외를 내면 아무것도 기록하지 않고 그대로 올라간다 |
| `default_llm_middlewares(store: TranscriptStore) -> list[LLMMiddleware]` | `[usage_ledger_middleware(store)]`. 부를 때마다 새 목록. docstring: 「기본으로 끼울 LLM 미들웨어의 목록과 순서는 이 함수 한 곳이 정한다」 |
| `connect_call_recorder(agent: Any) -> bool` | `client = agent.llm_client`. `isinstance(client, CallRecordable)`이고 `callable(client.set_call_recorder)`이면 `client.set_call_recorder(lambda record: agent.session_db.record_llm_call(session_id=agent.session_id, **record))` 후 `True`, 아니면 아무것도 하지 않고 `False`. `callable` 검사를 남기는 이유: `runtime_checkable` 프로토콜의 `isinstance`는 이름이 있는지만 보므로, 지금의 `hasattr and callable` 판정과 같게 하려면 필요하다 |

- import 추가: `hermes_core.kernel.llm_pipeline`(`LLMMiddleware`, `LLMNext`, `LLMRequest`), `hermes_core.kernel.ports`(`CallRecordable`, `LLMReply`, `TranscriptStore`). `hermes_core.agent.agent`·`hermes_core.session_db`·`hermes_core.llm_client`는 import하지 않는다(에이전트는 `Any`, 저장소는 포트 타입).
- 모듈 docstring에 「기본 LLM 미들웨어와 호출 기록처 연결도 이 파일이 정한다」를 더한다. 기존 두 함수는 바꾸지 않는다.

### 1-5. `agent/agent.py` (변경) — 겉면은 연결 방법을 모른다

- import 줄을 `from hermes_core.assembly import compression_config_of, connect_call_recorder, default_extensions, default_llm_middlewares`로.
- 생성자의 `hasattr` 블록(주석 「콜백 레코더 등록」 포함)을 `connect_call_recorder(self)` 한 줄로 바꾼다. **위치는 그대로**(모델명·모드 판정 뒤, 기억 디스크 로드 앞).
- `run_conversation`의 `run_turn(...)` 호출에 `llm_middlewares=default_llm_middlewares(self.session_db)`를 더한다. 턴마다 만드는 이유: 지금 루프는 `store=self.session_db`를 턴마다 읽으므로 같은 시점의 저장소를 쓴다.
- 이 파일에 `hasattr`·`set_call_recorder`·`record_llm_call`·`update_token_counts`라는 이름이 남지 않는다. 그 밖(생성자 인자, `MockLLMClient`, `_ExtensionHost`, 확장 설치, 프롬프트 조립)은 바꾸지 않는다.

## 5. 다음 지시서(060 마감)로 넘기는 관찰 (이 단계에서 처리하지 않음)

- **세션 토큰 합계의 길이 둘로 남는다**: 본 호출의 사용량은 조립 지점의 미들웨어가, 압축 요약 호출의 사용량은 커널의 대화 교체(`_replace_transcript`의 `usage` 인자)가 누적한다. 요약 호출은 루프 체인을 지나지 않으므로(압축이 클라이언트를 직접 부름) 지금 구조에서 한 길로 합치려면 압축이 체인을 쓰게 해야 하고, 그러면 040 시나리오 2(압축 설정의 `llm_client`가 에이전트의 클라이언트 그 객체)가 바뀐다. 060에서 가정 E를 「이뤘다(값 불변)」로, 「단일 입구」를 「본 호출에 한해」로 대조할 근거로 남긴다.
- **호출 기록은 체인 밖이다**: ADR D-08 보완대로 기록 내용은 어댑터가 만든다. 체인에 기록을 두려면 어댑터가 상태 코드·지연 시간을 응답·오류에 실어 보내야 하고, 요약 호출 문제(위)도 함께 풀어야 한다. 확장 쪽 LLM 미들웨어 창구(ADR D-08 마지막 항목)와 함께 후속 후보.
- **`HermesAgent` 생성 뒤 `llm_client`를 바꾸면 기록처가 따라가지 않는다**: 지금도 같다(연결은 생성 때 한 번). 바꾸지 않았다.
