## 1. 목표와 결과

### 1-1. 목표 달성 요약
본 로드맵의 목표는 부모 에이전트가 `delegate_task`로 일을 넘기면, 자식이 부모와 분리된 새 대화에서 제한된 도구로 일을 하고 길이 상한이 있는 요약만 돌려주는 **순차 단일 자식 기반 서브에이전트 MVP**를 구축하는 것이었다.

핵심은 일을 넘기는 기능 자체보다, **넘겨받은 쪽이 어디까지 닿을 수 있고 어디에 기록되는지를 4대 격벽(대화·도구·원장·세션 링크)으로 가두는 것**이었다:
1. **대화 격리**: 자식은 부모의 이전 대화 이력, 장기 기억, 작업 폴더 규칙 문서를 물려받지 않고(`skip_memory=True`, `skip_context_files=True`), 부모가 넘긴 `goal`과 `context`만으로 새 세션을 시작했다.
2. **도구 격리 및 재귀 원천 배제**: 자식에게는 읽기/쓰기/터미널/스킬 6종 도구(`CHILD_TOOL_NAMES`)만 제공했다. 위임 도구(`delegate_task`), 기억 도구(`memory`), 세션 검색(`session_search`)이 도구 통로에 아예 존재하지 않아 재귀 폭주와 부모 기억 오염이 구조적으로 차단되었다.
3. **호출 원장 격리**: 자식 클라이언트는 팩토리 주입(`llm_client_factory`)을 통해 독립 생성되며, 자식의 모든 LLM 호출과 토큰 사용량은 자식 세션 ID로 `llm_calls` 원장에 독립 기록되고 부모 세션 토큰 합계에 합산되지 않았다.
4. **단방향 세션 링크**: 자식 세션은 `source="subagent"`, `parent_session_id`로만 부모와 이어지며, 사후 감사 시 부모-자식 관계가 명확히 추적되도록 했다.
5. **실패 안전 격리와 요약 상한**: 자식 오류(타임아웃, 500 오류, 최대 턴 도달)는 프로세스 크래시 없이 `status: "failed"` 도구 결과 메시지로 안전히 변환되었고, 최종 요약은 8,000자(`DELEGATE_SUMMARY_MAX_CHARS`) 상한으로 절삭되어 부모 컨텍스트를 보호했다.
6. **가짜 통신 기반 010~050 단계 전수 통과**: 총 504건 회귀 테스트 100% 통과 (0줄 삭제).
7. **실제 키 스모크(060) 관찰**: 모델이 도구 안내문만으로는 `delegate_task`를 부르지 않고 자신이 가진 `terminal` 도구로 자가 교정(Self-Correction)하며 직접 해결하는 현상이 관찰되었다. 이는 [WHY.md](WHY.md) 가정 G에서 미리 예견한 「이번 1회 관찰에서는 틀렸다」로 정직하게 기록하고 후속 과제의 핵심 실증 근거로 전환했다.

## 3. 설계 결정의 평가 ([README.md](README.md) D-01 ~ D-09)

- **D-01 (도구와 범위: `delegate_task(goal, context?)` 순차 단일 자식, 동기 실행)**:
  - 평가: **매우 성공적**. 복잡한 비동기 이벤트 루프나 동시성 제어 없이도 서브에이전트의 핵심인 격리 구조를 최소 코드로 완벽하게 검증할 수 있었다.
- **D-02 (대화 격리: 새 세션, 부모 메모리/규칙 비주입, `goal`을 첫 메시지로 사용)**:
  - 평가: **매우 성공적**. 부모의 프라이빗 기억과 작업 규칙이 자식에게 유출되지 않으면서도, 자식은 부모가 넘긴 `goal`과 `context`만으로 독립된 작업 문맥을 형성할 수 있었다.
- **D-03 (도구 제한: 자식 전용 허용 목록 6종, `delegate_task`·`memory`·`session_search` 배제)**:
  - 평가: **핵심 성공 요인**. 차단 목록(Blacklist) 대신 허용 목록(Whitelist)을 채택함으로써, 향후 코어에 새 도구가 추가되더라도 자식에게 부지불식간에 열리는 보안 구멍을 원천 봉쇄했다. 재귀 호출과 기억 오염이 구조적으로 차단되었다.
- **D-04 (호출 원장 분리: 팩토리 주입 방식 채택)**:
  - 평가: **설계 최적화 달성**. `OpenRouterClient`에 무리한 복제 메서드(`clone`)를 추가하지 않고, 외부에서 팩토리(`llm_client_factory`)를 주입받아 자식 에이전트를 생성하게 함으로써 `llm_client.py` 0줄 변경을 달성하고 원장 격리를 깔끔하게 처리했다.
- **D-05·D-06 (한도와 실패: 반복 25회 상한, 실패는 예외가 아닌 결과 `status`, 요약 8,000자 상한)**:
  - 평가: **안전성 확보**. 자식 에이전트 내부에서 HTTP 500 오류나 턴 초과가 발생해도 부모 프로세스가 크래시되지 않고 `status: "failed"` 도구 결과 메시지로 정상 변환됨을 가짜 E2E 시나리오 8을 통해 확실히 증명했다.
- **D-07 (토큰 격리: 자식 세션 원장에만 기록, 부모 세션 합계 미합산)**:
  - 평가: **투명성 확보**. 세션별 실제 토큰 사용량이 `llm_calls`와 `sessions`에 1:1로 정확히 기록되어, 사후 감사 시 비용 추적이 왜곡되지 않도록 보장했다.
- **D-08 (세션 연결·종료: `parent_session_id`, `source="subagent"`)**:
  - 평가: **감사 추적성 확보**. 자식 세션이 부모 세션 ID를 단방향 외래키로 참조하여 부모-자식 간의 가계도가 SQLite 상에 영구 보존되었다.
- **D-09 (커밋 식별자 및 태그 규칙)**:
  - 평가: **추적성 준수**. 단계별로 `R07-010`, `R07-020`, `R07-030`, `R07-040`, `R07-045`, `R07-050` 접두부를 부여하여 Git 히스토리 격리를 철저히 지켰다.

## 5. 트레이드오프와 기술 부채

### 5-1. 이번에 포기한 것과 얻은 것
- **포기한 것**:
  1. **자식의 비동기 병렬 실행**: 여러 자식을 동시에 띄워 분할 정복하는 속도와 처리량.
  2. **중첩(다층) 위임**: 자식이 또 다른 하위 자식을 부르는 유연성.
  3. **자식 모델 개별 지정**: 가벼운 작업에 더 싸고 빠른 모델(예: Haiku, Flash-Lite)을 선택하는 비용 최적화.
  4. **부모 세션 토큰 합산**: 부모 세션 하나만 보고 전체 위임 비용을 한눈에 파악하는 편의.
- **얻은 것**:
  1. **무한 재귀 루프 원천 차단**: 자식 도구 통로에 위임 도구가 아예 없어, 모델이 아무리 헛돌아도 재귀 폭주가 일어날 수 없음.
  2. **부모 기억과 규칙의 무결성 100% 보존**: 자식에게 기억 도구와 과거 검색 도구를 주지 않아 부모의 영구 장부가 오염되지 않음.
  3. **부모 컨텍스트 창 보호**: 자식의 최종 보고서가 최대 8,000자로 강제 절삭되어 부모의 입력 토큰이 급증하지 않음.
  4. **투명한 세션별 비용 감사**: 자식 세션 ID로 독립 원장이 기록되어 사후에 어떤 서브에이전트가 얼마나 비용을 썼는지 완벽히 추적 가능.

### 5-2. 빚으로 남긴 것 (기술 부채)
1. **CLI `input()`의 유니코드 디코드 예외 방어 부재**:
   - 스모크 종료 시 관찰된 것처럼, 터미널 제어문자(`^[[D`)나 멀티바이트 특수문자 입력 시 `UnicodeDecodeError`가 발생해 REPL 루프가 깨지는 현상. 향후 CLI 안정화 과제에서 `try-except UnicodeDecodeError` 래핑 필요.
2. **동일 작업 폴더 쓰기 공유의 잠재적 충돌**:
   - 자식 에이전트 역시 부모와 동일한 `.hermes/workspace`에서 파일 쓰기 도구(`write_file`, `patch`)를 실행하므로, 자식이 작성한 파일이 부모의 작업 파일과 이름이 겹치거나 기존 파일을 수정할 위험(쓰기 정책 가드 외의 세부 격리 부재).
3. **자식 요약 결과의 환각(Hallucination) 검증 부재**:
   - 자식이 작업한 내용을 사실과 다르게 요약해서 부모에게 전달하더라도 부모는 이를 액면 그대로 믿을 수밖에 없는 한계.

## 7. 원본과의 차이와 의미 (`hermes-agent` vs `hermes-core`)

- **원본 (`hermes-agent`)**:
  - 서브에이전트 기능이 복잡한 비동기 작업 큐, 백그라운드 태스크 관리자, 역할별 커스텀 프롬프트 템플릿, 동적 컨텍스트 파일 주입 등 방대한 상용 기능과 강하게 결합되어 있어, 순수하게 서브에이전트 격리가 어떻게 이루어지는지 한눈에 파악하기 어렵다.
- **이 코어 (`hermes-core`)**:
  - 비동기·병렬·중첩을 과감히 걷어내고, **"새 대화 격리, 6종 허용 도구 통로, 팩토리 기반 호출 원장 격리, 8,000자 요약 절삭"이라는 4대 격벽의 물리적 실체**를 순수 파이썬 동기 루프로 구현했다.
  - 이를 통해 에이전트 시스템에서 서브에이전트를 도입할 때 발생할 수 있는 가장 치명적인 위험(재귀 폭주, 기억 오염, 컨텍스트 소진)을 단 100여 줄의 단단한 격벽 코드로 방어할 수 있음을 증명했다.

## 8. 새로 발견한 부분과 교훈

1. **모델의 도구 선호 편향 (스킬에 이은 2차 실증)**:
   - 로드맵 06의 스킬 시스템에서 모델이 "스킬"이라는 키워드가 없으면 `skills_list`를 부르지 않았던 것처럼, 서브에이전트에서도 사용자가 "위임", "자식"이라는 단어를 명시하지 않으면 시스템 지시문에 `delegate_task` 안내문이 있어도 자신이 직접 쓸 수 있는 강력한 기본 도구(`terminal`)를 먼저 활용해 끝까지 해결하려는 경향이 확인되었다.
   - 특히 모델은 `terminal`에서 glob(`data/*.txt`)이 안 먹히자 포기하지 않고 즉시 "셸 없이 실행되는 환경이라 glob이 안 되네요. 파일들을 명시해서 다시 실행합니다."라며 자가 교정(Self-Correction)을 수행했다.
   - **교훈**: 모델에게 복합 도구(스킬, 위임)를 스스로 쓰게 하려면, 단순 안내문 나열을 넘어 "언제 위임을 써야 하는가(예: 3개 이상의 다단계 작업 등)"에 대한 명확한 규칙형 트리거를 시스템 지시문에 주입해야 한다.
2. **클라이언트 복제 대신 팩토리 패턴의 우수성**:
   - 당초 계획했던 `OpenRouterClient.clone()` 방식 대신, 외부에서 자식 클라이언트를 생성해 넘겨주는 `llm_client_factory` 패턴을 도입함으로써 기존 통신 계층 코드를 전혀 건드리지 않고도 테스트 격리와 CLI 연동을 완벽히 달성할 수 있었다.
3. **CLI 사용자 입력의 인코딩 복원력 필요성**:
   - 터미널에서 화살표 키나 백스페이스를 누를 때 발생하는 ANSI 이스케이프 시퀀스가 Python `input()`에서 `UnicodeDecodeError`를 유발할 수 있음을 실제 스모크에서 확인했다. REPL 루프에 인코딩 예외 방어 처리가 필수적이다.

## 9. 다음 로드맵 제안 (08번 후보)

로드맵 07까지 완료됨으로써, 코어는 **도구(파일·터미널) $\rightarrow$ 기억(장기·압축·스킬) $\rightarrow$ 위임(서브에이전트)**의 3대 핵심 축을 모두 갖추었다. 이제 다음 단계로 나아갈 수 있는 세 가지 유력한 후보를 제안한다:

1. **후보 A: 자율적 도구 선택 강화 및 지시문 최적화 (Prompt Tuning & Auto-Routing)**
   - 배경: 06번(스킬)과 07번(위임) 실제 스모크에서 모델이 안내문만으로는 상위 도구를 적극적으로 부르지 않는 현상이 반복 관찰됨.
   - 내용: 질문의 성격과 파일 개수, 복잡도에 따라 모델이 `skills_list`와 `delegate_task`를 자연스럽게 호출하도록 지시문 규칙을 구조화하고, 필요 시 경량 인덱스나 명시적 라우팅 트리거를 설계.
2. **후보 B: 다중 턴 REPL 안정화 및 세션 관리 강화 (Session & CLI Robustness)**
   - 배경: 실제 스모크에서 확인된 `UnicodeDecodeError`, 세션 복원 및 과거 대화 이어가기(Resume), 세션 내역 요약 조회 등 사용자 경험과 운영 안정성 보강.
   - 내용: CLI 입력 예외 방어, 세션 재개 기능(`hermes --resume <session_id>`), 세션 아카이브 내보내기 도구.
3. **후보 C: 안전한 작업 환경 격리 (Workspace Isolation & Sandbox)**
   - 배경: 자식 에이전트와 터미널 도구가 부모와 동일한 로컬 작업 폴더를 공유하는 한계.
   - 내용: 임시 격리 디렉터리 기반 작업 분리 또는 Docker/샌드박스 기반 명령 실행 격리.
