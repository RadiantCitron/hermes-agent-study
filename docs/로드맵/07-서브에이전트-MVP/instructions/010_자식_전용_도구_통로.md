## 1. 구현 내용 명세

1. **상수** ([`constants.py`](../../../../src/hermes_core/constants.py)): `CHILD_TOOL_NAMES = ("terminal", "read_file", "write_file", "patch", "skills_list", "skill_view")`. 자식이 쓸 수 있는 도구의 **허용 목록**이다. 제외 목록(`delegate_task`·`memory`·`session_search`)은 코드에 상수로 두지 않는다. 허용 목록 방식이라야 이후 기본 도구가 늘어도 자식에게 **자동으로 열리지 않는다**(안전한 쪽이 기본). 이 단계에서 쓰지 않는 상수는 만들지 않는다(반복 상한·요약 상한·`source` 값은 이후 단계).
2. **`create_default_dispatcher`에 `include` 인자 추가** ([`dispatcher.py`](../../../../src/hermes_core/tools/dispatcher.py)):
   - 시그니처: `create_default_dispatcher(memory_store=None, session_db=None, include: Optional[Collection[str]] = None)`.
   - `include is None`이면 **현재와 완전히 같다**(8종 전부, 등록 순서 포함).
   - `include`가 주어지면 그 이름의 도구**만** 등록한다. 빈 컬렉션이면 아무것도 등록하지 않는다. 기본 도구 이름 집합에 없는 이름이 들어 있으면 `ValueError`(이름에 오타가 있어도 조용히 빠진 채 통과하지 않게 한다).
   - 도구 정의(이름·핸들러·스키마)는 한 곳에서만 관리한다. 자식용 목록을 따로 복사해 두지 않는다.
3. **`create_child_dispatcher()`** (같은 파일): 인자 없음. `create_default_dispatcher(include=CHILD_TOOL_NAMES)`를 돌려준다. 호출할 때마다 새 인스턴스다. `memory_store`·`session_db`를 받지 않으므로 자식 통로는 기억 저장소와 세션 DB에 **닿을 길이 없다**.
4. **작동원리 갱신**: 없음 (050에서 일괄 반영).
5. **ROADMAP 정정**: 이 지시서 작성 중 확인한 사실 두 가지를 [ROADMAP.md](../ROADMAP.md)에 반영한다 — ① 허용 목록 방식(§6-1·§2-3), ② 기본 에이전트의 도구 8종을 단언하는 기존 시험이 있어 위임 도구는 자동 등록하지 않는다(§3).

## 3. 인수 테스트 시나리오 (구현 전 작성, 임의 변경 금지)

시험 방식: 함수를 직접 호출한다. 모델·네트워크 없음. 기대하는 도구 이름 집합은 **시험 안에 문자열로 직접 적는다**(`CHILD_TOOL_NAMES`를 import해서 기대값으로 쓰지 않는다 — 구현을 기대값으로 삼는 동어반복 방지). 파일 도구를 실행하는 시나리오는 `tmp_path`를 작업 폴더로 `monkeypatch.chdir`한다.

| # | 입력 | 기대 결과 |
|---|---|---|
| 1 | `create_child_dispatcher().get_tools_schema()`의 도구 이름들 | 집합이 정확히 `{"terminal", "read_file", "write_file", "patch", "skills_list", "skill_view"}`이고 개수 6 |
| 2 | 자식 통로에 `delegate_task`·`memory`·`session_search`를 각각 `handle_function_call` | 셋 모두 `success: false`, 오류에 `Unknown tool`. 도구가 실행되지 않음 |
| 3 | `create_default_dispatcher()`(인자 없음)의 도구 이름 | 정확히 기존 8종 `{"memory", "session_search", "terminal", "read_file", "write_file", "patch", "skills_list", "skill_view"}`, 등록 순서도 `memory, session_search, terminal, read_file, write_file, patch, skills_list, skill_view` |
| 4 | 시나리오 3의 8종 집합에서 시나리오 1의 6종을 뺀 차이 | 정확히 `{"memory", "session_search"}` (자식에게 주지 않은 기본 도구가 의도한 둘뿐임) |
| 5 | 같은 도구 이름의 스키마를 기본 통로와 자식 통로에서 각각 꺼내 비교 | 6종 모두 `==` (자식용 스키마가 따로 복사되어 어긋나지 않음) |
| 6 | 자식 통로로 `tmp_path`에 만든 `a.txt`를 `read_file`, `new.txt`를 `write_file` | 둘 다 `success: true`, `new.txt`가 실제로 생성됨 (자식 통로의 파일 도구가 실제로 동작) |
| 7 | 자식 통로로 `write_file(path=".env", ...)`, `read_file(path=".env")` (작업 폴더에 `.env` 존재) | 둘 다 `success: false`, `.env` 내용(비밀 마커 문자열)이 응답에 없음. 쓰기는 파일이 만들어지지도 바뀌지도 않음 (자식 통로도 같은 경로 가드를 통과) |
| 8 | 자식 통로로 `read_file`에 정의되지 않은 인자(`foo=1`) | `success: false`, `Invalid arguments for tool 'read_file'` (인자 검증이 자식 통로에도 동일하게 적용) |
| 9 | `create_default_dispatcher(include=["terminal"])` / `include=[]` | 각각 `terminal`만 / 도구 0개. 둘 다 예외 없음 |
| 10 | `create_default_dispatcher(include=["terminal", "nope"])` | `ValueError`, 메시지에 `nope` 포함 |
| 11 | `create_child_dispatcher()`를 두 번 호출해 한쪽에 `register_tool("extra", ...)` | 다른 쪽 인스턴스와 새로 만든 기본 통로에는 `extra`가 없음 (인스턴스 독립) |
| 12 | `create_default_dispatcher(memory_store=임시 MemoryStore, session_db=임시 SessionDB)` (기존 호출 형태) | 기존과 같이 8종이고 `memory`·`session_search`가 주입한 객체로 동작 (기존 시험이 그대로 통과함으로 갈음하되, 호출 형태가 바뀌지 않았음을 한 번 직접 확인) |
| 13 | 기존 코어 테스트(06 마감 시점 전체) | **수정 없이** 통과 |
