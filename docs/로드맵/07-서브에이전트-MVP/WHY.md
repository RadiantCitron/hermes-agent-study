# [WHY] 07-서브에이전트-MVP — 왜 이 로드맵을, 왜 이 정도로만 하는가

> **성격**: 이 로드맵의 의도를 적은 문서다 (ROADMAP_정책 §3-2). 마감 때 종합보고서(`결과정리및리뷰.md`, 마감 시 작성)가 이 문서의 「검증할 가정」을 하나씩 대조한다. 4단계 착수 후에는 본문을 고치지 않고 맨 끝 「변경 기록」에만 덧붙인다.

## 1. 왜 지금 이 로드맵인가

06번까지로 에이전트는 기억(장기 기억, 과거 대화 검색, 압축, 절차 기억)과 도구(터미널, 파일)를 갖췄다. 그런데 에이전트는 아직 **혼자서 한 줄짜리 대화** 안에서만 일한다. 파일 수십 개를 뒤지거나 여러 번 고쳐 가며 확인하는 일을 맡기면, 그 모든 중간 과정이 같은 대화에 쌓인다. 대화가 부풀면 압축(05)이 일부를 요약하지만, 이는 **이미 쌓인 뒤에 줄이는** 사후 수단이다.

사람이 이 시스템을 맡았을 때 묻는 질문은 이렇다.

- *"큰 일을 시키면 에이전트의 대화가 중간 과정으로 가득 차서 정작 중요한 앞부분을 잊지 않는가?"*
- *"일을 다른 에이전트에게 넘겼다면, 넘겨받은 쪽이 내 기억과 파일을 마음대로 건드리지는 않는가?"*
- *"넘겨받은 쪽이 또 다른 쪽에게 일을 넘기고, 그것이 무한히 이어지지는 않는가?"*
- *"넘긴 일에 든 비용과 호출은 어디에 기록되는가? 내 기록에 섞이지는 않는가?"*

지금은 네 질문에 「구조가 없다」가 정직한 답이다. 이 로드맵은 **일을 격리된 새 대화에서 하고 요약만 돌려받는** 구조를 세운다. 핵심은 일을 넘기는 기능 자체보다, **넘겨받은 쪽이 어디까지 닿을 수 있고 어디에 기록되는지를 구조로 고정하는 것**이다.

## 2. 왜 이 정도로만 하는가

이 로드맵이 **일부러 하지 않는 것**과 그 이유다.

| 하지 않는 것 | 이유 | 언제 하는가 |
|---|---|---|
| 여러 자식을 동시에(병렬) 돌리기 | 스레드, SQLite 동시 쓰기, 호출 원장 교차가 한꺼번에 들어온다. 격리가 맞는지 확인하기도 전에 동시성 문제가 섞인다. 합의한 범위는 순차 단일 자식이다. | 단일 자식의 격리가 검증되고 병렬이 실제로 필요해질 때 |
| 자식이 또 자식을 만들기(중첩) | 도구 목록에서 위임 도구를 빼면 구조적으로 불가능해진다. 허용하려면 깊이 추적과 상한이 필요하다. | 깊이가 필요한 작업이 실제로 생길 때 |
| 백그라운드 실행, 개별 제어(steer/stop), 중단 전파, 타임아웃 | 동기 실행에서는 자식이 끝날 때까지 부모가 기다리므로 필요하지 않다. 중단은 현재 코어에 중단 구조 자체가 없다. | 코어에 중단 구조가 생길 때 |
| 자식 결과의 형식 검증(`output_schema`), 이미지 전달 | 요약 텍스트 반환으로 격리 구조는 충분히 익힌다. | 요약 형식이 문제가 될 때 |
| 작업 폴더 분리(worktree) | 자식의 쓰기가 부모와 같은 작업 폴더에 닿는다. 분리하려면 파일 복사·병합 문제가 따로 생긴다. 03·04의 쓰기 정책이 방어선이다. | 자식 쓰기 사고가 관찰될 때 |
| 자식 모델 별도 지정, 비용 합산 | 한 모델·한 키로 격리의 핵심을 먼저 확인한다. | 모델 비용 차이가 실제로 문제될 때 |
| 원본 현행 HEAD의 확장 기능 전체 | 억지 모방은 안티패턴이다. | 필요가 생겼을 때 |

한마디로, **「일을 넘겨 요약을 받고, 넘겨받은 쪽의 접근 범위와 기록을 구조로 가둔다」까지만** 한다. 위임을 잘 쓰게 만드는 일은 그 이후의 문제다.

## 3. 왜 이 순서, 왜 이 단계 수인가

단계는 여섯 개이고, **가둘 울타리부터, 에이전트 쪽 문을 열고, 도구를 만들고, 안내문은 뒤에, 실제 키는 맨 마지막에** 둔다.

| 순서 | 하는 일 | 왜 이 자리인가 |
|---|---|---|
| 1 (010) | 자식이 쓸 수 있는 도구 목록과 자식 전용 도구 통로를 만든다 | 모델도 에이전트도 필요 없는 조립이다. 「자식에게 무엇을 주지 않을 것인가」를 먼저 고정한다. |
| 2 (020) | 에이전트가 부모 세션과 이어진 자식 세션을 만들 수 있고, 메모리·지시문을 끌 수 있게 한다 | 기존 에이전트의 생성자를 건드리는 유일한 단계다. 파급이 커서 도구보다 먼저 따로 검증한다. |
| 3 (030) | 위임 도구를 만들어 부모 도구 통로에 등록한다 | 010·020이라는 부품 위에 서는 단계다. 별도 클라이언트로 원장을 분리하는 핵심이 여기서 확인된다. |
| 4 (040) | 시스템 지시문에 위임 안내 한 덩어리를 더한다 | 지시문은 모든 대화의 앞부분이라 파급이 크다. 도구가 검증된 뒤 한 번만 건드린다. |
| 5 (050) | 가짜 통신으로 「위임 → 자식이 도구 사용 → 요약 반환 → 부모 응답」을 시험한다 | 부품별 시험이 아니라 합쳐졌을 때의 격리를 확인한다. |
| 6 (060) | 진짜 키로 딱 한 번, 모델이 스스로 위임하는지 본다 | 모델이 실제로 위임 도구를 부르는지는 가짜 모델로 알 수 없다. 비용 때문에 마지막에, 사용자가 지시할 때만 한다. |

010과 020을 합치지 않는 이유는, 하나는 새 모듈이고 하나는 기존 에이전트 수정이라 같은 단계에 섞이면 회귀 원인을 찾기 어렵기 때문이다.

## 4. 왜 이 방식을 택하고 무엇을 배척했나

| 선택 | 배척한 대안 | 이유 |
|---|---|---|
| 자식은 새 대화에서 시작하고 부모 이력을 보지 못한다 | 부모 이력 상속 | 이력을 보여 주면 격리의 이점(대화가 부풀지 않음)이 사라진다. 필요한 배경은 부모가 `context`로 의도적으로 넘긴다. |
| 자식 전용 도구 통로를 따로 만든다 | 부모 통로에서 목록만 숨기기 | 숨기는 것과 막는 것은 다르다. 자식 통로에는 위임 도구가 아예 없으므로 재귀가 규칙이 아니라 구조로 불가능하다. |
| 자식에게 기억·과거 검색·위임 도구를 주지 않는다 | 부모와 같은 도구 | 기억을 고치거나 부모 이력을 우회해 읽거나 무한히 위임할 길을 닫는다. |
| 자식은 별도 클라이언트로 호출하고 원장도 자식 세션에 쌓는다 | 클라이언트 공유 후 사후 구분 | 기록기가 하나라 공유하면 한쪽으로 섞인다. 상태 변화를 숨기는 임시 방편은 쓰지 않는다. |
| 자식 실패를 결과 항목으로 돌려준다 | 예외 전파 | 부모 루프가 도구 결과 하나로 읽고 스스로 대응하게 한다. 부모가 죽지 않는다. |
| 요약에 길이 상한을 둔다 | 전부 반환 | 자식 한 명이 부모 문맥을 한 번에 키우는 것을 막는다. |
| 원본에서 구조(새 대화, 제한 도구, 요약 반환)만 참고한다 | 원본 이식 | 현행 버전은 비동기·역할·스키마 검증 등으로 크게 늘었다. |

## 5. 성공 판단 기준과 검증할 가정

**성공 기준**: 가짜 통신으로 모든 시험이 통과하고, 부모가 위임하면 자식이 새 대화에서 도구를 써서 일을 하고 요약이 부모에게 돌아오며, 자식이 위임·기억·과거 검색 도구를 쓰려는 시도가 모두 막히고, 자식의 호출 기록이 자식 세션에만 쌓이며, 부모 대화에는 자식의 중간 과정이 들어가지 않고, 기존 테스트가 한 줄도 바뀌지 않고 통과하며, 사용자가 지시하면 진짜 키로도 모델이 위임하는 것이 관찰되고, 그 과정에서 키가 어디에도 남지 않는다.

마감 때 종합보고서가 아래 가정을 하나씩 「맞았다 / 틀렸다 / 바뀌었다」로 대조한다.

| 번호 | 가정 | 틀렸다면 |
|---|---|---|
| **A** | 자식 전용 도구 통로를 따로 조립하는 것만으로 재귀 위임·기억 쓰기·과거 검색 접근이 모두 구조적으로 막힌다. | 우회 경로를 찾아 통로 조립 방식을 고친다. |
| **B** | 클라이언트를 자식마다 새로 만들면 자식 호출이 부모 원장에 섞이지 않는다. 실제 클라이언트에서 호출 기록기와 연결 설정을 복제할 수 있다. (**미확인**: 클라이언트의 키·전송 설정을 복제하는 방법은 030에서 코드로 확정) | 팩토리 계약을 바꾸거나 기록기 구조를 고친다. |
| **C** | `HermesAgent`에 자식용 인자를 더해도 기존 호출부와 기존 시험이 한 줄도 바뀌지 않는다. | 인자 기본값이나 위치를 고치고 결합 원인을 분리한다. |
| **D** | 자식 세션을 `parent_session_id`·`source="subagent"`로 만들면 부모의 `session_search`에 자식 대화가 섞이지 않는다. | 검색 필터나 `source` 규약을 고친다. |
| **E** | 위임 안내문 추가는 시스템 지시문의 불변성, 압축의 헤드 보존, 기존 지시문 시험과 충돌하지 않는다. | 안내문 위치나 주입 방식을 바꾼다. |
| **F** | 요약 상한(후보 값은 ROADMAP에서 확정)이 일반 자식 응답에 충분하고 잘림이 드물다. (**미확인**: 실제 자식 응답 길이 분포는 060에서 한 번 관찰할 뿐) | 상한을 조정한다. |
| **G** | 안내문만으로 실제 모델이 필요할 때 위임 도구를 부르고, 자식은 `goal`만으로 일을 끝낸다. (**미확인**: 이 모델로 해 본 적이 없다.) | 안내문을 고치거나 자식 프롬프트를 보강한다. |
| **H** | 기존 테스트가 한 줄도 바뀌지 않고 통과한다. 위임 도구와 안내문 추가가 기존 도구·압축·DB에 영향을 주지 않는다. | 결합이 있다는 뜻이므로 원인을 찾아 분리한다. |

## 6. 알려진 위험과 아직 확인하지 못한 것

- **자식의 쓰기가 부모와 같은 작업 폴더에 닿는다**: 자식이 파일을 망가뜨려도 부모 대화와 달리 되돌릴 수 없다. 03·04의 쓰기 정책(새 파일만, 보호 이름, 지시문 파일 금지)이 유일한 방어선이다.
- **요약은 모델이 쓴 글이다**: 자식이 한 일을 틀리게 요약할 수 있다. 07은 부모가 이를 검증하게 하지 않는다.
- **비용이 곱해질 수 있다**: 부모가 위임을 여러 번 부르면 자식 호출이 곱해진다(부모 반복 횟수 × 자식 반복 상한). 상한이 비용의 유일한 제어다.
- **모델이 위임을 안 부르거나 남용할 수 있다**: 06에서 스킬을 안 부른 관찰이 있었다. 07도 안내문 한 덩어리로 유도하고 스모크에서 한 번 관찰할 뿐이다(가정 G).
- **자식 토큰이 부모 합계에 없다**: 부모 세션 지표만 보면 비용이 작게 보인다.
- **원본 현행 HEAD의 내부 동작 일부는 읽지 않았다**: 「미확인」으로 ADR-0007에 적었다.
