## 1. 왜 지금 이 로드맵인가

에이전트는 06번에서 「절차 기억」(스킬)을 갖게 되었다. 팀의 릴리스 절차처럼 모델이 사전 지식으로는 알 수 없는 일을 파일로 적어 두면, 필요할 때 꺼내 읽는다. 그런데 이 기억은 **모델이 스스로 「스킬이 있을까?」 하고 찾아봐야만** 쓰인다. 찾아보라는 안내문은 있지만 어떤 스킬이 있는지는 보여 주지 않는다.

실제 모델로 해 본 결과가 갈렸다. 같은 질문(「우리 팀의 릴리스 절차를 순서대로 알려줘」)에 한 모델은 스킬 목록을 보지도 않고 과거 대화 검색과 명령 실행으로 헤맸고, 다른 모델은 스스로 스킬을 찾아 정확히 답했다. 두 모델, 각 1회씩이라 원인을 단정할 수는 없다.

사람이 이 시스템을 맡았을 때 묻는 질문은 이렇다.

- *"스킬을 써 두었는데 에이전트가 그 사실을 모르고 엉뚱하게 헤매지 않는가?"*
- *"목록을 보여 주면 에이전트의 앞부분 지시문이 길어지고, 그것이 세션 도중 바뀌어 기억을 흔들지는 않는가?"*
- *"스킬 파일에 적힌 글이 에이전트의 지시문이 되어 버리면, 누가 거기에 무엇을 써도 되는가?"*

지금은 첫 질문에 「모델에 따라 다르다」, 나머지에 「아직 그런 경로가 없다」가 답이다. 이 로드맵은 **스킬의 이름과 한 줄 설명만 세션 시작 때 한 번 보여 주고**, 그것이 지시문의 안정성과 안전을 해치지 않게 가두는 구조를 세운다. 06 때 「모델이 도구만으로는 스킬을 잘 못 찾는다는 증거가 나오면 하겠다」고 미뤄 둔 바로 그 일이다.

## 2. 왜 이 정도로만 하는가

이 로드맵이 **일부러 하지 않는 것**과 그 이유다.

| 하지 않는 것 | 이유 | 언제 하는가 |
|---|---|---|
| 위임 쪽 안내문이나 동작을 고치기 | 위임은 두 모델 모두 쓰지 않았지만 자료가 파일 5개뿐이라 「직접 푸는 게 합리적이었다」고 읽힐 여지가 크다. 증거가 약한 채 고치면 근거 없는 수정이다. 한 로드맵에서 두 가지를 고치면 어느 쪽 효과인지도 가려진다. | 파일을 늘린 자료의 관찰이 쌓인 뒤 다음 로드맵에서 |
| 스킬 본문을 지시문에 넣기 | 스킬이 늘수록 모든 대화의 기본 짐이 커지고, 이름 → 본문 → 부속 파일로 단계적으로 꺼내 읽는 06의 장점이 사라진다. | 하지 않는다 |
| 질문과 스킬을 자동으로 맞춰 미리 읽어 넣기 | 맞추는 장치가 새 시스템이 되고 틀린 스킬을 줄 수 있다. 이번 목적은 모델이 스스로 고르도록 돕는 것이다. | 목록을 보여 줘도 못 고른다는 증거가 나올 때 |
| 세션 도중 스킬 변화를 목록에 반영하기 | 지시문이 도중에 바뀌면 캐시와 압축의 「앞부분은 변하지 않는다」는 전제가 깨진다. 새 스킬은 `skills_list` 도구가 실시간으로 보여 준다. | 필요가 실제로 생길 때 |
| 외부에서 스킬을 가져오는 기능, 스킬을 만들고 고치는 기능 | 누가 쓴 글이 지시문에 실릴지 통제할 수 없게 된다. 이번 신뢰 전제(내 폴더의 내 글)가 깨진다. | 그 기능을 만들 때 신뢰 경계를 다시 결정 |
| 원본 현행 버전의 인덱스 기능 전체 | 카테고리 축약, 스냅샷 파일, 다중 폴더 우선순위 등으로 크게 늘어 있다. 억지 모방은 안티패턴이다. | 필요가 생겼을 때 |

한마디로, **「스킬이 있다는 사실을 모델이 첫 호출부터 알게 한다」까지만** 한다. 모델이 그 사실을 얼마나 잘 쓰느냐는 그 이후의 문제다.

## 3. 왜 이 순서, 왜 이 단계 수인가

단계는 다섯 개이고, **글을 만드는 부분부터, 에이전트에 붙이는 일은 그다음, 문구는 뒤에, 실제 모델은 맨 마지막에** 둔다.

| 순서 | 하는 일 | 왜 이 자리인가 |
|---|---|---|
| 1 (010) | 스킬 목록을 안전하게 한 덩어리 글로 만드는 부분을 따로 만든다 | 모델도 에이전트도 필요 없다. 「지시문에 실릴 글을 무엇으로 가둘 것인가」(정제·길이 상한)를 가장 먼저 고정한다. 신뢰 경계의 핵심이다. |
| 2 (020) | 켜 둔 에이전트가 세션을 시작할 때 이 글을 한 번 붙인다. 기본은 꺼짐이라 자식·기존 구성·스킬 도구가 없는 구성에는 붙지 않는다 | 기존 에이전트의 앞부분 조립을 건드리는 유일한 단계라 파급이 크다. 글 만드는 부분이 검증된 뒤에 붙인다. |
| 3 (030) | 목록에 붙일 제목과 규칙 문장을 확정한다 | 문구는 모델 반응에 영향을 주지만 구조와는 독립이다. 구조가 굳은 뒤 한 번만 정한다. |
| 4 (040) | 가짜 통신으로 전체 흐름과 안정성을 확인하고, 시스템 설명서(작동원리)를 사실에 맞춘다 | 실제 모델 전에 남은 모든 구멍을 돈 없이 확인한다. |
| 5 (050) | 실제 모델 두 종으로 한 번씩 확인하고 마감한다 | 가짜로는 판정할 수 없는 「모델이 실제로 목록을 보고 부르는가」를 본다. 키와 비용이 드는 유일한 단계라 사용자 지시가 있을 때만 한다. |

한 단계를 쪼개거나 합치지 않은 이유: 010은 모델 없이 시험되고, 020은 에이전트 한 곳만 바꾸며, 025는 앱에서 켜는 한 줄이고, 030은 글 한두 문장이다. 각 단계가 독립된 검증 대상을 갖는다. (025는 020 지시서 작성 중 코드 대조로 생겼다: 기존 시험이 「스킬이 있어도 프롬프트에 스킬 이름이 없다」를 단언해, 기본 꺼짐 + 앱에서 켜기를 택했기 때문이다.)

## 4. 왜 이 방식을 택하고 무엇을 배척했나

| 선택 | 배척한 대안 | 이유 |
|---|---|---|
| 이름과 한 줄 설명만 지시문에 보여 주고 본문은 계속 도구로 읽는다 | 본문 전체를 보여 주기 | 지시문이 부풀고 단계적으로 꺼내 읽는 구조가 무너진다. |
| 세션이 시작될 때 한 번만 만들고 그대로 둔다 | 매 턴 다시 만들기 | 앞부분이 바뀌면 캐시와 압축의 불변 전제가 깨진다. 최신 목록은 도구가 준다. |
| 스킬 설명을 한 줄로 접고 구조를 깨는 문자를 지우고 길이를 제한한다 | 설명을 있는 그대로 싣기 | 파일에 적힌 글이 지시문의 제목·구획을 위조하지 못하게 한다. 단, 글 속 「이전 지시를 무시하라」 같은 문장의 내용까지는 걸러 주지 못한다는 한계를 문서에 적는다. |
| 상한을 넘으면 「나머지는 도구로 보라」고 알린다 | 상한 없이 전부 싣기 / 말없이 자르기 | 숨기지 않고 도구로 이어 준다. |
| 기본은 꺼짐이고 앱이 켠다. 자식은 켜지 않는다 | 기본 켜짐 + 자식만 끄기 | 기본 켜짐이면 이전 결정(스킬이 있어도 지시문에 스킬 이름이 없다)을 단언하는 기존 시험을 고쳐 써야 한다. 꺼짐이 기본이면 기존 구성이 한 글자도 바뀌지 않고, 자식도 별도 수정 없이 부모가 일러 준 한 가지 일만 한다는 07의 원칙을 지킨다. |
| 규칙 문장은 「훑고, 관련 있으면 읽어라」 수준으로 한다 | 「반드시 읽어라」식 강한 강제 | 스킬이 늘수록 매 질문마다 불필요하게 읽는 비용이 늘 수 있다. 약하게 시작해 관찰한다. |
| 원본에서는 「목록 + 규칙 문장」이라는 구조만 참고한다 | 원본 이식 | 현행 버전은 기준 시점에 없던 기능이고 크게 확장돼 있다. |

## 5. 성공 판단 기준과 검증할 가정

**성공 기준**: 가짜 통신으로 모든 시험이 통과하고, 스킬이 있는 세션의 지시문에 이름·한 줄 설명 목록이 정확히 한 번 실리며, 그 글이 세션 내내 바뀌지 않고, 스킬이 없거나 스킬 도구가 없는 구성의 지시문은 이전과 한 글자도 다르지 않으며, 설명에 섞인 줄바꿈·구획 위조 문자가 구조를 깨지 못하고, 자식 프롬프트에는 목록이 없고, 기존 시험이 한 줄도 바뀌지 않고 통과하며, 사용자가 지시하면 실제 모델에서 목록이 보인 채 스킬 호출 여부를 관찰해 기록한다.

마감 때 종합보고서가 아래 가정을 하나씩 「맞았다 / 틀렸다 / 바뀌었다」로 대조한다.

| 번호 | 가정 | 틀렸다면 |
|---|---|---|
| **A** | 목록을 보여 주면 이전에 스킬을 부르지 않던 모델(deepseek)도 같은 질문에서 `skills_list` 또는 `skill_view`를 부른다. (**미확인**: 1회 관찰이 전부다. 못 불러도 구조를 되돌리지 않고 「모델 한계, 관찰 기록」으로 남기고 멈춘다.) | 규칙 문장을 보강하는 후속 로드맵을 제안한다. 이 로드맵은 여기까지로 한다. |
| **B** | 세션 시작 때 한 번 만든 목록은 세션 내내 같고, 05의 압축 뒤에도 앞부분 글이 한 글자도 변하지 않는다. | 조립 시점이나 캐시 방식을 고친다. |
| **C** | 인덱스를 켜지 않은 구성(기본값)과, 켜더라도 스킬 폴더가 없거나 비어 있거나 스킬 도구가 등록되지 않은 구성에서는 지시문이 이전과 한 글자도 다르지 않다. | 조건 판단을 고친다. 기존 사용자에게 영향이 있다는 뜻이다. |
| **D** | 항목 수·줄 길이·전체 길이 상한으로 스킬이 많아도 목록이 일정 길이를 넘지 않고, 잘린 사실은 알려진다. (**미확인**: 후보 값 50개·120자·4,000자가 실제 사용에 충분한지는 스모크에서 한 번 볼 뿐) | 상한을 조정한다. |
| **E** | 설명을 정제하면 줄바꿈·제어문자·구획 위조(`<`·`>`)로 목록 구조를 깨거나 지시문 제목을 위조하는 시도가 모두 막힌다. (이것은 **구조**에 대한 가정이다. 자연어 지시 내용은 걸러지지 않는다.) | 정제 규칙을 보강한다. |
| **F** | 자식 프롬프트에는 목록이 들어가지 않고(켜지 않은 기본값), 자식은 스킬 도구를 그대로 쓴다. | 자식 생성부의 기본값 전달을 고친다. |
| **G** | 이미 스킬을 부르던 모델(Gemini Flash)이 목록 추가 뒤에도 정상으로 부르고 같은 답을 낸다(회귀 없음). | 규칙 문장이 오히려 방해했다는 뜻이므로 문장을 약화한다. |
| **H** | 기존 시험이 한 줄도 바뀌지 않고 통과한다. 인덱스 추가가 도구·압축·DB·위임에 영향을 주지 않는다. | 결합이 있다는 뜻이므로 원인을 찾아 분리한다. |
| **I** | 코드와 문구를 바꾸지 않고 파일을 늘린 자료로 위임 관찰을 해 기록할 수 있다. 결과가 어떻든 이번 로드맵에서는 위임을 고치지 않는다. (**미확인**: 모델의 반응은 모른다.) | 관찰 방법을 바꾼다. 위임 수정은 다음 로드맵 몫이다. |

## 6. 알려진 위험과 아직 확인하지 못한 것

- **새 신뢰 경로**: 스킬 설명이 지시문에 실린다. 정제는 구조만 지킨다. 지금은 스킬 폴더가 사용자 본인이 관리하는 영역이라는 전제 위에 있고, 외부에서 스킬을 가져오는 기능이 생기면 다시 결정해야 한다.
- **스킬이 많을 때**: 상한에서 잘리면 뒤쪽 스킬은 목록에 없다. 모델이 `skills_list`로 확인해야 보인다.
- **목록이 있어도 안 부를 수 있다**: 모델의 선호는 지시문 설계만으로 정해지지 않는다. 2종 1회의 관찰이라는 한계가 계속된다.
- **세션 중 추가한 스킬**: 다음 세션부터 목록에 나온다. 도구로는 즉시 보인다.
- **규칙 문장의 부작용**: 문장이 강하면 불필요한 로딩이 늘어 호출 수와 비용이 는다. 약하게 시작했다.
- **위임 관찰의 해석**: 파일을 늘려도 모델이 직접 푸는 쪽을 택할 수 있다. 그 자체가 관찰 결과이고, 이번에 고치지 않는다.
- **원본 현행 HEAD의 인덱스 내부 동작 일부는 읽지 않았다**: 「미확인」이다. 우리 구현은 원본을 따라가지 않는다.

## 변경 기록

(4단계 착수 후 계획이 바뀌면 여기에 날짜와 이유를 덧붙인다.)

- 2026-10-29 (착수 전, 020 지시서 작성 중): 자식 제외 방식을 「기본 켜짐 + `skip_skills_index`」에서 「기본 꺼짐 + `skills_index`(앱이 켬)」으로 바꿨다. 이유: 기존 시험 `test_scenario_05_skills_list_not_injected_into_prompt`가 ADR-0006의 구 결정을 단언해 기본 켜짐이면 깨진다. 사용자가 선택했다. §3 단계 표(025 추가, 030 범위), §4 선택 표, 가정 C·F 문구를 이에 맞췄다. 근거 [ADR-0008](../../adr/0008-스킬_인덱스_주입_범위와_신뢰_경계.md) §2-5(개정).
- 2026-10-29 (착수 전, 025 지시서 작성 중): 앱(CLI)이 켜는 방식을 정했다 — 모의·실제 두 모드 모두 기본 켜짐, `--no-skills-index`로 끔. 이유: 모드마다 프롬프트가 갈라지는 분기를 만들지 않고, 050 스모크에서 같은 모델로 켠 경우와 끈 경우를 비교하기 위해서다. 07의 `--delegate`(기본 꺼짐)와 다른 이유는 이 로드맵의 목적이 앱 사용자에게 스킬의 존재를 알리는 것이기 때문이다.
