# [구현지시서 050] 실제 키 스모크 (사용자 지시가 있을 때만 실행) 및 마감

> **상위 대시보드**: [08-README.md](../README.md)  
> **선행 조건**: 040 단계 완료 (`Done`) **그리고 사용자의 명시적 실행 지시**. 마감은 추가로 사용자의 종료 선언이 있을 때만 한다.  
> **근거**: [WHY.md](../WHY.md) 가정 A·B·D·G·I, [ADR-0008](../../../adr/0008-스킬_인덱스_주입_범위와_신뢰_경계.md), 형식 선례: [07의 060](../../07-서브에이전트-MVP/instructions/060_실제키_스모크와_마감.md), 관찰 기준선: [06 060](../../06-스킬-시스템-MVP/instructions/060_실제키_스모크.md)·[계획 009](../../../계획/009-Gemini_Flash_도구호출_관찰스모크.md)  
> **성격**: 코드·문구를 바꾸지 않는 **실행·검증 단계**다. 지시서는 절차와 기대 결과만 정한다. 실행 결과는 대시보드와 종합보고서에 기록한다.

## 1. 목적

가짜 통신으로 모든 시험이 통과한 상태에서, 실제 모델·실제 클라이언트로 다음을 확인한다.

1. **가정 A**: 인덱스를 보여 주면 이전에 스킬을 부르지 않던 모델(deepseek)이 같은 질문에서 `skills_list` 또는 `skill_view`를 부르는가. 같은 날·같은 자료로 인덱스를 **켠 경우와 끈 경우(`--no-skills-index`)**를 나란히 본다.
2. **가정 G**: 이미 스킬을 부르던 모델(Gemini Flash)이 인덱스를 켠 뒤에도 정상으로 부르고 같은 답을 내는가(회귀 없음).
3. **가정 B**: 실제 요청에서 인덱스 구획이 헤드에 한 번 실리고 호출 사이에 바이트 동일한가.
4. **가정 D**: 스킬이 많을 때 인덱스가 상한(50개·4,000자)에서 잘리고, 첫 조립이 눈에 띄게 느려지지 않는가(로컬 측정, 키 불필요).
5. **가정 I**: 코드와 문구를 바꾸지 않고, 파일을 늘린 자료(40개)로 위임 관찰을 기록할 수 있는가. **결과가 어떻든 이번에는 위임을 고치지 않는다.**
6. 키가 어디에도 남지 않는가. 비용·호출 수.

## 2. 사전 조건 (사용자가 확인)

1. 키 변수 이름은 `OPENROUTER_API_KEY`다. 사용자의 셸에서 이 이름으로 내보냈는지만 확인한다. 에이전트는 `.env`를 열지 않는다.
2. **별도 터미널**(에이전트 세션이 아닌 사용자의 터미널)에서 직접 환경변수로 키를 내보낸다. **키는 에이전트와의 대화·명령줄·프롬프트에 절대 쓰지 않는다** ([AGENTS.md](../../../../AGENTS.md) §3).
3. `pytest tests -q`가 모두 통과한다.
4. **모델 ID**: deepseek는 `DEFAULT_REAL_MODEL`(`--model`을 주지 않음). Gemini는 009에서 확인된 `google/gemini-3.8-flash`이며 실행 직전에 OpenRouter에서 한 번 더 확인한다. 명령은 **한 줄로 붙여 넣고 입력기 상태를 영문으로** 둔다(009에서 ID 끝에 한글 한 글자가 붙어 400이 난 전례가 있다). 시작 화면의 `Model:` 줄이 의도한 ID와 정확히 같은지 본 뒤에 질문을 입력한다.
5. **임시 상태 폴더**: 실제 `.hermes`를 쓰지 않고 레포 밖 임시 폴더(세션 scratchpad 등)를 실행마다 따로 `HERMES_HOME`으로 쓴다. 에이전트가 그 경로를 사용자에게 알려 주며, 레포의 문서·대시보드에는 로컬 경로 대신 `<임시>`로 적는다. 에이전트는 키가 없는 **가짜 자료만** 만든다:
   - **스킬 폴더(runs A1·A0·G1)**: 폴더마다 `skills/release/SKILL.md`. 머리말 `name: release-procedure`, `description: Team release procedure for this project`, 본문은 모델이 사전 지식으로 알 수 없는 고유 절차(예: 「1) 브랜치 이름은 `rel-PELICAN`으로 만든다 2) 마지막에 `PELICAN-7`이라고 보고한다」). 이 마커가 답에 나오면 모델이 본문을 읽은 것이다.
   - **위임 자료(runs D1·D2)**: 스킬 폴더 **없음**(인덱스 변수를 빼려는 것). `workspace/data/f01.txt`~`f40.txt` 40개. 각 파일은 여러 줄의 잡다한 문장 사이에 모델이 사전 지식으로 알 수 없는 **고유 줄** `CODE: <단어>-<숫자>`를 정확히 하나 가진다(40개 모두 서로 다름). 기대 코드 표는 에이전트가 레포 밖 임시 위치에 따로 보관한다(레포에 기록하지 않음).
6. 비용 상한: 5회 실행(질문 각 1턴). 호출 수는 스킬 질문 3~6회 안팎, 위임 자료는 파일 40개를 명시해 읽으므로 더 길 수 있다(위임이 일어나면 부모 2~3회 + 자식 수 회~25회 이내). 공개 단가 기준 수 센트 미만으로 예상하나 **실제 청구는 확인하지 못한다**. 예상보다 호출이 많아 보이면 사용자가 `Ctrl-C`로 멈춘다(자동 중단은 없다).

## 3. 절차

사용자는 레포 루트에서 `HERMES_HOME=<임시>/<실행명> .venv/bin/python -m hermes_core.cli [옵션]`을 직접 실행한다. 에이전트는 이 실행을 대신하지 않는다. 실행마다 질문 1개만 입력하고 `exit`한다.

| 실행 | 모델 | 옵션 | 자료 | 입력 |
|---|---|---|---|---|
| **A1** | deepseek | (기본: 인덱스 켜짐) | 스킬 폴더 | `우리 팀의 릴리스 절차를 순서대로 알려줘.` |
| **A0** | deepseek | `--no-skills-index` | A1과 같은 스킬 폴더(별도 임시 폴더에 같은 내용) | 같은 입력 |
| **G1** | `google/gemini-3.8-flash` | `--model google/gemini-3.8-flash` | 스킬 폴더 | 같은 입력 |
| **D1** | deepseek | `--delegate` | 40개 자료 | `data 폴더에 있는 모든 텍스트 파일에서 CODE: 로 시작하는 줄을 찾아서 파일 이름 순서로 정리해 알려줘.` |
| **D2** | `google/gemini-3.8-flash` | `--delegate --model google/gemini-3.8-flash` | 40개 자료 | 같은 입력 |

| 순서 | 동작 |
|---|---|
| 1 | 에이전트가 실행별 임시 `HERMES_HOME`에 가짜 자료를 만들고, 만든 직후 파일 해시와 `HERMES_HOME` 직하위 항목 이름을 기록 |
| 2 | **(키 불필요, 에이전트)** 스킬 200개를 별도 임시 `HERMES_HOME`에 만들고(이름 `s000`~`s199`, 설명은 40자 이하의 짧은 영문. 그래야 50줄이 4,000자 안에 들어가 항목 수 상한이 먼저 걸린다), 레포의 `.venv` 파이썬으로 `HermesAgent(skills_index=True)`를 매번 새로 만들어 `_build_system_prompt()`의 소요 시간을 `time.perf_counter()`로 3회 측정하고 결과 인덱스 블록의 줄 수·길이를 기록 |
| 3 | 사용자가 위 표의 A1 → A0 → G1 → D1 → D2를 별도 터미널에서 하나씩 실행(시작 화면의 모드·모델·`Skills index disabled` 줄·`Delegation enabled` 줄을 확인) |
| 4 | 사용자가 응답을 확인하고 비밀을 뺀 화면 출력을 에이전트에게 전달 |
| 5 | 에이전트가 원장(`messages`, `llm_calls`, `sessions`)을 **읽기 전용**으로 조회해 §4를 채운다 |
| 6 | 사용자가 별도 터미널에서 키 값을 출력하지 않고 각 실행의 `state.db` 파일에 키가 들어 있는지 확인하고 결과(`True`/`False`)만 전달 |

실패(오류 종료, 인덱스가 있는데도 스킬 미호출, 위임 미호출, 이상한 응답)하면 **자동으로 다시 시도하거나 코드·문구를 고치지 않는다.** 원인을 기록하고 멈춰서 보고한다. 같은 실행을 다시 하려면 사용자의 새 지시가 필요하다. 모델이 스킬이나 위임 도구를 쓰지 않고 다른 도구로 풀어도 오류가 아니다. 그 사실이 관찰 결과다.

## 4. 기대 결과와 확인 항목

원장 조회는 에이전트가 읽기 전용으로 한다. 판정은 통과/실패가 아니라 **가정을 「맞았다 / 틀렸다 / 바뀌었다」로 기록**하는 것이다.

| # | 확인 | 기대 결과 |
|---|---|---|
| 1 | **인덱스 노출 (A1·G1)** | `sessions.system_prompt`에 구획 전체(제목 `## Available Skills` + 규칙 문장 + `<available_skills>\n- release-procedure: Team release procedure for this project\n</available_skills>`)가 정확히 1번 있다 |
| 2 | **끈 경우 (A0)** | `sessions.system_prompt`에 `## Available Skills`와 `<available_skills>`가 없다. 시작 화면에 `Skills index disabled (--no-skills-index).`가 1번 나왔다 |
| 3 | **본문 미주입 (A1·A0·G1)** | 첫 호출 `llm_calls.request_json`에 `PELICAN`이 **없다**(모델은 도구로만 읽었다) |
| 4 | **가정 A (deepseek)** | A1에서 `skills_list` 또는 `skill_view` 호출이 있는가, 도구 호출 순서, 최종 응답에 `PELICAN-7`이 있는가를 기록한다. **A0(끈 경우)와 나란히** 적는다. 호출했으면 가정 A는 「맞았다」, 안 했으면 「틀렸다」(모델 한계로 기록하고 구조를 되돌리지 않는다) |
| 5 | **가정 G (Gemini)** | G1에서 `skill_view`를 호출했고 최종 응답에 `PELICAN-7`·`rel-PELICAN`이 있는가. 009 S2(인덱스 없이 `session_search`+`skills_list` → `skill_view`)와 호출 수·순서를 비교해 적는다. 부르지 않았거나 답이 틀리면 「틀렸다」(규칙 문장이 방해했을 가능성을 기록) |
| 6 | **가정 B: 헤드 불변** | A1·A0·G1 각각 첫 호출과 마지막 호출의 `request_json` 첫 system 메시지가 동일 |
| 7 | 모든 호출 정상 | 모든 `llm_calls`의 `error_kind`가 NULL (아니면 어느 실행의 몇 번째 호출인지 기록) |
| 8 | **가정 D: 상한 (로컬 측정)** | 200개 스킬에서 인덱스 블록이 정확히 50줄 + `(+150 more; use skills_list to see all)` 한 줄이고 길이 ≤ 4,000. `_build_system_prompt()` 소요 시간(ms) 3회를 기록(통과/실패 기준 없음, 눈에 띄게 느린지만 기록) |
| 9 | **가정 I: 위임 관찰 (D1·D2)** | `delegate_task` 호출 유무, 도구 호출 순서, 응답의 40개 코드 중 정확한 개수, 호출했다면 `goal`·`context` 실제 문장과 자식 세션의 `llm_calls` 분리·요약 길이/`truncated`. 판정이 아니라 기록이다. **어떤 결과여도 위임 코드·문구를 고치지 않는다** |
| 10 | 읽기 전용 확인 | 스킬 파일 해시, `data/` 파일 해시, `HERMES_HOME` 직하위 항목이 실행 전과 같다(상태 DB·`memories/`는 에이전트가 만든 것이므로 이름만 기록) |
| 11 | **키 미저장** | 5개 실행 모두 `state.db`에 키가 없다. **사용자가 별도 터미널에서** 확인한 `True`/`False` |
| 12 | 비용·호출 수·토큰 | 실행마다 `llm_calls` 호출 수와 입력·출력 토큰을 적는다. **A1 대 A0의 입력 토큰 차**로 인덱스 구획의 비용을 기록한다. 단가를 알 수 없으면 비용은 「미계산」 |
| 13 | 출력·로그 | 키 값이 화면·로그에 없다 |

## 5. 결과 기록

- 대시보드 실행 기록에 날짜, 지시 문구, 실행별(A1·A0·G1·D1·D2) 호출 수·도구 순서·토큰, 가정별 판정을 적는다.
- 확인 항목 4·5·8·9의 관찰을 **그대로** 종합보고서의 「목표와 결과」·「새로 발견한 부분」에 옮긴다. 관찰이 기대와 달라도 코드·문구는 이 단계에서 고치지 않고, 후속 제안만 근거와 함께 적는다.
- **판정의 한계**: 모델 2종, 실행별 1회다. 성공해도 보장이 아니며 실패해도 우연일 수 있다. 스킬이 1개뿐이라 모델이 목록에서 고르는 어려움을 거의 겪지 않는다. 위임 자료는 파일 40개가 위임에 유리했는지 불리했는지 알 수 없다. 이 한계를 종합보고서에 함께 적는다. 비용 단가는 확인하지 못했다.

## 6. 마감 (5단계, 사용자의 종료 선언이 있을 때만)

[ROADMAP_정책.md §5](../../ROADMAP_정책.md)가 정본이다. 이 로드맵에 해당하는 순서만 적는다.

1. **종합보고서** `결과정리및리뷰.md`를 정책의 9개 항목으로 상세히 쓴다. `WHY.md`의 가정 A~I를 **하나씩** 「이뤘다 / 못 이뤘다 / 바뀌었다」로 근거(커밋 해시·시험·이 스모크의 관찰)와 함께 대조한다. 대조하지 않은 가정이 있으면 마감하지 않는다. 가정 C·F는 020 시점에 「기본 꺼짐」으로 문구가 바뀌었음(WHY 변경 기록)을 「바뀌었다」로 기록한다.
2. **대시보드** `README.md`의 전체 상태를 `Closed`로, 시작·완료 일자와 종합보고서 링크를 채운다. 050 행과 실행 기록을 갱신한다. 실행 기록의 커밋 칸은 같은 커밋에서 자기 해시를 쓰지 않는다(정책 §4).
3. **`docs/인계.md`** 를 갱신한다(상태가 바뀌는 작업의 완료 보고).
4. **작동원리 01편 ③의 「미확인」 줄**(실제 모델이 인덱스를 보고 스킬을 더 부르는지)은 이번 관찰과 그 한계로 갱신할 수 있다. 이 갱신은 마감 보고에서 **제안만** 하고, 사용자가 지시하면 수행한다.
5. **커밋과 태그**: 스모크 결과 기록과 마감이 같은 지시로 요청되면 하나의 마감 커밋(`docs(core): R08-마감 - ...`), 스모크 기록이 먼저면 `R08-050` 기록 커밋 뒤 마감 커밋을 따로 만든다. 변경 파일을 경로로 지정해 스테이징한다. **마감 커밋에만** 가벼운 태그 `roadmap-08-closed`를 단다. 푸시와 태그 푸시는 하지 않으며 사용자의 별도 지시가 있을 때만 한다.
6. 마감 후 구현지시서(`instructions/`)는 수정하지 않는다.
7. **후속 인계**: 종합보고서 §8에 다음 로드맵 후보를 적는다. 후보 방향은 스모크 결과에 따른다(예: 위임 평가 규모·문구, REPL 안정성, 작업 환경 격리).
