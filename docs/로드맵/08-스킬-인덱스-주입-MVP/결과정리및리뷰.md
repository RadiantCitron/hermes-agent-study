## 1. 개요 및 배경

06번 로드맵에서 구축된 스킬 시스템(`skills_list`, `skill_view`)은 도구 중심의 점진 공개 아키텍처를 취했으나, 06번 및 07번 스모크 관찰 결과 실제 모델(`deepseek-v4-flash`)은 프롬프트에 스킬 목록이 아예 없자 스킬 키워드가 포함되지 않은 질문("우리 팀의 릴리스 절차")에서 `skills_list`를 스스로 떠올리지 못하고 세션 검색이나 기억 도구를 헤매는 한계를 보였습니다.

본 08번 로드맵은 이러한 한계를 극복하기 위해 **세션 시작 시점에 1회 스킬 이름과 한 줄 요약 목록(`## Available Skills`)을 시스템 프롬프트 헤드에 주입**하여 모델이 첫 턴부터 스킬의 존재를 인지할 수 있도록 하였습니다. 동시에 프롬프트 캐시 보호(세션 중 불변 고정), 3중 상한(50개·120자·4,000자) 및 마크다운 구획 위조 방어(제어문자 치환, `<`·`>` 제거), 서브에이전트(자식) 격벽 유지(미주입)를 시스템 수준에서 철저히 보장하도록 설계·구현되었습니다.

## 2. 목표 대비 달성도 (가정 A~I 대조)

[WHY.md](WHY.md)에서 수립한 9개 가정(A~I)을 실제 코드 구현, E2E 테스트, 실제 모델 스모크 5회 관찰 결과와 1:1로 엄격히 대조 검증했습니다.

| 가정 | 내용 | 판정 | 대조 결과 및 근거 |
|---|---|---|---|
| **가정 A** | 인덱스를 보여주면 deepseek가 스킬 도구를 부를 것이다 | **맞았다** | **A1 실행**: 질문 입력 후 단 1회 호출 만에 `skills_list`를 거치지 않고 곧바로 `skill_view(name="release-procedure")`를 호출하여 2턴 만에 `rel-PELICAN`, `PELICAN-7`을 완벽 응답함. **A0(끈 경우)**는 5회 호출 동안 세션 검색·기억을 방황하다 뒤늦게 스킬을 불렀음. |
| **가정 B** | 세션 시작 시점 1회 고정으로 프롬프트 캐시 바이트가 보존된다 | **맞았다** | 단위 시험(`test_agent_skills_index.py`), E2E 시험 3, 실제 스모크(A1·A0·G1·D1·D2) 전수에서 턴 간 및 호출 간 첫 system 메시지 100% 바이트 동일성 검증 완료. 1턴 후 스킬이 추가되어도 프롬프트 인덱스는 불변. |
| **가정 C** | 시스템 전체가 기본으로 켜지되 자식만 끌 수 있다 | **바뀌었다** | 기존 시험 호환성 및 라이브러리 최소주의를 위해 **라이브러리 기본은 꺼짐(`skills_index=False`), CLI 앱 기본은 켜짐(`--no-skills-index`로 끔)**으로 020에서 합리적 조정(ADR-0008 §2-5 개정). 의도대로 완벽 동작. |
| **가정 D** | 스킬이 200개여도 상한에서 잘리고 첫 조립 지연이 없다 | **맞았다** | 200개 스킬 벤치마크 결과, 50개 항목(+150 more)으로 정확히 절삭, 블록 길이 1,778자(≤4,000자 준수), 첫 조립 소요 시간 **30~32ms**로 체감 지연 0 확인. |
| **가정 E** | 스킬 설명으로 구획이나 제목을 위조할 수 없다 | **맞았다** | 설명에 개행, `</available_skills>`, `## System`, 제로폭 공백(`\u200b`)을 주입해도 정제 로직에 의해 공백 치환 및 `<` `>` 제거되어 줄 맨 앞 `## `는 `["## Available Skills"]` 1개뿐임을 E2E 시나리오 5로 검증. |
| **가정 F** | 서브에이전트 자식에게는 인덱스가 주입되지 않는다 | **바뀌었다** | 라이브러리 기본이 `skills_index=False`이므로 `delegate_tool.py` 수정 없이도 자식은 자연스럽게 인덱스 미주입 격리가 유지됨(E2E 시나리오 7 검증). |
| **가정 G** | Gemini Flash는 인덱스를 켠 뒤에도 정상 동작한다 | **맞았다** | **G1 실행**: 회귀 없이 첫 호출에서 곧바로 `skill_view`를 호출하여 2회 호출 만에 완벽 응답(009의 3회 호출 대비 단축). 약한 규칙 문장("Before answering...")이 모델의 행동을 방해하지 않음. |
| **가정 H** | 대본형 가짜 통신으로 종단간 검증할 수 있다 | **맞았다** | `SequentialMockTransport` 기반 E2E 시나리오 1~8 신설 및 567건 회귀 테스트 100% 통과. `src/` 수정 0줄로 검증 완료. |
| **가정 I** | 40개 파일 자료로 위임 동작을 관찰할 수 있다 | **맞았다** | **D1(deepseek)·D2(Gemini) 실행**: 40개 대용량 파일 조건에서도 두 모델 모두 위임(`delegate_task`)을 부르지 않고 자신이 가진 `terminal` 도구(`ls` + `grep -H ^CODE: ...`)로 40개 코드를 한 번에 정확히 추출하여 해결함. 위임 코드를 임의 수정하지 않고 관찰 사실로 기록. |

## 4. 새로 발견한 사실 및 인사이트

1. **A1 vs A0의 극적인 대조: 방황 제거 및 토큰 64% 절감**
   - **인덱스 켠 deepseek (A1)**: 질문 즉시 인덱스를 인지하고 1번째 호출에서 바로 `skill_view`를 호출하여 **총 2회 호출, 3,705 입력 토큰**으로 해결.
   - **인덱스 끈 deepseek (A0)**: 스킬이 있는지 알지 못해 과거 대화 검색(`session_search`)과 기억(`memory`)을 헤매다 3번째 호출에서야 `skills_list`를 부르고 4번째 호출에서 `skill_view`를 호출하여 **총 5회 호출, 10,217 입력 토큰**을 소모.
   - 인덱스 1줄 목록이 모델의 불필요한 방황을 원천 차단하고 **입력 토큰을 약 2.76배(64% 절감)** 아끼는 효과를 실증했습니다.
2. **모델의 강력한 자가 해결 성향과 위임 미호출 (D1·D2)**
   - 파일이 40개로 늘어났음에도 deepseek과 Gemini 모두 자식을 부르지 않고, `terminal` 도구의 `ls`로 목록을 파악한 뒤 40개 파일 경로를 단 한 줄의 `grep -H ^CODE: data/f01.txt ...` 명령으로 엮어 한 번에 해결했습니다.
   - 모델은 자신이 직접 해결할 수 있는 강력한 도구(`terminal`)가 있을 때는 서브에이전트 위임으로 책임을 넘기지 않는다는 사실을 재확인했습니다.
3. **약한 규칙 문장의 안전성**
   - 강제 어조("MUST") 없이 제안형("Before answering, scan...")으로 작성된 258자 규칙 문장은 Gemini Flash의 기존 추론 능력을 저하시키지 않고(회귀 0), deepseek의 스킬 도구 직접 호출을 효과적으로 유도했습니다.

## 7. 보안 및 Zero Leakage 검증

1. **실제 키 미저장 검증 (사용자 터미널 대조)**:
   - 5개 실행 전체(`run_A1`, `run_A0`, `run_G1`, `run_D1`, `run_D2`)의 `state.db`를 사용자가 별도 터미널에서 바이너리/스트링 레벨로 검사한 결과 모두 `Key Not Found (False)` 확인.
2. **지시문 마크다운 구획 방어**:
   - 스킬 설명에 악의적으로 삽입된 `</available_skills>`, `## System`, 제로폭 공백(`\u200b`)이 정제되어 마크다운 헤딩이 오직 1개(`## Available Skills`)만 유지됨을 E2E 검증.
3. **읽기 전용 무결성 보존**:
   - 스킬 파일 해시(`7922880450e6...`), 40개 데이터 파일 수 및 해시 불변 확인.

## 8. 후속 제안

1. **서브에이전트 위임 트리거 지침 강화 연구**:
   - 모델이 `terminal` 도구를 직접 호출할 수 있는 상태에서는 다량의 파일 작업도 위임하지 않고 직접 셸 명령으로 해결함이 07번(5개 파일)과 08번(40개 파일) 스모크에서 일관되게 관찰되었습니다. 위임이 반드시 필요한 상황(예: 터미널 도구가 없는 순수 조사 작업, 대규모 독립 분기)에 대한 시스템 프롬프트 지침 개선 검토.
2. **스킬 설명 내 프롬프트 주입(Prompt Injection) 방어선 연구**:
   - 구조적 구획 위조는 정제로 방어했으나, 설명문 내부의 정교한 자연어 탈옥 지시는 여전히 방어선 밖에 있습니다. 스킬 로딩 시 신뢰도 검증 메커니즘 검토.
3. **CLI `input()`의 유니코드 디코드 예외 방어**:
   - 대화형 CLI의 터미널 입력 디코드 예외(`try-except UnicodeDecodeError`) 방어선 추가.
