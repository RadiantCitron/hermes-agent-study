## 1. 구현 내용 명세

파일 도구가 바꾸기 **전에** 바뀌기 전 상태를 남기고, 도구가 끝나거나 되돌린 뒤 같은 행의 상태를 갱신하는 저장소를 만든다. 이 단계에서는 **도구·디스패처·에이전트·CLI를 전혀 바꾸지 않는다.** 파일을 읽거나 쓰지 않는 순수 저장 기능이다(020 이후가 이것을 쓴다).

1. **새 표** `file_checkpoints` ([`session_db.py`](../../../../src/hermes_core/session_db.py) `SCHEMA_SQL`에 `CREATE TABLE IF NOT EXISTS`, `approval_requests`와 같은 방식):

   | 열 | 타입 | 뜻 |
   |---|---|---|
   | `id` | INTEGER PRIMARY KEY AUTOINCREMENT | 기록 번호. 같은 턴 안의 복원 순서(역순)의 기준 |
   | `session_id` | TEXT NOT NULL REFERENCES sessions(id) | 어느 세션의 변경인가 |
   | `turn_index` | INTEGER NOT NULL | 세션 안의 턴 번호(1부터). 번호를 세는 쪽은 020의 체크포인트 모듈 |
   | `tool_name` | TEXT NOT NULL | `write_file` 또는 `patch` |
   | `workspace` | TEXT NOT NULL | 기록할 때의 작업 폴더 절대 경로. 되돌릴 때 같은 작업 폴더인지 대조하는 데 쓴다(020) |
   | `rel_path` | TEXT NOT NULL | 작업 폴더 기준 상대 경로(POSIX 표기) |
   | `before_exists` | INTEGER NOT NULL | 바뀌기 전에 파일이 있었으면 1, 없었으면 0 |
   | `before_content` | TEXT | 바뀌기 전 텍스트. `before_exists = 0`이면 `NULL` |
   | `after_sha256` | TEXT | 도구 성공 뒤 파일 내용의 SHA-256(소문자 16진수 64자). `applied`가 될 때만 채운다 |
   | `status` | TEXT NOT NULL | 아래 닫힌 목록 중 하나. 처음은 `pending` |
   | `created_at` | REAL NOT NULL | 선기록 시각(`time.time()`) |
   | `updated_at` | REAL | 마지막 상태 갱신 시각. `pending`일 때는 `NULL` |
   | `reason` | TEXT | 상태 갱신 사유 한 줄(선택) |

   인덱스 `idx_file_checkpoints_session_turn` (`session_id`, `turn_index`). `tool_call_id` 열은 **두지 않는다**: 디스패처는 도구 핸들러에 호출 ID를 넘기지 않는다(`ToolDispatcher.handle_function_call`, 10번 010과 같은 사정). `workspace`는 사용자 홈 경로를 담지만 `state.db`(레포 밖 `~/.hermes`)에만 저장된다.

2. **상수** ([`constants.py`](../../../../src/hermes_core/constants.py), 「체크포인트·롤백 (11 로드맵)」 절 신설):
   - 상태값 5개: `CHECKPOINT_STATUS_PENDING = "pending"`, `CHECKPOINT_STATUS_APPLIED = "applied"`, `CHECKPOINT_STATUS_FAILED = "failed"`, `CHECKPOINT_STATUS_ROLLED_BACK = "rolled_back"`, `CHECKPOINT_STATUS_SKIPPED = "skipped"`.
   - 허용 전이 `CHECKPOINT_TRANSITIONS`: 새 상태 → 허용되는 이전 상태의 튜플. 정확히 아래 다섯 개다.

     | 새 상태 | 허용되는 이전 상태 | 뜻 |
     |---|---|---|
     | `applied` | `pending` | 도구 성공 |
     | `failed` | `pending` | 도구 실패 |
     | `rolled_back` | `applied` | 되돌림 |
     | `skipped` | `applied`, `pending` | 되돌리지 않고 넘어감(충돌·경로 판정 실패, 또는 결과를 모르는 `pending`) |

     `pending → skipped`를 허용하는 이유: 기록 뒤 프로세스가 끝나 `pending`으로 남은 행은 쓰기가 일어났는지 알 수 없다(바뀐 뒤 해시가 없어 충돌을 판정할 수 없다). 그런 행은 되돌리지 않고 「건너뜀」으로 남길 수 있어야 한다. 실제로 언제 그렇게 할지는 020에서 정한다. `pending → rolled_back`은 허용하지 않는다.
   - 대상 도구 `CHECKPOINT_TOOL_NAMES = ("write_file", "patch")`.

3. **`SessionDB` 메서드** (`record_approval_request`/`resolve_approval_request`/`get_approval_requests`와 같은 모양, 쓰기마다 즉시 `commit`):
   - `record_file_checkpoint(session_id, turn_index, tool_name, workspace, rel_path, before_exists, before_content) -> int`
     - 검증(하나라도 어기면 `ValueError`, 행을 만들지 않음):
       - `turn_index`는 1 이상의 `int`(`bool` 제외).
       - `tool_name`은 `CHECKPOINT_TOOL_NAMES` 안의 값.
       - `workspace`·`rel_path`는 빈 문자열이 아닌 `str`.
       - `before_exists`는 `bool`.
       - `before_exists`가 `True`면 `before_content`는 `str`이고 UTF-8 인코딩 길이가 `FILE_MAX_BYTES` 이하. `False`면 `before_content`는 `None`.
     - `status='pending'`, `after_sha256`·`updated_at`·`reason`은 `NULL`로 INSERT하고 즉시 커밋한 뒤 새 `id`를 반환한다. 없는 `session_id`는 외래키 위반(`sqlite3.IntegrityError`)이 그대로 올라온다.
   - `update_file_checkpoint(checkpoint_id, status, *, after_sha256=None, reason=None) -> bool`
     - `status`가 `CHECKPOINT_TRANSITIONS`의 키가 아니면(`pending` 포함) `ValueError`.
     - `status == "applied"`면 `after_sha256`은 소문자 16진수 64자 `str`이어야 하고, 아니면 `ValueError`. 그 밖의 상태에 `after_sha256`을 주면(`None`이 아니면) `ValueError`.
     - 허용되는 이전 상태인 행만 갱신한다(`UPDATE … WHERE id = ? AND status IN (…)`). `status`, `updated_at`, `reason`, 그리고 `applied`일 때 `after_sha256`을 쓴다. 갱신하면 `True`, 이전 상태가 맞지 않거나 없는 `id`면 아무것도 바꾸지 않고 `False`.
   - `get_file_checkpoints(session_id, turn_index=None) -> list[dict]`: 그 세션의 행을 `id` 오름차순으로 `dict` 리스트로 반환한다. `turn_index`를 주면 그 턴의 행만. `before_exists`는 DB 값(0/1) 그대로 둔다.

4. **스키마 버전 6**: `SCHEMA_VERSION = 6`. `_init_schema`에 `if current_version < 6: UPDATE schema_version SET version = 6`을 더한다. 새 표만 늘어서 `ALTER`는 없고, 표는 `executescript(SCHEMA_SQL)`의 `IF NOT EXISTS`가 만든다. 기존 표·열·메서드는 바꾸지 않는다.

5. **기존 시험 수정 (예고된 예외)**: [`test_approval_ledger.py`](../../../../tests/test_hermes_core/test_approval_ledger.py)의 19·104·176행 `assert db.schema_version == 5`는 버전을 6으로 올리면 틀어진다. 세 줄을 **`assert db.schema_version >= 5`로 교체**한다(10번 010의 `== 4 → >= 4` 선례와 같다). 같은 파일의 docstring(16·38·129행)은 바꾸지 않는다. 이 세 줄 외에 기존 시험 파일은 어떤 줄도 바꾸지 않는다. 구현 중 다른 시험이 깨지면 임의로 고치지 말고 멈춰서 보고한다.

6. **알려진 한계**: 행은 지우지 않고 쌓인다(정리 없음, ADR-0011 §4). 세션당 상한은 020에서 정하며, 이 저장소는 행 수를 제한하지 않는다. `rel_path`가 실제로 작업 폴더 안의 안전한 경로인지는 저장소가 판정하지 않는다. 기록 전 판정과 복원 전 재판정은 020이 `check_write_path`로 한다.

7. **작동원리·ROADMAP 갱신**: 작동원리는 없음(050에서 일괄 반영). ROADMAP §2-7 상태도와 §6-1의 열 목록은 이 지시서와 같은 커밋에서 맞춘다(`pending → skipped` 전이, `workspace` 열 추가).

## 3. 인수 테스트 시나리오 (구현 전 작성, 임의 변경 금지)

## 5. 위험·주의

- **「선기록」은 커밋까지 포함이다**: 커밋하지 않은 행은 다른 연결에서 보이지 않고, 쓰기 직전에 프로세스가 끝나면 사라진다. 시나리오 6이 이를 잡는다.
- **전이 표는 이후 단계의 계약이다**: 020·030·040이 이 다섯 상태와 전이를 쓴다. 바꾸려면 이 지시서를 고치지 않고(불변) 새 지시서에서 상수를 확장한다.
- **원장은 파일을 모른다**: 이 단계는 해시를 계산하지도 파일을 읽지도 않는다. 해시 형식 검사(소문자 16진수 64자)는 잘못된 값이 원장에 들어와 이후 충돌 판정을 망치는 것을 막는 바닥일 뿐이다.
- **크기 상한을 저장소에서도 검사하는 이유**: 파일 도구는 이미 1MB를 넘는 파일을 고치지 않는다. 그래도 저장소가 받는 값의 상한을 스스로 지켜, 감싸는 쪽(030)의 실수가 DB 비대화로 번지지 않게 한다(다층 방어). 경계값은 시나리오 15가 잡는다.
- **마이그레이션 시험이 옛 DB 모양에 의존**: 시나리오 2·3의 옛 DB 스크립트는 현재 `SCHEMA_SQL`을 복사해 만들지 않는다. 시험이 구현의 거울이 되지 않게 하기 위해서다.
- **시험이 구현의 거울이 되지 않게**: 시나리오 9·10·11의 기대(허용 전이, 해시 형식)는 위 명세에서 나왔다. 구현 중 결과가 다르면 시나리오를 바꾸지 말고 멈춰서 보고한다.
- **`>= 5` 교체의 의미**: 이 단언들은 「v3·v4 DB가 최소 v5까지 마이그레이션되어 `approval_requests`가 생긴다」를 확인하던 시험이다. 최신 버전과 같다는 단언은 이 단계의 시나리오 1·2·3이 맡는다.
