## 1. 구현 내용 명세

020이 만든 `Checkpointer`를 **디스패처의 `write_file`·`patch`에 연결**한다. 이 단계가 끝나면 `checkpointer`를 넘겨 만든 디스패처는 두 도구를 부르기 전에 바뀌기 전 모습을 원장에 먼저 적고, 적지 못하면 도구를 부르지 않으며, 부른 뒤에는 파일의 실제 상태로 결과를 확정한다. `checkpointer`를 넘기지 않은 모든 구성(`create_default_dispatcher()` 기본값, `create_child_dispatcher()`, 지금까지의 모든 호출처)은 **이전과 한 글자도 다르지 않게** 동작한다. **`file_tools.py`·`checkpoint.py`·`HermesAgent`·CLI는 바꾸지 않는다**(CLI 연결과 턴 경계 알림은 040). 이 단계의 시험은 실제 터미널·실제 모델 없이 돈다.

### 1-3. `create_default_dispatcher`와 `_checkpointed_handler` ([`dispatcher.py`](../../../../src/hermes_core/tools/dispatcher.py))

`create_default_dispatcher`에는 `checkpointer: Optional[Checkpointer] = None`만 더하고 `write_file`·`patch` 등록 두 곳만 바꾼다(`checkpointer`가 있으면 감싼 핸들러, 없으면 지금과 같은 등록). `Checkpointer`는 `hermes_core.tools.checkpoint`에서 가져온다(순환 없음: `checkpoint.py`는 `constants`·`session_db`·`path_guard`만 쓴다). `include`에 두 도구가 없으면 `checkpointer`는 쓰이지 않는다(오류 아님). 스키마(`WRITE_FILE_SCHEMA`·`PATCH_SCHEMA`)는 그대로 등록하므로 모델이 보는 도구 정의는 불변이다.

`_checkpointed_handler(tool_name, tool, checkpointer)`가 돌려주는 핸들러의 **판정 순서가 계약이다**:

1. **인자 모양**: `path`가 `str`이 아니면(디스패처를 거치지 않은 직접 호출) 아무것도 하지 않고 `tool(**kwargs)`를 그대로 부른다. 그 경우의 오류는 기존과 같다.
2. **작업 폴더 일치 확인**: `resolve_workspace(None) != resolve_workspace(checkpointer.workspace)`이면 도구를 **부르지 않고** `CHECKPOINT_WORKSPACE_MISMATCH_MESSAGE + CHECKPOINT_REFUSED_HINT` 실패를 돌려준다. 기록은 하지 않는다.
3. **선기록**: `cid = checkpointer.record_before(tool_name, path)`.
   - `CheckpointLimitError`가 나면 `str(예외) + CHECKPOINT_REFUSED_HINT`를 오류로 하는 실패를 돌려주고 도구를 부르지 않는다(R5).
   - 그 밖의 `Exception`(DB 오류, `ValueError("Turn has not begun")` 포함)은 `CHECKPOINT_PRE_RECORD_FAILED_MESSAGE.format(reason=str(예외)) + CHECKPOINT_REFUSED_HINT` 실패를 돌려주고 도구를 부르지 않는다(**fail-closed**, 가정 B).
   - `cid is None`이면 1-1의 「`None`」 규칙대로 기록 없이 도구를 부른다(4번으로).
4. **도구 실행**: `tool(**kwargs)`를 받은 인자 그대로 부른다.
5. **확정**: `cid`가 있으면 도구가 정상 반환하든 예외를 던지든(`BaseException` 포함) `try/finally`로 `checkpointer.finalize(cid, tool_name, path, result_success=…, exception=…)`를 부른다. `result_success`는 결과 문자열이 JSON 객체이고 `success`가 bool일 때만 그 값, 그 밖(깨진 JSON·`success` 없음·bool 아님·예외)은 `None`이다. 확정에서 `Exception`이 나면 삼키고 `logging` 경고(체크포인트 id 포함)만 남긴다.
6. **반환**: 도구 결과 문자열을 **그대로** 돌려준다. 도구가 예외를 던지면 확정을 거친 뒤 **그 예외를 다시 던져** 디스패처의 기존 처리(`Tool '…' failed: …` JSON)에 맡긴다. `cid is None`이었는데 결과가 `success: true`이면 「기록 없는 변경」 경고 로그를 남기고 결과는 그대로 돌려준다.

로그는 `dispatcher.py` 모듈의 `logging.getLogger(__name__)`를 쓴다(`agent.py`·`llm_client.py`와 같은 방식). 이 함수는 모델에게 가는 문구를 바꾸지 않는다(성공·도구 거부는 도구가 만든 JSON 그대로, 실패 3종만 위 문구).

### 1-4. 알려진 한계 (시험하지 않고 문서에 남긴다)

- **도구가 거부한 호출도 세션 상한을 쓴다.** `record_before`는 도구 결과를 알기 전에 바뀌기 전 내용의 바이트를 세션 합계에 더하고 `failed` 행에도 `before_content`가 남는다. 모델이 1MB 가까운 파일에 틀린 `patch`를 반복하면 50MB(약 50회)에서 이후 모든 쓰기가 거부된다. 020의 동작이라 이 단계는 고치지 않고 가정 J의 근거로 마감 때 대조한다. 고친다면 후속에서 `failed` 확정 시 바이트를 돌려주거나 내용을 비우는 방식이다.
- **기록 없이 바뀌는 길이 둘 있다**: ① `record_before`가 `None`을 줬는데 도구가 성공한 경우(경고 로그만), ② 확정 실패로 `pending`이 남은 경우(복원은 못 하지만 경고로 보임). 둘 다 정상 경로에서는 일어나지 않아야 하며 시험은 이를 흉내 낸 가짜로만 본다.
- 감싼 핸들러는 CLI 화면에 알리지 못한다(핸들러는 출력 채널이 없다). 거부 사실을 사람에게 한 번 알리는 일(R5 ③)은 040에서 정한다.
- 위임 자식의 쓰기는 기록하지 않는다(ADR 대안 F). 부모가 위임한 뒤 자식이 바꾼 파일은 되돌려지지 않는다.

### 1-5. 040에 넘기는 사항 (이 단계에서 구현하지 않음)

- CLI는 `Checkpointer`를 만들 때 도구가 쓰는 폴더와 같은 폴더(`Path.cwd()`)를 `workspace`로 넘겨야 한다. 기본값(`get_default_workspace()`)을 쓰면 2번 확인에 걸려 모든 쓰기가 거부된다.
- `run_conversation` 직전에 `begin_turn()`을 부르지 않으면 모든 쓰기가 「Turn has not begun」으로 거부된다.
- ROADMAP §4-1 R1 ①의 「`resolve_workspace(None)` → `check_write_path`」 서술은 `Checkpointer` 기본값과 맞지 않는다. 050에서 ROADMAP 본문을 정정한다.

## 3. 인수 테스트 시나리오 (구현 전 작성, 임의 변경 금지)

시험은 `tests/test_hermes_core/test_file_tools_checkpoint.py`에 둔다. 공통 준비: 작업 폴더 `ws`는 `tmp_path`의 하위 폴더이고 `monkeypatch.chdir(ws)`로 현재 폴더를 옮긴다(도구가 현재 폴더를 쓰므로). 실제 `SessionDB(tmp_path / "state.db")`에 `create_session(sid)`, `cp = Checkpointer(db, sid, ws)`, `cp.begin_turn()`, `d = create_default_dispatcher(session_db=db, checkpointer=cp)`. 「행」은 `db.get_file_checkpoints(sid)`로 읽은 원장 행이다. 비교용 쌍둥이는 같은 순서의 호출을 `checkpointer` 없는 디스패처로 **다른 임시 작업 폴더**에서 돌린 결과다(결과 JSON에는 상대 경로·개수만 들어 있어 폴더가 달라도 같다). 가짜 도구는 `hermes_core.tools.dispatcher.write_file_tool`/`patch_tool`을 디스패처를 만들기 **전에** `monkeypatch.setattr`로 바꿔 끼운다. 기대값은 ADR-0011 §2-3·§2-10, ROADMAP §2-3·§4·§6-3과 위 명세에서 나왔고 구현 결과를 보고 쓰지 않았다. 해시의 기대값은 시험이 `hashlib.sha256(예상 바이트)`로 직접 계산한다.

## 5. 위험·주의

- **이 단계는 에이전트의 실제 쓰기 동작이 바뀌는 유일한 단계다.** 단 `checkpointer`를 넘긴 디스패처에서만이고 이 단계에서는 아무 앱도 넘기지 않는다(040 전까지 사용자 경로는 이전과 같다). 시나리오 1~4가 이 전제를 잡는다.
- **작업 폴더 확인은 이 단계가 발견한 구멍을 막는 장치다**: `Checkpointer` 기본값이 도구의 기본값과 다르다는 점은 020 시험이 모두 `workspace`를 명시해 가려졌다. 시나리오 16이 두 방향(처음부터 다름, 중간에 현재 폴더가 바뀜)을 모두 잡는다. 040이 이 지시서 1-5를 지키지 않으면 CLI의 모든 쓰기가 거부되므로 040 지시서가 먼저 이 항목을 인수 시나리오로 옮겨야 한다.
- **확정 예외를 삼키는 것은 의도적**이다. 삼키지 않으면 파일은 바뀌었는데 모델이 실패를 받는다. 대신 경고 로그와 `pending` 행이 남는다(시나리오 19). `pending`이 사람에게 보이는 자리는 040의 `/rollback` 목록이다.
- **`KeyboardInterrupt` 경로**(시나리오 12)는 `finally`가 확정을 거치는지만 본다. 실제 터미널에서 도구 실행 중 Ctrl+C의 화면 동작은 **미확인**이며 050·060에서 본다.
- **알려진 한계 1-4**(거부 호출의 상한 소모, 기록 없는 변경 2경로, 화면 알림 없음, 자식 쓰기 미기록)는 이 단계가 해결하지 않는다. 마감 보고에서 가정 B·F·J와 함께 그대로 대조한다.
- **실제 모델·터미널 동작은 미확인**: 이 단계의 시험은 모의 모델과 가짜 도구만 쓴다. 가정 G는 050(pty)·060(사람)에서 본다.
