# [WHY] 11-체크포인트-롤백-MVP — 왜 이 로드맵을, 왜 이 정도로만 하는가

> **성격**: 이 로드맵의 의도를 적은 문서다 (ROADMAP_정책 §3-2). 마감 때 종합보고서(`결과정리및리뷰.md`, 마감 시 작성)가 이 문서의 「검증할 가정」을 하나씩 대조한다. 4단계 착수 후에는 본문을 고치지 않고 맨 끝 「변경 기록」에만 덧붙인다.  
> **작성일**: 2026-10-29 · **함께 보는 문서**: [PLAN.md](PLAN.md)(무엇을 하기로 승인했나), [ROADMAP.md](ROADMAP.md)(설계), [ADR-0011](../../adr/0011-체크포인트_롤백_MVP_범위와_결정.md)(결정 근거)

## 1. 왜 지금 이 로드맵인가

이 에이전트는 작업 폴더 안에서 새 파일을 만들고, 있는 파일의 글자를 바꿀 수 있다. 10번 로드맵은 위험한 터미널 명령을 사람이 미리 보고 허락하게 했지만, 파일을 만들고 고치는 일에는 묻지 않기로 미뤘다. 그때 내건 이유가 「파일 변경의 위험은 되돌리는 수단과 함께 판단한다」였다. 이 로드맵이 그 되돌리는 수단이다.

사람이 이 시스템을 쓸 때 묻는 질문은 이렇다.

- *"에이전트가 내 파일을 엉뚱하게 고쳐 놓으면 어떻게 원래대로 돌리는가?"*
- *"되돌리다가 내가 그사이 직접 고친 내용까지 날아가지 않는가?"*
- *"에이전트가 무엇을 바꿨고 무엇을 되돌렸는지 나중에 확인할 수 있는가?"*

지금은 첫 질문에 「직접 열어서 기억을 더듬어 고친다」, 둘째에 「해당 없음」, 셋째에 「대화 기록을 뒤져 짐작한다」가 답이다. 이 로드맵은 **「에이전트가 바꾸기 전 모습을 먼저 적어 두고, 사람이 한 번의 명령으로 직전 요청 전 모습으로 돌린다」** 하나를 만든다.

---

## 2. 왜 이 정도로만 하는가

이 로드맵이 **일부러 하지 않는 것**과 그 이유다.

| 하지 않는 것 | 이유 | 언제 하는가 |
|---|---|---|
| 터미널 명령이 바꾼 파일 되돌리기 | 명령이 어떤 파일을 바꿀지는 실행해 봐야 안다. 그러려면 작업 폴더 전체를 매번 통째로 떠 둬야 하고, 원본은 이 일에 별도 저장소와 정리 장치를 둔다. 허용목록 밖 명령은 10번에서 사람이 이미 보고 허락한다 | 터미널로 파일을 바꾸는 일이 잦아졌다는 증거가 쌓일 때 |
| 원본처럼 숨은 git 저장소에 폴더 전체 저장 | 위와 같은 이유. 우리 파일 도구는 한 번에 파일 하나만 바꾸고, 바뀌기 전 모습은 「없었음」 아니면 1MB 이하 글뿐이다 | 위와 같음 |
| 보조 에이전트(위임 자식)가 바꾼 파일 되돌리기 | 자식은 별도 대화로 기록되어 「부모의 어느 요청에 딸린 변경인가」를 묶는 규칙이 새로 필요하다. 위임은 켤 때만 동작한다 | 위임으로 파일을 고치는 일이 실제로 쓰일 때 |
| 되돌렸다는 사실을 모델에게 알리기 | 대화 기록에 끼워 넣는 규칙(언제, 어떤 역할로)을 새로 정해야 한다. 모델이 옛 내용을 믿고 고치려 하면 「찾는 글이 없다」로 실패하므로 피해가 크지 않을 것으로 본다(가정 H) | 실제 사용에서 모델이 헤매는 것이 관찰될 때 |
| 변경 목록·차이 보기·특정 요청 골라 되돌리기 | 최근 것부터 차례로 되돌리기만 해도 「직전 실수 되돌리기」는 된다. 중간 것만 되돌리면 순서가 꼬인다 | 필요가 생기면 |
| 오래된 기록 정리(지우기), 대화를 넘는 용량 관리 | 한 대화에서 쌓이는 양은 작다. 정리 규칙은 오래 쓴 뒤에 근거를 갖고 정한다. 다만 한 대화 안의 저장량에는 상한을 두고, 넘으면 쓰기를 거부한다(끝없이 쌓이는 것을 막는 안전장치이며 정리가 아니다. [ROADMAP](ROADMAP.md) §4-1 R5) | 기록이 실제로 커졌을 때 |
| 이전 대화의 변경 되돌리기 | 프로그램을 다시 켜면 이전 대화의 파일이 이미 다른 경로로 바뀌었을 수 있다. 한 대화 안으로 묶어 둔다 | 필요가 생기면 |
| 파일 도구에도 승인 묻기 | 되돌릴 수 있으면 매번 묻지 않아도 된다는 것이 이 로드맵의 전제다. 둘 다 하면 효과를 가리기 어렵다 | 되돌리기로 부족하다는 증거가 나올 때 |

한마디로, **「파일 도구가 바꾼 것은 바꾸기 전에 적어 두고, 사람이 직전 요청부터 하나씩 되돌린다. 그사이 사람이 고친 파일은 건드리지 않는다」까지만** 한다.

## 3. 왜 이 순서, 왜 이 단계 수인가

단계는 여섯 개(010~060)이고, 10번과 같은 줄기다. **기록 자리를 먼저, 판단 부품은 그다음, 도구에 붙이는 일은 그 뒤, 앱에 붙이는 일은 그 뒤, 실제 사람이 쓰는 확인은 맨 마지막**에 둔다.

| 순서 | 하는 일 | 왜 이 자리인가 |
|---|---|---|
| 1 (010) | 바뀌기 전 모습을 남길 기록 표와 기록·조회 방법 | 「먼저 적고 바꾼다」가 이 설계의 핵심이다. 파일을 전혀 건드리지 않는 저장소 작업이라 가장 먼저, 가장 안전하게 만든다 |
| 2 (020) | 바뀌기 전 모습을 읽어 적기, 다 바꾼 뒤 확정하기, 되돌릴 계획 세우기, 충돌 건너뛰기를 하는 부품 | 도구와 화면 어디에도 붙지 않아 임시 폴더만으로 시험할 수 있다. 되돌리기 규칙을 한 곳에 모은다 |
| 3 (030) | 파일 도구에 이 부품 연결, 적지 못하면 쓰지 않기 | 에이전트의 실제 쓰기 동작이 바뀌는 유일한 단계라 부품이 검증된 뒤 따로 둔다 |
| 4 (040) | 앱에서 켜기·끄기, 요청 경계 알리기, 되돌리기 명령 | 사람에게 보이는 동작이 바뀌는 지점을 한 단계로 둔다 |
| 5 (050) | 가짜 모델·가상 터미널로 끝에서 끝까지 확인, 작동원리 문서 맞추기 | 사람 없이 할 수 있는 확인을 먼저 끝낸다 |
| 6 (060) | 실제 모델이 실제로 파일을 만들고 고친 뒤 사람이 되돌려 본다 | 되돌린 뒤 모델의 반응과 화면이 이해 가능한지는 실제 모델과 사람이 있어야 본다. 실제 키가 필요한 유일한 단계다 |

## 4. 왜 이 방식을 택하고 무엇을 배척했나

| 선택 | 배척한 대안 | 이유 |
|---|---|---|
| 바뀌기 전 모습을 대화 기록과 같은 저장소(상태 DB)에 둔다 | 숨은 git 저장소에 폴더 전체를 둔다(원본) | 바꾸는 파일이 하나뿐이라 폴더 전체가 필요 없다. 별도 프로그램(git)을 부르지 않고, 대화·승인 기록과 한곳에서 볼 수 있다 |
| 적지 못하면 쓰지 않는다 | 적지 못해도 쓴다(원본) | 「되돌릴 수 있다」고 믿었는데 기록이 없는 변경이 생기지 않는다. 이 코어는 기록이 먼저라는 원칙을 지켜 왔다 |
| 요청(턴) 단위로, 최근 것부터 차례로 되돌린다 | 변경 한 건씩 골라 되돌린다 | 같은 파일을 여러 번 고친 경우 순서가 꼬이지 않는다. 사람은 「아까 그 요청 전으로」라고 생각한다 |
| 그사이 다른 손이 고친 파일은 건너뛰고 알린다 | 덮어쓴다 / 하나라도 어긋나면 전부 멈춘다 | 덮으면 사람의 작업을 잃는다. 전부 멈추면 무관한 파일까지 못 돌린다 |
| 라이브러리는 기본 꺼짐, 앱은 기본 켜짐 | 항상 켜짐 / 옵션으로만 켜짐 | 기존 시험과 사용은 그대로이고, 사람이 쓰는 앱에서는 따로 켜지 않아도 된다. 저장량이 작아 기본으로 켜도 부담이 작다 |
| 부품은 도구를 만드는 자리에서 넣고 파일 도구 자체는 손대지 않는다 | 파일 도구 안에 기록 코드를 넣는다 / 만든 뒤 바꿔 끼운다 | 파일 도구의 기존 검사·쓰기 순서가 그대로 남고, 자식에게는 넣지 않는다는 사실이 만드는 자리에서 보인다(10번 결정과 같은 방식) |
| 되돌리기는 사람이 치는 명령이다 | 모델이 부르는 도구로 둔다 | 에이전트의 실수를 사람이 바로잡는 수단이다. 그 판단을 다시 모델에게 맡기지 않는다 |
| 되돌리기 전 목록을 보이고 예/아니오를 받는다 | 바로 되돌린다 | 되돌리기도 파일을 바꾸는 일이다. 무엇이 바뀔지 사람이 보고 결정한다 |

## 5. 성공 판단 기준과 검증할 가정

**성공 기준**: 가짜 모델로 모든 시험이 통과한다. 체크포인트 기능이 없는 구성(라이브러리 기본, 위임 자식)은 이전과 같이 동작한다. 파일 도구의 모든 성공한 변경은 바꾸기 전에 기록되고, 기록하지 못하면 쓰지 않는다. `/rollback`은 최근 턴부터 차례로 파일을 정확히 바꾸기 전 모습으로 돌리고, 그사이 다른 손이 고친 파일은 건드리지 않고 알린다. 사용자가 실제 터미널에서 실제 모델로 되돌리기를 해 본다. 기존 시험은 바뀌지 않는다(스키마 버전 단언은 010 지시서에 예고된 예외).

마감 때 종합보고서가 아래 가정을 하나씩 「맞았다 / 틀렸다 / 바뀌었다」로 대조한다.

| 번호 | 가정 | 틀렸다면 |
|---|---|---|
| **A** | 체크포인트 기능이 없는 구성(라이브러리 기본, 위임 자식, `--no-checkpoints`)에서는 파일 도구가 지금과 똑같이 동작하고, 기존 시험이 바뀌지 않고 통과한다. | 연결 방식을 고친다. 기존 사용에 영향이 있다는 뜻이다. |
| **B** | 파일 도구가 성공한 모든 변경은 바뀌기 **전에** 기록되고, 기록하지 못하면 파일이 바뀌지 않으며 모델에게 실패가 돌아간다. | 기록 순서를 고친다. 이 로드맵의 핵심이 틀렸다는 뜻이다. |
| **C** | `/rollback` 한 번이 가장 최근 턴의 변경만 되돌린다. 만든 파일은 사라지고 고친 파일은 바이트 단위로 원래 내용이 된다. 다시 치면 그 앞 턴이 되돌려진다. | 묶음 규칙이나 복원 방법을 고친다. |
| **D** | 에이전트가 쓴 뒤 사람이나 터미널 명령이 다시 고친 파일은 되돌리지 않고 「건너뜀」으로 보고하며, 같은 턴의 나머지 파일은 되돌린다. | 충돌 판정을 고친다. |
| **E** | 되돌리기도 작업 폴더 밖, 보호 파일, 쓰기 금지 파일을 건드리지 않는다(경로 판정 재검사). | 복원 경로의 검사 위치를 고친다. |
| **F** | 기록과 쓰기 사이에 실패나 중단이 있어도(도구 실패, 기록 뒤 프로세스 종료) 원장과 실제 파일 상태가 되돌리기를 틀리게 만들지 않는다. (**미확인**: 처리 규칙은 020에서 정한다.) | 남은 행의 처리 규칙을 고친다. |
| **G** | 실제 터미널에서 `/rollback`의 목록·확인 질문이 정상으로 뜨고 y/n이 전달되며, 그 뒤 REPL이 이어진다. (**미확인**) | 입력 경로를 고친다. |
| **H** | 되돌린 뒤 실제 모델이 옛 내용을 전제로 고치려 하면 「찾는 글이 없다」 실패를 받고, 파일을 다시 읽어 바로잡는다(또는 사람에게 알린다). (**미확인**: 모델 1~2종·소수 관찰의 한계.) | 기록하고 「모델에게 되돌림 알리기」를 후속 후보로 올린다. 구조는 되돌리지 않는다. |
| **I** | 새 부품이 파일 도구 외의 부분(에이전트 루프, 터미널과 승인, 압축, 위임, 입력)에 영향을 주지 않는다. | 결합을 고친다. |
| **J** | 한 대화에서 쌓이는 기록의 양이 실사용에서 문제가 되지 않는다(파일당 1MB 상한). (**미확인**: 세션당 상한을 둘지는 020에서 정한다.) | 상한이나 정리 규칙을 후속으로 올린다. |

## 6. 알려진 위험과 아직 확인하지 못한 것

- **터미널 명령과 위임 자식이 바꾼 파일은 되돌리지 못한다.** 사람이 이 사실을 모르고 `/rollback`을 믿으면 일부만 돌아간 상태를 보게 된다. 그래서 되돌리기 화면과 문서에 대상이 파일 도구뿐임을 적는다.
- **작업 폴더의 파일 내용이 상태 DB에 복사된다.** 상태 DB는 대화 원장이 있는 `~/.hermes`에 있다. 쓰기 금지·보호 파일(`.env*` 등)은 처음부터 쓰기 도구가 거부하므로 기록 대상이 되지 않는다.
- **되돌린 뒤 모델은 그 사실을 모른다.** 대화 기록에는 바뀐 내용이 그대로 남는다(가정 H).
- **기록과 쓰기 사이의 중단**(기록 뒤 프로그램 종료 등) 처리는 미확인이다(가정 F).
- **실제 터미널에서의 동작**은 미확인이다(가정 G).
- **원본 `/rollback`의 화면 절차와 모델 알림 여부**는 읽지 않았다(미확인).
