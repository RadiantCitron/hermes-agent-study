# [WHY] 21-원장-파일-도메인-분리-및-실행환경-포트-완결-MVP — 왜 이 정도로만 하는가

> 사람의 말로, 코드 용어 없이 적는다([ROADMAP_정책 §3-2](../ROADMAP_정책.md)). 마감 때 종합보고서가 이 문서의 가정을 하나씩 대조한다.

## 1. 왜 지금 이 로드맵인가

- 18번부터 20번까지 세 차례의 정비를 거치며, 프로그램의 심장부(커널)를 떼어내고, 제어판을 세우고, 모든 도구의 방향을 바로잡아 「울타리 위반 빚 0건」과 「실행 중 취소 시 기억 일치」를 이루었다.
- 그러나 프로그램을 한 걸음 물러나 바라보았을 때, 마지막으로 눈에 밟히는 세 가지 아쉬움이 남아 있다:
  1. **천 줄이 넘는 거대한 장부 파일 하나**: 대화와 도구 실행 기록을 적는 데이터베이스 장부 파일이 1,000줄을 넘어 프로그램 전체에서 가장 뚱뚱하다. 이 파일 하나 안에 실제 데이터베이스에 접속하고 명령을 던지는 일과, 들어온 값이 올바른지 따지는 온갖 깐깐한 규칙 검사, 대화를 줄였을 때 이름을 짝지어 주는 일, 검색 명령 문장을 조립하는 순수한 계산 작업이 한 덩어리로 뭉쳐 있다.
  2. **파일 도구 안의 텍스트 처리와 실제 디스크 작업 혼재**: 파일을 읽고, 고치고, 찾는 도구 파일(640줄) 안에 실제로 하드디스크의 파일을 읽고 쓰는 일과, 줄 번호를 매기고 글자 수를 세어 자르거나 일치하는 문장을 찾아 바꾸는 순수한 글자 계산 알고리즘이 뒤섞여 있다.
  3. **내 컴퓨터의 터미널에만 묶여 있는 실행 구조**: 명령을 실행하는 도구가 내 컴퓨터의 기본 터미널에만 딱 달라붙어 있어, 나중에 격리된 가상 상자(컨테이너 샌드박스)나 다른 안전한 곳에서 명령을 돌리고 싶어도 그 길목(약속된 통로)이 열려 있지 않다. 승인 질문 역시 콘솔 화면에만 묶여 있어 웹이나 메신저로 승인을 물어볼 수 있는 통로가 없다.
- 이 세 가지를 정리하면, **천 줄 넘는 비대 파일이 단 하나도 없고, 모든 도메인 규칙이 밑바닥 입출력과 깔끔하게 갈라지며, 향후 사내 시스템이나 샌드박스를 붙이더라도 프로그램의 알맹이를 한 줄도 고치지 않아도 되는 완성형 구조**로 대장정을 기분 좋게 매듭지을 수 있다.

## 2. 왜 이 정도로만 하는가 (비목표)

| 하지 않는 것 | 이유 | 언제 하나 |
|---|---|---|
| 프로그램 전체를 비동기(async/await) 방식으로 전면 뜯어고치기 | 파이썬에서 비동기로 바꾸면 모든 함수에 `async`를 붙여야 해서 심장부(커널)와 기존 1,173개 시험 전체를 뒤엎어야 한다. 개인용으로 쓰는 데는 동기 방식이 훨씬 직관적이고 안전하며, 외부 연동이 필요하면 밖에서 일꾼 스레드로 감싸면 충분하다 | 별도의 비동기 서비스 게이트웨이를 바깥에 구축할 때 |
| 실제 Docker나 가상 컨테이너 인프라를 직접 구축하기 | 지금 로드맵의 목적은 「컨테이너나 샌드박스를 꽂을 수 있는 약속(포트)을 프로그램에 뚫어 두는 것」이다. 실제 클라우드/컨테이너 인프라는 개인용 프로그램 범위를 벗어나며 별도 인프라의 몫이다 | 사내 배포용 인프라 프로젝트를 진행할 때 |
| 옛날 부품 이름을 새 위치로 연결해 주는 호환 다리 없애기 | 기존의 수많은 시험들이 안정적으로 통과하는 바닥이므로 건드리지 않는다 | 별도 코드 정리 작업에서 필요할 때만 |
| 고정 숫자·문구 모음 파일 쪼개기 | 기능이나 구조 안전과 무관하게 불필요한 흔들림만 만들므로 배척한다 | 코드 다듬기 작업에서 필요할 때만 |

## 3. 왜 이 순서, 왜 이 단계 수인가

1. **장부 파일에서 순수 도메인 규칙 떼어내기(010)**: 가장 크고 거슬리는 1,000줄짜리 장부 파일부터 시작한다. 데이터베이스 연결선을 바깥으로 꺼내지 않으면서도 온갖 규칙과 계산을 순수 파일로 떼어내어 장부 파일의 몸집을 절반으로 줄인다.
2. **파일 도구에서 순수 글자 알고리즘 떼어내기(020)**: 두 번째로 큰 파일 도구에서 줄 번호 계산, 패치 치환, 라인 매칭 알고리즘을 순수 파일로 분리하여 디스크 입출력과 순수 계산을 나눈다.
3. **실행 환경과 승인 통로 열기(030)**: 터미널 도구와 도구 배선함이 외부 명령 실행기(샌드박스)와 외부 승인기를 받아들일 수 있도록 약속(포트)을 세우고, 기존의 수많은 터미널 시험들이 한 줄도 깨지지 않음을 확인한다.
4. **구조 불변식 최종 총결산 잠금(040)**: 순수 도메인 6종의 인프라 무참조, 전 모듈 800줄 이하 상한, 신규 약속 적합성을 자동 시험으로 영구히 못 박는다.
5. **해설서 최종 동기화(050)**, **마감(060)**: 정리된 구조를 시스템 해설서에 반영하고 가정을 전수 대조해 최종 마감한다.

## 4. 왜 이 방식을 택하고 무엇을 배척했나

- **택한 것**:
  - 장부 모듈을 쪼갤 때 데이터베이스 연결선(`_conn`)은 장부 본체에만 남겨두고, 데이터베이스를 전혀 쓰지 않는 순수한 검사와 계산 함수만 별도 파일(`ledger_domain.py`)로 떼어낸다. (20번의 연결선 격리 시험을 100% 무수정 보존)
  - 파일 도구에서 파일시스템 I/O와 순수 텍스트 처리 알고리즘을 분리하여, 디스크 파일 없이 메모리 안에서 1ms 안에 초고속으로 검증할 수 있게 한다.
  - 터미널 도구에 실행기 약속(`CommandExecutorPort`)을 주입받는 자리를 만들되, 주입하지 않았을 때는 기존 방식을 그대로 쓰게 하여 기존의 모든 시험을 단 한 줄도 건드리지 않는다.
- **배척한 것**:
  - 장부 모듈을 테이블별 클래스로 여러 파일에 쪼개면서 데이터베이스 연결선을 이리저리 넘기는 방식: 20번에서 어렵게 세운 「장부 외부에서 `_conn` 접근 0건」 불변식을 깨뜨리므로 배척했다.
  - 비동기(async) 프레임워크를 억지로 도입하는 방식: 개인용 프로그램에 불필요한 복잡성과 디버깅 난이도만 키운다.

## 5. 성공 판단 기준과 검증할 가정 목록

| 번호 | 가정 |
|:---:|---|
| **A** | 데이터베이스 장부 파일(`session_db.py`)과 파일 도구 파일(`file_tools.py`)에서 순수 검사·규칙 코드가 분리되어, 프로그램의 모든 코드 파일이 800줄 이하가 된다 (1,000줄 비대 모듈 0건) |
| **B** | 장부의 순수 규칙 파일(`ledger_domain.py`)과 파일 글자 처리 규칙 파일(`file_domain.py`)은 실제 데이터베이스나 파일시스템이나 통신 라이브러리를 전혀 부르지 않고 혼자서도 시험할 수 있다 |
| **C** | 데이터베이스 연결선(`_conn`)은 오직 장부 본체 파일 안에서만 접근되며, 장부 외부에서 직접 접근하는 곳이 0건으로 유지된다 |
| **D** | 터미널 명령 도구는 외부에서 별도의 명령 실행기(샌드박스)나 사람 승인기를 건네받아 실행할 수 있으며, 건네받지 않았을 때도 기존과 완전히 똑같이 동작한다 |
| **E** | 터미널 명령과 승인을 시험하는 기존 시험들은 한 줄도 고치지 않고 100% 통과한다 |
| **F** | 순수 도메인 모듈 6종에 대한 인프라 무참조 검증과 단일 파일 800줄 상한이 아키텍처 자동 시험으로 영구 고정된다 |
| **G** | 한가운데(되풀이와 약속, `kernel/`) 파일들은 이 로드맵 동안 단 한 줄도 바뀌지 않는다 |
| **H** | 에이전트와 도구들을 만드는 기존 방법(겉모습)은 바뀌지 않고, 기존 시험 1,173개는 한 줄도 고치지 않고 모든 단계에서 통과한다 |
| **I** | 한 단계 낮은 파이썬 버전(3.12)에서도 새로 만든 도메인 파일과 포트 파일을 포함해 프로그램이 정상으로 켜진다 |

## 6. 알려진 위험과 아직 확인하지 못한 것

- 장부 파일(`session_db.py`)의 SQL 문장들을 상수 문자열로 떼어낼 때, 마이그레이션 순서나 FTS5 트리거 정의가 기존 초기화 시험과 어긋나지 않는지 010 단계에서 확인한다.
- 파일 도구의 텍스트 슬라이싱을 떼어낼 때 줄바꿈(`\r\n` vs `\n`) 정규화가 기존의 윈도우 스타일 파일 읽기 시험과 완전히 일치하는지 020 단계에서 확인한다.
