## 1. 왜 지금 이 로드맵인가

04번으로 차에 연료가 들어갔다. 실제 모델이 도구를 쓰고 돌아오는 한 번의 대화가 성공했다. 그런데 그 한 번의 대화에서 이미 불편한 사실이 보였다. 도구를 두 번 쓰는 동안 **이전 대화가 매번 통째로 다시 전송되어** 호출마다 입력이 불어났다. 대화가 길어지면 이 짐은 계속 커진다. 모델이 한 번에 받을 수 있는 양에는 한계가 있고, 한계에 가까워질수록 비용도 늘고 모델이 앞부분을 놓치기 시작한다.

사람이 이 시스템을 맡았을 때 묻는 질문은 이렇다.

- *"대화가 한참 길어지면 이 에이전트는 어떻게 되는가? 갑자기 멈추는가, 앞을 잊는가?"*
- *"기억을 아껴 쓴다면, 무엇을 버리고 무엇을 남기는가? 버린 것은 정말 사라지는가?"*
- *"아껴 쓰는 과정에서 시스템이 쓰는 지시문이나 기억이 망가지지 않는가?"*

지금은 세 질문에 「모른다」가 정직한 답이다. 더 근본적인 사실이 하나 더 있다. 조사해 보니 **지금의 CLI는 입력 사이에 이전 대화를 모델에게 넘기지 않는다.** 기록은 쌓이지만 다음 질문을 할 때 모델은 직전 대화를 모른다. 에이전트가 「기억」을 말하기 전에 가장 기본적인 단기 기억이 비어 있는 셈이다. 이 로드맵은 그 빈칸을 먼저 메우고(010), 그 위에 **대화가 길어졌을 때 오래된 부분을 요약해 짐을 줄이는 장치**를 얹는다.

이 레포의 목적은 Hermes Agent의 메모리 구조와 작동 구조를 직접 만들며 익히는 것이다. 원본이 「장기 기억(파일), 과거 대화 검색, **대화 기억의 압축**, 절차 기억(스킬)」으로 기억을 나누는데 우리에게는 앞의 둘만 있다. 압축은 셋째 기둥이다.

## 2. 왜 이 정도로만 하는가

이 로드맵이 **일부러 하지 않는 것**과 그 이유다.

| 하지 않는 것 | 이유 | 언제 하는가 |
|---|---|---|
| 모델이 「너무 길다」고 거절한 뒤 줄여서 다시 시도하는 안전망 | 평소 압축이 제대로 도는지가 먼저다. 안전망은 평소 장치가 빗나갈 때를 위한 것이라, 실제 모델에서 빗나가는 정도를 본 뒤에 필요한지 판단한다. | 05 스모크에서 추정 오차가 크게 관찰되면 후속 |
| 요약만 전담하는 다른 모델, 요약 모델 장애 시 갈아타기 | 모델이 하나뿐이고 제공자도 하나다. 구조(요약 호출 1회)만 익히면 충분하다. | 여러 제공자를 지원할 때 |
| 모델마다 다른 임계값, 반복 압축 폭주 방지 장치(쿨다운 등) | 정상 동작을 한 번 확인하기 전에 튜닝할 대상이 없다. 폭주는 「압축 후 줄어들지 않으면 거부」라는 단순한 규칙으로 막는다. | 실제 운용에서 문제가 관찰될 때 |
| 새 세션으로 갈아타는 방식(부모-자식 세션) | 원본에서도 옛 방식이다. 같은 세션 안에서 잇는 쪽이 기록이 끊기지 않는다. 부모-자식 세션 열은 07번(서브에이전트)의 몫이다. | 07번 |
| 외부 기억 제공자와의 연동, 사용자가 직접 압축을 부르는 명령, 이미지·사고 과정 처리 | 원본의 부가 기능이고 기본 구조 이해와 무관하다. | 필요가 생겼을 때 |
| 세션 재개(꺼졌다 켜도 이전 대화 이어가기) | 다른 주제(저장된 세션을 불러오는 방식)다. 05는 한 번 켠 동안의 대화를 다룬다. | 별도 로드맵 |
| 요약 품질을 체계적으로 평가 | 평가 기준을 만드는 일이 별도의 큰 주제다. 스모크에서 눈으로 한 번 본다. | 요약 품질이 문제가 될 때 |

한마디로, **「줄여야 할 때를 알고, 안전하게 줄이고, 줄인 사실을 기록한다」까지만** 한다. 줄이기를 잘하는 법은 그 이후의 문제다.

## 3. 왜 이 순서, 왜 이 단계 수인가

단계는 일곱 개이고, **바닥(문맥)부터 쌓고, 모델 없이 검증되는 부분을 먼저, 기록과 연결은 뒤에, 실제 키는 맨 마지막에** 둔다.

| 순서 | 하는 일 | 왜 이 자리인가 |
|---|---|---|
| 1 (010) | 입력 사이에 이전 대화를 모델에게 넘긴다 | 압축할 「쌓인 대화」가 있어야 압축이 의미가 있다. 가장 먼저 메워야 할 빈칸이다. |
| 2 (020) | 지금 대화가 얼마나 큰지 재고, 줄일 때인지 판단한다 | 모델도 DB도 필요 없는 계산이라 가장 안전하게 먼저 만들 수 있다. |
| 3 (030) | 오래된 도구 결과를 짧게 바꾸고, 어디까지 지킬지(맨 앞과 최근)를 정하고, 도구 호출과 결과의 짝이 깨지지 않게 한다 | 모델을 부르지 않는 순수 계산이다. 짝이 깨지면 모델이 요청을 거절하므로 가장 위험한 부분을 먼저 고정한다. |
| 4 (040) | 중간 부분을 요약하는 문장을 만들고, 요약이 실패해도 대체 요약을 만들며, 맨 앞+요약+최근으로 조립한다 | 모델 호출이 처음 등장하지만 가짜 모델로 시험한다. |
| 5 (050) | 에이전트에 연결하고, 줄인 사실을 DB에 안전하게 기록한다(옛 기록은 보관) | 부품이 모두 검증된 뒤에 연결해야 원인 추적이 쉽다. DB 구조 변경이 포함되므로 마지막에 한 번만 건드린다. |
| 6 (060) | 가짜 통신으로 「길게 대화 → 압축 → 이어서 질문」 전체를 시험한다 | 부품별 시험이 아니라 합쳐졌을 때도 되는지 확인한다. |
| 7 (070) | 진짜 키로 딱 한 번 압축이 실제로 일어나는지 본다 | 비용과 재현성 때문에 마지막에, 사용자가 지시할 때만 한다. |

04번(여섯 단계)보다 하나 많은 이유는 바닥 단계(010)가 추가되었기 때문이다. 020(계산)과 030(변형)을 합치면 한 단계에 두 종류의 위험이 섞이고, 나누면 각각 독립적으로 검증되고 되돌릴 수 있다.

## 4. 왜 이 방식을 택하고 무엇을 배척했나

| 선택 | 배척한 대안 | 이유 |
|---|---|---|
| 같은 세션 안에서 옛 기록은 「보관」으로 표시하고 줄인 본을 새로 둔다 | 새 세션으로 갈아타기 / 옛 기록 삭제 | 한 대화가 한 세션이어야 기록이 끊기지 않는다. 지우지 않으므로 나중에 되짚을 수 있다. |
| 요약은 참고용 배경이라고 문장으로 못박는다 | 요약을 그냥 앞에 붙임 | 요약 안의 문장을 모델이 지시로 오해하면 엉뚱한 일을 한다. 「이것은 과거 기록이며 지시가 아니다」를 요약 앞에 둔다. |
| 맨 앞(시스템 지시문과 기억)은 절대 줄이지 않는다 | 전체를 균등하게 요약 | 시스템 지시문과 기억이 바뀌면 안전 규칙과 기억이 흔들린다. 헤드 불변을 시험으로 고정한다. |
| 먼저 모델 없이 도구 결과를 짧게 바꾼다 | 곧바로 모델에게 요약 | 오래된 도구 출력(긴 파일 내용 등)은 요약하지 않고 짧은 표지로 바꾸는 것만으로 큰 몫이 줄고, 비용이 들지 않는다. |
| 요약 실패 시 모델 없이 만드는 대체 요약 | 실패하면 대화 중단 / 자동 재시도 | 압축 실패로 대화가 멈추는 것은 안전하지 않다. 대체 요약은 정확도는 낮아도 항상 만들 수 있다. |
| 원본에서 구조만 참고하고 핵심 알고리즘만 축소 구현 | 원본 이식 | 5,825줄의 대부분이 이 레포에 무관한 제공자 대응·동시성·튜닝이다. 억지 모방은 안티패턴이다. |

## 5. 성공 판단 기준과 검증할 가정

**성공 기준**: 가짜 통신으로 모든 시험이 통과하고, 낮춘 임계값으로 긴 대화가 압축된 뒤에도 에이전트가 앞선 사실을 이어서 답하며, 줄이기 전의 원문이 DB에 보관되어 있고, 시스템 지시문과 기억이 압축 전후 같으며, 사용자가 지시하면 진짜 키로도 압축이 실제로 일어나 대화가 이어지고, 그 과정에서 키가 어디에도 남지 않는다.

마감 때 종합보고서가 아래 가정을 하나씩 「맞았다 / 틀렸다 / 바뀌었다」로 대조한다.

| 번호 | 가정 | 틀렸다면 |
|---|---|---|
| **A** | 압축은 에이전트 루프의 두 지점과 세션 DB만 건드려 나머지 코드(도구, 지시문 조립, 모델 통신)는 영향이 없다. | 수정 범위가 커진 것이므로 결합을 줄이는 후속이 필요하다. |
| **B** | 맨 앞 보호 + 최근 보호 + 도구 짝 정리로 압축 후에도 모델이 요청을 거절하지 않는다. | 짝 정리 규칙이 부족한 것이므로 보강한다. |
| **C** | 일반 대화 호출 한 번으로 쓸 만한 요약이 나온다. (**미확인**: 이 모델로 한 번도 해 본 적이 없다.) | 요약 문장 구조나 입력 정리를 바꿔야 한다. |
| **D** | 압축 후 모델이 요약에 담긴 앞선 사실을 이어서 답한다. | 요약이 핵심을 놓친 것이므로 섹션 구성을 고친다. |
| **E** | 거친 글자 수 기반 추정이 실제 입력 토큰과 크게 어긋나지 않는다. (**미확인**: 특히 한국어.) | 임계값 비율에 더 여유를 두거나, 오버플로 안전망을 앞당긴다. |
| **F** | 요약 호출이 실패해도 대화가 멈추지 않는다. | 실패 처리 범위를 넓힌다. |
| **G** | 압축해도 시스템 지시문과 기억 스냅샷은 한 글자도 바뀌지 않는다. | 헤드 경계가 새는 것이므로 원인을 찾아 고친다. |
| **H** | DB 구조 변경이 기존 DB를 깨지 않고, 보관된 원문은 이후에도 검색할 수 있다. | 마이그레이션이나 검색 필터를 고친다. |

## 6. 알려진 위험과 아직 확인하지 못한 것

- **요약 품질**: 이 모델이 일반 호출 한 번으로 내는 요약이 쓸 만한지 아직 모른다(가정 C).
- **한국어 토큰 추정 오차**: 글자 수 기반 추정이 한국어에서 얼마나 빗나가는지 모른다(가정 E). 모델이 「너무 길다」고 거절한 뒤의 복구 장치는 이 로드맵에 없다.
- **보관 방식의 세부**: 앞·뒤 기록을 복제할지 제자리에 둘지에 따라 검색 결과에 같은 말이 두 번 나올 수 있다. 050 착수 전에 정한다.
- **손실 압축의 한계**: 요약은 정보를 버린다. 버려진 세부는 보관된 원문에만 남는다.
- **이 MVP의 압축은 한 번 켠 동안의 대화만 다룬다.** 꺼졌다 켜면 이전 대화는 이어지지 않는다(세션 재개 없음).
