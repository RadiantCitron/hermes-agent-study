## 1. 왜 지금 이 로드맵인가

15번에서 기능을 붙이는 자리 세 곳(도구 앞 줄, 한 바퀴의 정해진 지점, 화면 알림)을 만들었다. 그런데 그 자리에 **무엇을 해도 되는지에 대한 규칙**이 없다.

> 자리는 있는데 규칙이 없는 공구함과 같다. 아무 기능이나 대화 내용을 몰래 바꿀 수 있고, 바꾼 내용이 장부에는 안 남는다. 기능끼리 같은 서랍에 물건을 넣다가 섞일 수 있다. 품질을 보는 장치가 고장 나면 모든 도구가 멈추고, 보안 장치는 누가 먼저 꽂았느냐에 따라 순서가 바뀐다.

곧 들어올 두 로드맵이 이 위에 얹힌다. 17번은 「같은 호출을 계속 반복하면 막는」 장치를, 18번은 모든 설정과 상황을 한곳에서 보고 조종하는 제어판을 만든다. 규칙 없이 이 둘을 얹으면 지금의 빈틈이 그대로 굳어서, 나중에 고치려면 얹은 것까지 다 뜯어야 한다. 지금은 이 자리를 실제로 쓰는 기능이 대화 줄이기 하나뿐이라 규칙을 정하는 비용이 가장 싸다.

이 로드맵은 새 능력을 더하지 않는다. **기능을 붙일 때 지켜야 할 계약**(상태는 어디 두는가, 무엇을 볼 수 있고 무엇을 바꿀 수 있는가, 고장 나면 어떻게 되는가, 누가 먼저인가)을 코드로 못 박는다.

## 2. 왜 이 정도로만 하는가 (비목표)

| 하지 않는 것 | 이유 | 언제 하는가 |
|---|---|---|
| 제어판(설정 묶음, 상태 보기, 원격 조종, 변경 기록, 고장 난 기능 자동 끄기) | 계약이 먼저 있어야 제어판이 읽고 조종할 대상이 정해진다 | 18번 |
| 반복 호출 막기(LoopGuard) | 이 계약의 첫 실제 사용자다. 계약과 같이 만들면 어느 쪽이 틀렸는지 가리기 어렵다 | 17번 |
| 승인·체크포인트를 새 줄로 옮기기 | 이번엔 순서와 고장 규칙만 정한다. 실제로 옮기는 건 잘 돌던 안전장치를 건드리는 일이라 따로 한다 | 계약이 안정된 뒤 별도 |
| AI 호출 앞뒤에 끼우는 줄(재시도·비용 한도·추적) | 쓸 기능이 아직 없다 | 비용 한도나 제어판이 필요로 할 때 |
| 대화에 안내 문장을 끼워 넣는 연산 | 쓰는 기능이 없다. 생기면 장부 기록까지 포함한 연산으로 만든다 | 그런 기능이 생길 때 |
| 비동기·스트리밍 | 지금 코어는 한 번에 하나씩 순서대로 돈다 | 스트리밍 응답을 도입할 때 |

## 3. 왜 이 순서, 왜 이 단계 수인가

- **010 상태 칸 → 020 단일 입구 → 030 대화 지키기 → 040 확장 단위·고장 규칙·압축 옮기기 → 050 통합 검증 → 060 마감**.
- 010을 먼저: 다른 모든 단계가 「상태는 확장 이름별 칸에 둔다」를 전제로 한다.
- 020을 030보다 먼저: 도구 앞 줄만 건드려 대화 처리와 섞이지 않는다.
- 030을 040보다 먼저: 압축을 옮길 때 쓸 「장부 먼저 쓰고 대화 바꾸기」 연산이 030에서 생긴다.
- 040이 가장 크다: 확장 단위와 고장 규칙이 압축 옮기기와 묶여야 「쓰는 곳 없는 구조」가 되지 않는다.
- 6단계로 14·15번보다 하나 많다. 010과 020은 둘 다 도구 호출 값을 바꾸지만, 하나가 깨졌을 때 원인을 바로 찾도록 나눴다.

## 4. 왜 이 방식을 택하고 무엇을 배척했나

| 선택 | 배척한 대안 | 이유 |
|---|---|---|
| 도구 앞 줄에는 턴의 상태 칸만 준다 | 대화 전체를 준다 | 도구 쪽 장치가 대화를 바꿀 수 있게 되면 권한이 넓어진다 |
| 고장 규칙은 장치가 놓인 단계가 정한다 | 장치를 붙일 때마다 고른다 | 보안 장치를 「고장 나도 통과」로 잘못 고를 수 있다 |
| 단계 순서를 고정 | 붙인 순서대로 | 안전이 우연한 등록 순서에 달린다 |
| 대화 변경은 「장부 먼저」 연산 하나 | 장치가 직접 바꾸고 장부 일치는 장치 책임(15번 방식) | 14번이 막은 「기억과 장부가 다름」이 다시 생긴다 |
| 계약을 지금 따로 정비 | 17번(LoopGuard)이나 18번(제어판)에 합침 | 계약 없는 장치 위에 먼저 얹으면 나중에 다시 뜯어야 한다 |

## 5. 성공 판단 기준과 검증할 가정

**성공 기준**: 확장이 대화를 장부 없이 바꿀 수 없고, 상태는 확장 이름별 칸에만 있으며, 품질 장치가 고장 나도 도구는 계속 돌고 보안 단계 장치가 고장 나면 도구가 막히며, 기존 시험이 H3 하나를 빼고 수정 없이 통과한다.

| 가정 | 내용 | 확인 시점 |
|---|---|---|
| A | 기존 시험이 H3를 빼고 수정 없이 통과한다(압축 골든 포함) | 각 단계, 050 |
| B | 깨진 JSON 호출도 도구 앞 줄을 지나며, 모델이 받는 오류 문구는 이전과 글자까지 같다 | 020 |
| C | 확장이 대화를 직접 바꾸려 해도 실제 대화와 장부는 그대로이고 기록(`hook_error`)이 남는다 | 030 |
| D | 대화 변경 연산은 장부 쓰기가 실패하면 대화를 바꾸지 않는다 | 030 |
| E | 「고장 나도 통과」 단계의 장치가 고장 나면 도구는 한 번만 실행되고, 「고장 나면 막음」 단계의 장치가 고장 나면 도구는 실행되지 않는다 | 040 |
| F | 압축이 에이전트 내부를 직접 읽거나 쓰지 않는다(코드 검색으로 확인) | 040 |
| G | 붙인 순서와 무관하게 단계 순서대로 실행된다 | 040 |
| H | 위임 자식이 부모의 도구 호출 안에서 돌아도 두 턴의 상태 칸이 섞이지 않는다 | 050 |
| I | 17번 LoopGuard를 이 계약만으로(루프·디스패처 본문 수정 없이) 붙일 수 있다 | 미확인(17번 때) |

## 6. 알려진 위험과 아직 확인하지 못한 것

- **대화 복사 비용**: 장치가 대화를 몰래 바꾸지 못하게 매번 복사·비교한다. 대화가 길수록 느려진다. 실제 비용은 060 전까지 미확인.
- **이름 규칙은 관례로 지킨다**: 기존 시험과 맞추려고 턴 상태 저장소를 그대로 두므로, 「서랍 이름 = 설치된 기능 이름」은 강제가 아니라 약속이다.
- **안전장치 이관 전 공백**: 승인·체크포인트는 아직 새 줄 밖에 있다. 단계는 준비되지만 실제로 옮기기 전까지 순서 보장은 그 둘에 적용되지 않는다.
- **멈춤 요청 뒤 같은 묶음의 나머지 호출**: 코어는 도구 짝을 지키려고 같은 묶음의 나머지 호출을 끊지 않는다. 끊어야 하는 장치는 스스로 막아야 한다.
- **번호가 두 번 바뀐 이력**: 16번 식별자 `R16-PLAN`이 이전 로드맵(현 17번)의 이동 커밋에도 쓰였다.
