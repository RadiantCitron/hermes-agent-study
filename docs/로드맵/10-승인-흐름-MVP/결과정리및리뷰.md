## 1. 마감 개요

- **목표 달성**: 터미널 도구의 허용 목록 밖 명령 실행 시 사람이 대화형 터미널에서 예/아니오(`y`/`N`)로 승인해야만 실행되도록 하는 안전 승인 흐름 MVP 구축 완료.
- **핵심 안전망**:
  1. **사전 선기록 원장**: 사람에게 묻기 전에 `approval_requests`에 `pending`으로 선기록하여 심문 누락 및 판정 번복 원천 차단.
  2. **Zero Leakage 환경 격리**: 승인된 명령이 실행되더라도 프로세스 환경에서 `OPENROUTER_API_KEY`를 완전히 제거하여 키 노출 원천 차단.
  3. **보호 파일 바닥 가드**: 승인기가 동작하더라도 `.env*` 및 `.git` 경로가 인자에 포함되면 사람에게 묻지도 않고 사전 차단.
  4. **Fail-Closed 격벽**: 비터미널 환경, 위임 자식 에이전트, 타임아웃/입력 오류 시 질문 없이 즉시 안전 거부.
- **정량 성과**: 전체 708건 단위/통합 회귀 테스트 100% 통과 (기준선 617건 대비 +91건 신규 검증), 실제 모델(`deepseek/deepseek-v4-flash-0731`) 및 GUI 터미널(WezTerm) 수동 스모크 5회 전수 성공 (API 키 미저장 `False` 전수 확인, 총비용 $0.0035).

## 3. 단계별 구현 및 상세 (Why 중심)

### 010: 승인 요청 원장 (`approval_requests` 표, 스키마 v5, `SessionDB` 메서드)
- **무엇을**: SQLite 스키마 버전 5 상향, `approval_requests` 테이블 및 세션 인덱스 추가, `record_approval_request`, `resolve_approval_request`, `get_approval_requests` 메서드 구현.
- **왜**: 심문(사람에게 묻기) 전에 상태 DB에 먼저 남겨야 모델이나 프로세스가 죽더라도 무슨 명령을 승인 요청했는지 알 수 있고, 한 번 결정된 상태는 사후 번복되지 않아야(불변 원칙) 시스템 일관성을 지킬 수 있습니다.
- **결과**: `SessionDB` 선기록 및 갱신 인터페이스 완비. 단위 시험 14개 통과, 회귀 630건 통과.

### 020: 승인 모듈 (표시 정제, 입력 해석, 요청 상한, fail-closed 판정)
- **무엇을**: `src/hermes_core/tools/approval.py` 신규 모듈 작성, `Approver` 클래스, `@dataclass(frozen=True) ApprovalOutcome`, `format_command_for_display`(제어문자 `repr` 이스케이프), `is_approval_answer`(`y`/`yes` 닫힌 목록) 구현, 상수 9개 추가.
- **왜**: 화면 표시 정제와 승인 판정 비즈니스 로직을 터미널 실행 코드와 분리하여 순수하게 검증할 수 있어야 하며, 제어문자 위장 공격 및 비정상 입력 시 무조건 거부(fail-closed)하는 명확한 계약이 필요했습니다.
- **결과**: 순수 승인 모듈 격리 완성. 단위 시험 18개 통과, 회귀 647건 통과.

### 030: 터미널 도구 연동 (승인기 선택 인자, 디스패처 명시 주입, 보호 파일 바닥, 키 환경변수 차단, 원장 연결)
- **무엇을**: `terminal_tool` 및 `create_default_dispatcher`에 `approver: Optional[Approver] = None` 선택 인자 추가, `_execute` 단일 실행 경로 추출, `_child_env`에서 `TERMINAL_STRIPPED_ENV_NAMES`(`OPENROUTER_API_KEY`) 제거, 질문 전 보호 파일(`is_protected_path`) 바닥 가드 배치.
- **왜**: 터미널 도구 자체는 승인기의 존재를 강제하지 않고 순수하게 주입받아 동작해야 하며, 승인된 명령이라도 프로세스 환경변수로 API 키를 물려받아 출력이나 모델 전송으로 유출되는 참사(Zero Leakage 위반)를 원천 차단해야 했습니다.
- **결과**: 안전한 실행 환경 및 바닥 가드 통합. 단위 시험 24개 통과, 회귀 670건 통과.

### 040: CLI 연동 (터미널일 때 기본 켜짐, `--no-approval`, 승인 프롬프트, 배너, 자식·비터미널 격리)
- **무엇을**: `cli.py`에 `--no-approval` 플래그 추가, `approval_enabled = not args.no_approval and is_interactive_terminal()` 조건부 조립, `session_id` 선발급을 통한 `Approver`와 디스패처 사전 조립 및 주입, 시작 배너 조건부 출력 연동.
- **왜**: 대화형 터미널 사용자에게는 기본으로 강력한 안전망을 제공하되 배치 실행이나 자동화 환경(`--no-approval`, 파이프)에서는 불필요한 프롬프트로 중단되지 않아야 하며, 에이전트 클래스 코드를 한 줄도 수정하지 않고 CLI 조립 계층에서 깔끔하게 주입해야 했습니다.
- **결과**: CLI 사전 조립 주입 완성. 단위 시험 17개 통과, 회귀 687건 통과.

### 050: 통합 검증 (대본형 가짜 모델 E2E, pty 승인 프롬프트) 및 작동원리 동기화
- **무엇을**: `test_agent_e2e.py`에 대본형 E2E 12개 시나리오 추가, `test_cli_approval_pty.py` 신설(pty 가상 터미널 9개 시나리오), 작동원리 01·02·03편 동기화(Q14 신설, 13번 승인 격벽 신설, 안티패턴 추가).
- **왜**: 실제 모델을 부르지 않고도 승인/거부/취소 및 가상 터미널 상호작용 전체 라이프사이클을 CI에서 영구 회귀 시험으로 고정하고, 문서 정본과 구현 사실을 100% 일치시켜야 했습니다.
- **결과**: E2E 및 pty 시험 전수 통과, 전체 회귀 708건 통과.

### 060: 실제 모델 + 실제 터미널 스모크 5회 (WezTerm) 및 마감
- **무엇을**: 사용자의 별도 터미널(WezTerm)에서 실제 모델(`deepseek/deepseek-v4-flash-0731`)로 R1~R5 스모크 실행, 사후 DB 덤프 키 미저장 검사, 종합보고서 작성 및 마감.

- **결과**: 5회 실행 전수 통과, 11회 API 호출 200 OK, Zero Leakage(키 미저장 `False` 5건) 완벽 확인.

## 5. 아키텍처 성과와 시스템 영구 사실

### 1. 13번 방어선: CLI 승인 격벽 (System Permanent Fact)
- **사전 선기록 원칙**: 사용자에게 묻기 전에 상태 DB에 `pending` 상태로 먼저 원장을 기록합니다. 질문 도중 비정상 종료되거나 Ctrl+C로 중단되어도 기록이 유실되지 않습니다.
- **단일 실행 통로 및 환경 격리 (`_execute`, `_child_env`)**: 허용목록 안 명령이든 승인된 명령이든 단 하나의 실행 경로를 거치며, 자식 프로세스 환경에서 `OPENROUTER_API_KEY`가 강제 박탈되어 실행됩니다.
- **보호 파일 바닥 가드 (`args[0]` 포함)**: 승인기가 켜져 있어도 `.env*` 및 `.git` 경로가 인자에 있으면 승인 질문을 띄우지 않고 도구 진입로에서 즉시 차단합니다.
- **격리 네 겹 준수**: 위임 자식 에이전트는 승인기가 주입되지 않아 허용 목록 밖 명령을 실행할 수 없습니다 (자식 격벽).
- **Fail-Closed 원칙**: 비터미널(파이프), 빈 입력(Enter), 모호한 답변, 타임아웃, 예외 발생 시 무조건 `denied` 또는 `cancelled`로 안전 거부합니다.

## 6. 새로 발견한 부분 (관찰 및 한계)

1. **실제 모델의 신사적인 거부 수용 (DeepSeek v4 Flash)**:
   - 거부 문구(`Do not retry it or work around the denial.`)를 받은 모델은 억지 우회나 반복 요청 없이 단번에 거부 사실을 인정하고, 시스템 프롬프트에 제공된 시작 시각을 대체 답변으로 안내하는 높은 순응도를 보였습니다 (가정 H 입증).
2. **모델의 도구 허용 규칙 자체 인지 (R4 관찰)**:
   - R4에서 `python3 .env`를 지시했을 때, 모델은 지시문에 적힌 터미널 허용 목록(echo, pwd, ls 등)을 스스로 읽고 판단하여 `terminal` 도구 자체를 호출하지 않고 텍스트로 불가 사유와 `cat` 대안을 제시했습니다.
3. **알려진 한계 (추후 과제)**:
   - **타임아웃 부재**: 승인 질문에서 사용자가 응답하지 않으면 프로세스가 무한 대기합니다 (`Ctrl+C`로 취소 가능).
   - **기타 비밀 환경변수**: 현재 박탈 목록은 `OPENROUTER_API_KEY` 1종이며, 시스템의 타 환경변수(AWS, GCP 등)는 막지 않습니다.
   - **종료 이유 NULL**: Ctrl+C/Ctrl+D로 세션 종료 시 `sessions.end_reason`이 `NULL`로 남는 기존 동작 유지 (09·10 공통 후속 정리 대상).

## 7. 배척하거나 유예한 대안들

- **세션 캐시 및 영구 허용 목록 배척 ([ADR-0010](../../adr/0010-승인_흐름_MVP_범위와_결정.md) D-03)**: 한 번 승인한 명령을 세션 동안 기억하거나 파일에 저장하면 사용자가 무심코 승인한 위험 명령이 이후 턴에서 자동 실행될 위험이 있으므로 매번 묻는 방식을 택했습니다.
- **파일 도구 승인 유예 (D-01)**: `write_file`·`patch` 승인은 파괴적 쓰기 위험이 있으나, MVP 단계에서는 가장 위험도가 높은 임의 코드 실행(터미널)에 집중했습니다.
- **위임 자식 에이전트의 승인 전달 배척 (D-05)**: 자식이 사용자에게 승인을 묻게 하면 부모-자식 간 인터페이스가 복잡해지고 동시성 문제가 생기므로 자식은 승인 기능 없이 기존 거부 방식을 엄격히 유지했습니다.
- **사후 디스패처 재등록 방식 배척 (D-11)**: 디스패처 생성 후 핸들러를 덮어쓰는 대신, `create_default_dispatcher(..., approver=...)`로 생성 시 명시 주입하는 방식을 채택하여 결합도를 낮추고 도구 불변성을 보장했습니다.

## 8. 후속 로드맵 및 개선 과제 제안

1. **차기 11번 로드맵: 「체크포인트·롤백 MVP」 (합의된 순서)**:
   - 파일 도구(`write_file`, `patch`)로 파일이 변경되기 직전 스냅샷을 뜨고, 에이전트 실패나 사용자 요청 시 이전 시점으로 안전하게 롤백하는 기능 구축.
2. **거부 문구 및 모델 프롬프트 고도화**:
   - 거부 시 모델이 당황하지 않고 허용 도구로 자연스럽게 전환할 수 있도록 프롬프트 가이드 보강.
3. **비정상 종료 원인(`end_reason`) 기록 보강**:
   - `Ctrl+C`(`cancelled`) 및 `Ctrl+D`(`eof`)로 종료 시 `sessions.end_reason`을 정확히 남기도록 CLI 종료 루프 정리.
