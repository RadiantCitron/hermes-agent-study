# [WHY] 10-승인-흐름-MVP — 왜 이 로드맵을, 왜 이 정도로만 하는가

> **성격**: 이 로드맵의 의도를 적은 문서다 (ROADMAP_정책 §3-2). 마감 때 종합보고서(`결과정리및리뷰.md`, 마감 시 작성)가 이 문서의 「검증할 가정」을 하나씩 대조한다. 4단계 착수 후에는 본문을 고치지 않고 맨 끝 「변경 기록」에만 덧붙인다.  
> **작성일**: 2026-10-29 · **함께 보는 문서**: [PLAN.md](PLAN.md)(무엇을 하기로 승인했나), [ROADMAP.md](ROADMAP.md)(설계), [ADR-0010](../../adr/0010-승인_흐름_MVP_범위와_결정.md)(결정 근거)

## 1. 왜 지금 이 로드맵인가

지금 이 에이전트는 허용된 8개 프로그램(`echo pwd ls cat head tail wc grep`) 밖의 명령을 **무조건 거부**한다. 안전하지만, 에이전트에게 「이 파이썬 스크립트를 돌려 봐」, 「테스트를 실행해」 같은 일을 시킬 수 없다는 뜻이기도 하다. 반대로 허용목록에 프로그램을 하나 더 넣으면 임의 코드를 실행할 수 있는 문이 열린다. 작동원리 01편은 이 길(목록 확대, 차단목록)을 이미 기각했다.

사람이 이 시스템을 쓸 때 묻는 질문은 이렇다.

- *"에이전트가 위험한 명령을 마음대로 실행하지 않는가?"*
- *"그렇다면 필요한 일은 어떻게 시키는가? 매번 내가 직접 해야 하는가?"*
- *"내가 승인한 것과 승인하지 않은 것을 나중에 확인할 수 있는가?"*

지금은 첫 질문에 「그렇다. 대신 아예 못 한다」, 둘째에 「못 시킨다」, 셋째에 「해당 없음」이 답이다. 이 로드맵은 **「안전 때문에 못 하는 일」을 「사람이 보고 허락한 일」로 바꾸는 문 하나**를 만든다. 09에서 입력 읽기를 한 함수로 모으고 터미널에서 안정화한 것도 이 질문(예/아니오)을 받기 위해서였다.

## 2. 왜 이 정도로만 하는가

이 로드맵이 **일부러 하지 않는 것**과 그 이유다.

| 하지 않는 것 | 이유 | 언제 하는가 |
|---|---|---|
| 한 번 승인한 명령/패턴을 기억하거나 영구 허용목록에 저장 | 상태가 늘고(저장·철회·동기화), 허용 범위가 시간이 지나며 몰래 커진다. 원본의 최근 변경 이력 대부분이 이 영역이다. MVP는 한 번에 한 명령이다 | 반복 승인이 실제로 불편하다는 증거가 쌓일 때 |
| 위험 패턴(`rm -rf`, `curl \| sh` 등) 감지 | 패턴에 걸리지 않으면 자동 실행되는 구멍이 생긴다. 이 코어는 「허용된 것만」이 기본이라 허용목록 밖은 전부 묻는다 | 하지 않는다 (필요하면 표시용 경고 정도) |
| LLM이 대신 승인 여부를 판단(smart 모드), yolo(전부 허용) | LLM 인젝션 표면을 새로 만들고, yolo는 안전 목적과 반대다 | 하지 않는다 |
| 위임 자식에게 승인 연결 | 사용자가 보지 못하는 자식 맥락에서 질문을 받고, 자식 루프가 같은 질문을 반복할 수 있다 | 자식의 작업이 실제로 필요로 할 때 별도 설계 |
| 파일 도구(`write_file`·`patch`) 승인 | 파일 도구는 이미 작업 폴더·쓰기 금지 정책으로 가둬져 있다. 파일 변경의 위험은 체크포인트·롤백(11)과 함께 판단하는 편이 맞다 | 11번 로드맵의 1단계 검토 때 |
| 승인 대기 타임아웃, 게이트웨이/웹훅 대기 | MVP는 사람이 터미널 앞에 있다고 가정한다. 비터미널은 묻지 않고 거부한다 | 필요가 생기면 |
| 승인 화면의 비밀값 마스킹 | 화면에 보이는 것은 모델이 만든 명령이고, 이 코어는 키를 명령에 넣지 않는다. 실제 위험은 화면이 아니라 승인된 프로그램이 물려받는 환경이며, 그쪽은 이 로드맵에서 막는다(§4) | 별도 점검 후보 |
| 원본 승인 구현(약 3,600줄) 이식 | 대부분이 게이트웨이·플러그인·i18n이다. 필요한 판정 순서와 fail-closed 원칙만 우리 방식으로 | 하지 않는다 |

한마디로, **「허용목록 밖 명령을 사람이 한 번씩 보고 허락하고, 그 기록이 남는다」까지만** 한다.

## 3. 왜 이 순서, 왜 이 단계 수인가

단계는 여섯 개(010~060)이고, **기록 자리를 먼저, 판정 부품은 그다음, 도구에 붙이는 일은 그 뒤, 앱에 붙이는 일은 그 뒤, 실제 사람이 쓰는 확인은 맨 마지막**에 둔다.

| 순서 | 하는 일 | 왜 이 자리인가 |
|---|---|---|
| 1 (010) | 승인 요청을 남길 원장 표와 기록 메서드 | 「묻기 전에 기록한다」가 이 설계의 핵심 원칙이다. 아무것도 실행하지 않는 순수 저장소 작업이라 가장 먼저, 가장 안전하게 만든다. |
| 2 (020) | 승인 요청 객체, 사람에게 보일 표시 정제, 요청 상한, 취소·비터미널 판정 | 화면과 도구 어디에도 붙지 않는 순수 부품이라 시험이 쉽다. fail-closed 규칙을 한 곳에 모은다. |
| 3 (030) | 터미널 도구에 승인기 연결 | 허용목록 밖 명령이 실제로 실행될 수 있게 되는 유일한 단계라서, 부품이 다 검증된 뒤 따로 둔다. |
| 4 (040) | CLI에서 사람에게 묻기 | 사용자에게 보이는 동작이 바뀌는 지점을 한 단계로 둔다. |
| 5 (050) | 가짜 모델·가상 터미널로 끝에서 끝까지 확인, 작동원리 동기화 | 사람 없이 할 수 있는 확인을 먼저 끝낸다. |
| 6 (060) | 실제 모델이 실제로 허용목록 밖 명령을 요청할 때 사람이 승인·거부해 본다 | 모델이 실제로 이 문을 쓰는지, 화면이 이해 가능한지는 실제 모델과 사람이 있어야 본다. 실제 키가 필요한 유일한 단계다. |

## 4. 왜 이 방식을 택하고 무엇을 배척했나

| 선택 | 배척한 대안 | 이유 |
|---|---|---|
| 허용목록 밖 명령을 전부 묻는다 | 위험 패턴에 걸린 것만 묻는다(원본) | 패턴에 안 걸린 명령이 자동 실행되지 않는다. 패턴 목록과의 싸움이 없다. |
| 예/아니오만 | 1회/세션/항상/거부 | 상태를 늘리지 않는다. 한 명령마다 사람이 본다. |
| 묻기 전에 원장에 기록하고, 결정 후 갱신 | 결정 후에만 기록 | 도중에 죽거나 취소돼도 「물었다」는 사실이 남는다. 기존 「선기록 후출력」 원칙과 같다. |
| 라이브러리 기본 꺼짐, CLI는 터미널일 때만 기본 켜짐 | 항상 켜짐 / 옵션으로만 켜짐 | 기존 시험·사용은 그대로 거부이고, 사람이 앉은 터미널에서는 별도 조작 없이 쓸 수 있다. 비터미널은 거부해 「응답할 사람이 없는 입력이 승인으로 읽히는」 일이 없다. |
| 보호 파일 차단은 승인해도 유지 | 승인하면 전부 허용 | 승인 화면에서 사람이 놓치기 쉬운 비밀 파일 접근을 구조적으로 막는다. |
| 승인된 명령은 모델 키를 물려받지 않는다 | 이 프로그램의 환경을 그대로 물려준다 | 승인한 프로그램이 키를 출력하면 그 출력이 모델에게 가고 기록에 남는다. 사람은 승인 화면의 명령만 보고 이 위험을 알아채기 어렵다. (개정 때 추가) |
| 승인 기능은 터미널 도구를 만드는 자리에서 넣는다 | 만들어 둔 도구를 나중에 같은 이름으로 바꿔 끼운다 | 도구의 실체를 한 곳에서 읽을 수 있고, 자식에게는 넣지 않는다는 사실이 만드는 자리에서 그대로 보인다. (개정 때 변경) |
| 위임 자식에는 승인 없음 | 자식에게도 연결 | 사용자가 보지 못하는 곳에서 질문이 쌓이는 일이 없다. |
| 취소·빈 입력·알 수 없는 입력은 거부 | 취소를 건너뛰기/기본 승인 | 「침묵은 동의가 아니다」. 데드락·인젝션 우회의 출구를 만들지 않는다. |

## 5. 성공 판단 기준과 검증할 가정

**성공 기준**: 가짜 모델·가짜 입력으로 모든 시험이 통과하고, 승인 기능이 꺼진 구성(라이브러리 기본, 위임 자식, 비터미널)은 이전과 같은 거부 동작이며, 허용목록 밖 명령은 사람이 승인한 경우에만 실행되고, 모든 요청과 결정이 실행 전에 원장에 남으며, 보호 파일 접근은 승인해도 막히고, 승인된 명령의 출력에 모델 키가 나오지 않으며, 사용자가 실제 터미널에서 실제 모델로 승인·거부를 해 보고, 기존 시험이 한 줄도 바뀌지 않는다(010의 스키마 버전 단언 한 줄은 지시서에 예고된 예외).

마감 때 종합보고서가 아래 가정을 하나씩 「맞았다 / 틀렸다 / 바뀌었다」로 대조한다.

| 번호 | 가정 | 틀렸다면 |
|---|---|---|
| **A** | 승인기가 없는 구성(라이브러리 기본, 위임 자식, 비터미널 입력)에서는 허용목록 밖 명령이 지금처럼 거부되고, 기존 시험이 바뀌지 않고 통과한다. | 연결 방식을 고친다. 기존 사용에 영향이 있다는 뜻이다. |
| **B** | 허용목록 밖 명령은 사람이 승인한 경우에만 실행되고, 거부·취소·빈 입력·알 수 없는 입력·EOF·요청 상한 초과는 모두 실행 없이 거부된다. | 판정 위치를 고친다. 이 로드맵의 핵심 목표가 틀렸다는 뜻이다. |
| **C** | 모든 승인 요청은 사람에게 묻기 **전에** 원장에 남고, 결정이 갱신되며, 결정 종류(승인/거부/자동 거부/취소/상한 초과)가 구분되어 조회된다. | 기록 순서를 고친다. |
| **D** | 보호 파일(`.env*`, `.git`) 접근 인자는 사람이 승인해도 실행되지 않는다. | 바닥 가드 위치를 고친다. |
| **E** | 사람에게 보이는 실행 명령 표시는 제어문자·ANSI 이스케이프가 제거된 `argv`이고, 모델이 만든 문자열이 질문을 위장하지 못한다. | 정제 규칙을 고친다. |
| **F** | 거부된 명령을 모델이 반복 요청해도 요청 상한에서 더 이상 묻지 않고 거부하여 프롬프트가 폭주하지 않는다. | 상한 값을 고치거나 거부 문구를 강화한다. |
| **G** | 실제 터미널에서 도구 실행 도중 승인 프롬프트가 정상으로 뜨고 y/n이 전달되며, 응답 뒤 REPL이 이어진다. (**미확인**: 지금까지 실제 터미널에서 시험하지 않았다.) | 입력 경로를 고친다(별도 프롬프트 방식 등). |
| **H** | 실제 모델이 허용목록 밖 명령을 요청하고, 거부 문구를 받은 뒤 우회 재시도를 하지 않거나 상한에서 멈춘다. (**미확인**: 모델 행동은 실행해 봐야 안다. 모델 1~2종·1회 관찰의 한계.) | 기록하고 거부 문구 보강을 후속 후보로 올린다. 구조는 되돌리지 않는다. |
| **I** | 새 부품 추가가 입력 외의 부분(에이전트 루프, 도구 통로, 압축, 위임, 출력)에 영향을 주지 않는다. | 결합을 고친다. |
| **J** | 승인된 명령은 모델 키 환경변수를 물려받지 않아, 환경변수를 출력하는 명령을 승인해도 키가 도구 결과·모델 요청·상태 DB 어디에도 남지 않는다. (개정 때 추가) | 환경을 넘기는 자리를 고친다. |

## 6. 알려진 위험과 아직 확인하지 못한 것

- **승인된 프로그램은 임의 코드를 실행할 수 있다.** 안전은 사람이 표시된 `argv`를 정확히 읽는 데 달려 있다. 이 로드맵은 그 판단을 대신하지 않는다.
- **작업 폴더 밖 경로 인자와 `state.db`·지시문 파일**은 승인된 명령에서 사람이 판단한다. 보호 파일(`.env*`, `.git`)만 바닥으로 막는다.
- **모델 키 외의 비밀 환경변수는 막지 않는다.** 사용자 셸에 다른 서비스의 토큰이 있으면 승인된 프로그램이 읽을 수 있다. 이 코어가 직접 다루는 비밀은 모델 키 하나다.
- **타임아웃이 없다.** 사람이 자리를 비우면 REPL이 멈춘다.
- **실제 터미널에서의 동작은 미확인**이다. 도구 실행 도중 프롬프트가 `prompt_toolkit` 경로에서 정상인지는 050(가상 터미널)·060(사람)에서 본다.
- **링크 따라가기 등** 승인된 프로그램의 옵션별 위험은 개별 검증하지 않는다.
- **원본의 승인 시험 케이스는 일부만 읽었다**. 세부는 미확인이다.
