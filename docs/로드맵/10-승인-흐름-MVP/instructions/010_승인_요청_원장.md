## 1. 구현 내용 명세

사람에게 묻기 **전에** 승인 요청을 남기고, 결정이 나오면 같은 행을 갱신하는 저장소를 만든다. 이 단계에서는 **도구·에이전트·CLI를 전혀 바꾸지 않는다.** 아무것도 호출하지 않는 순수 저장 기능이다(020 이후가 이것을 쓴다).

1. **새 표** `approval_requests` ([`session_db.py`](../../../../src/hermes_core/session_db.py) `SCHEMA_SQL`에 `CREATE TABLE IF NOT EXISTS`, `llm_calls`와 같은 방식):

   | 열 | 타입 | 뜻 |
   |---|---|---|
   | `id` | INTEGER PRIMARY KEY AUTOINCREMENT | 요청 번호 |
   | `session_id` | TEXT NOT NULL REFERENCES sessions(id) | 어느 세션의 요청인가 |
   | `tool_name` | TEXT NOT NULL | 요청한 도구 이름(지금은 `terminal`만 쓰이지만 11 이후 확장 여지) |
   | `argv_json` | TEXT NOT NULL | 실행될 인자 리스트를 JSON 문자열로(`ensure_ascii=False`) |
   | `created_at` | REAL NOT NULL | 요청을 남긴 시각(`time.time()`) |
   | `decision` | TEXT NOT NULL | 아래 닫힌 목록 중 하나. 처음은 `pending` |
   | `decided_at` | REAL | 결정 시각. `pending`일 때는 `NULL` |
   | `reason` | TEXT | 결정 사유 한 줄(선택) |

   인덱스 `idx_approval_requests_session` (`session_id`). `tool_call_id` 열은 **두지 않는다**: 터미널 도구는 그 값을 모르고(`ToolDispatcher.handle_function_call`이 넘기지 않음), 대응은 `session_id`와 시간 순서로 한다.
2. **결정 값의 닫힌 목록** ([`constants.py`](../../../../src/hermes_core/constants.py), 승인 흐름 절 신설): `APPROVAL_DECISION_PENDING = "pending"` 외에 최종 결정 5개 — `"approved"`(사람이 예), `"denied"`(사람이 아니오·빈 입력·알 수 없는 입력), `"cancelled"`(EOF·Ctrl+C·입력 예외), `"auto_denied"`(응답할 사람이 없는 비터미널), `"limit_exceeded"`(요청 상한 초과). 이 5개를 `APPROVAL_FINAL_DECISIONS` 튜플로 묶는다. 보호 파일 때문에 **묻기 전에** 막힌 요청은 승인 요청이 아니므로 이 표에 남기지 않는다(그 거부는 도구 결과로 대화 원장에 남는다. ROADMAP §2-4 표의 「기록 없음 또는 `blocked`」를 「기록 없음」으로 확정).
3. **`SessionDB` 메서드** (`record_llm_call`/`get_llm_calls`와 같은 모양, 쓰기마다 즉시 `commit`):
   - `record_approval_request(session_id, argv, tool_name="terminal") -> int`: `argv`는 비어 있지 않은 문자열 리스트여야 한다(아니면 `ValueError`, 행을 만들지 않음). `decision='pending'`, `decided_at=NULL`로 INSERT 하고 즉시 커밋한 뒤 새 `id`를 반환한다. 없는 `session_id`는 외래키 위반(`sqlite3.IntegrityError`)이 그대로 올라온다.
   - `resolve_approval_request(request_id, decision, reason=None) -> bool`: `decision`이 `APPROVAL_FINAL_DECISIONS`에 없으면(`pending` 포함) `ValueError`(행은 그대로). **`pending`인 행만** 갱신한다(`UPDATE … WHERE id=? AND decision='pending'`). 갱신하면 `True`, 이미 결정된 행이거나 없는 `id`면 아무것도 바꾸지 않고 `False`. 한 번 정해진 결정은 다시 바꾸지 않는다.
   - `get_approval_requests(session_id) -> list[dict]`: 그 세션의 행을 `id` 오름차순으로 `dict` 리스트로 반환(`get_llm_calls`와 같은 모양, `argv_json`은 문자열 그대로).
4. **스키마 버전 5**: `SCHEMA_VERSION = 5`. `_init_schema`에 `if current_version < 5: UPDATE schema_version SET version = 5`를 더한다(새 표만 늘어서 `ALTER`는 없다. 표는 `executescript(SCHEMA_SQL)`의 `IF NOT EXISTS`가 만든다). 기존 표·열·메서드는 바꾸지 않는다.
5. **기존 시험 한 줄 수정 (예고된 예외)**: [`test_agent_e2e.py`](../../../../tests/test_hermes_core/test_agent_e2e.py) 1085행 `assert db.schema_version == 4`(v3 DB를 열어 v4 마이그레이션을 확인하는 시험)는 버전을 5로 올리면 틀어진다. 이 줄을 **`assert db.schema_version >= 4`로 한 줄만 교체**한다(의미: 최소 v4까지 마이그레이션됨. `test_session_db.py`가 이미 `>= 3`을 쓰는 방식과 같다). 이 줄 외에 기존 시험 파일은 어떤 줄도 바꾸지 않는다. 이 예외는 계획 단계에서 미리 밝혔으며, 구현 중 다른 시험이 깨지면 임의로 고치지 말고 멈춰서 보고한다.
6. **알려진 한계**: 묻기 전에 죽으면 `pending` 행이 남는다(흔적 용도이며 이 단계는 정리하지 않는다). 세션 종료 시 `pending`을 어떻게 볼지는 후속 지시서에서 다룬다. 요청 문자열의 정제·길이 상한은 020에서 다루고, 이 단계의 저장소는 받은 리스트를 그대로 저장한다.
7. **작동원리·ROADMAP 갱신**: 없음(050에서 일괄 반영). ROADMAP §6-1의 `tool_call_id` 서술은 이 지시서의 결정(열 없음)에 맞춰 050 동기화 때 정정한다.

## 3. 인수 테스트 시나리오 (구현 전 작성, 임의 변경 금지)

시험은 `tests/test_hermes_core/test_approval_ledger.py`에 둔다. DB는 임시 폴더의 파일 DB(`tmp_path / "state.db"`)를 쓰고, 세션은 `create_session`으로 만든다(기존 `test_session_db.py` 방식). 옛 DB는 SQL 스크립트로 직접 만든다(기존 `test_agent_e2e.py`의 v3 시험 방식). 기대값은 ADR-0010 §2-7과 위 명세에서 나왔고 구현 결과를 보고 쓰지 않았다.

| # | 입력 | 기대 결과 |
|---|---|---|
| 1 | 새 DB를 `SessionDB(path)`로 연다 | `db.schema_version == 5`, `approval_requests` 표가 있고 열 이름 집합이 정확히 `{id, session_id, tool_name, argv_json, created_at, decision, decided_at, reason}` |
| 2 | v4 모양 옛 DB(표 `schema_version=4`, `sessions`·`messages`(v4 열 포함)·`llm_calls`에 각각 행 1개 이상)를 연다 | `schema_version == 5`, `approval_requests`가 생김, 옛 행이 모두 그대로(개수·내용 동일) |
| 3 | v3 모양 옛 DB(`test_agent_e2e.py`의 v3 시험과 같은 모양)를 연다 | `schema_version == 5`, `approval_requests`가 생김, 옛 행 그대로 |
| 4 | `record_approval_request(sid, ["python", "-c", "print('한글')"])` | 양의 정수 `id`를 반환, 조회한 행: `decision == "pending"`, `decided_at is None`, `reason is None`, `tool_name == "terminal"`, `session_id == sid`, `created_at`은 현재 시각 근처(양수), `json.loads(argv_json) == ["python", "-c", "print('한글')"]`이고 `argv_json` 원문에 `한글`이 그대로 보임(`\u` 이스케이프 아님) |
| 5 | 4 직후(결정 전) 같은 파일을 **다른** `SessionDB` 연결로 열어 조회 | 방금 남긴 `pending` 행이 보임 (묻기 전에 이미 커밋됨 = 선기록) |
| 6 | 최종 결정 5개 각각(`approved`, `denied`, `cancelled`, `auto_denied`, `limit_exceeded`)에 대해 새 요청을 만들고 `resolve_approval_request(id, 결정, "사유")` | 반환 `True`, 행의 `decision`이 그 값, `decided_at`이 `created_at` 이상, `reason == "사유"` |
| 7 | 6으로 `approved`가 된 행에 `resolve_approval_request(id, "denied", "번복")` | 반환 `False`, 행은 그대로(`decision == "approved"`, 사유도 원래 값) — 한 번 정해진 결정은 바뀌지 않음 |
| 8 | 새 요청에 `resolve_approval_request(id, "pending")` / `resolve_approval_request(id, "maybe")` | 둘 다 `ValueError`, 행은 여전히 `pending` |
| 9 | 존재하지 않는 `id`(예: 9999)로 `resolve_approval_request(9999, "approved")` | `False`, 예외 없음 |
| 10 | 존재하지 않는 `session_id`로 `record_approval_request` | `sqlite3.IntegrityError`, 표에 행이 늘지 않음 |
| 11 | `argv`가 `[]` / 문자열 `"ls -la"` / `["ls", 1]` / `None`인 `record_approval_request` | 모두 `ValueError`, 표에 행이 늘지 않음 |
| 12 | 세션 2개에 요청을 섞어 만든 뒤 `get_approval_requests(세션A)` / 요청 없는 세션 / 없는 세션 id | A는 A의 행만 `id` 오름차순, 요청 없는 세션과 없는 id는 `[]` |
| 13 | 요청 기록·결정 갱신 전후로 `messages` 개수, `llm_calls` 개수, 세션의 `message_count` | 모두 변하지 않음 (원장끼리 서로 섞이지 않음, 가정 I) |
| 14 | 기존 시험 전체 | `test_agent_e2e.py` 1085행 한 줄 교체(`== 4` → `>= 4`) 외에는 한 줄도 바꾸지 않고 통과 |

## 5. 위험·주의

- **「선기록」은 커밋까지 포함이다**: 연결이 열린 채 커밋하지 않은 행은 다른 연결에서 보이지 않는다. 시나리오 5가 이를 잡는다. 쓰기마다 즉시 커밋하는 `record_llm_call` 방식을 따른다.
- **닫힌 결정 목록은 이후 단계의 계약이다**: 020 이후가 이 5개 값을 쓴다. 값을 늘리려면 이 지시서를 고치지 않고(불변) 새 지시서에서 상수를 확장한다.
- **마이그레이션 시험이 옛 DB 모양에 의존**: 시나리오 2·3의 옛 DB 스크립트는 현재 코드가 만드는 표와 달라 보일 수 있다(열 일부 생략). 시험이 거울이 되지 않도록 옛 DB는 SQL로 직접 쓰고, 현재 `SCHEMA_SQL`을 복사해 만들지 않는다.
- **시험이 구현의 거울이 되지 않게**: 시나리오 7·8의 기대(번복 불가, 닫힌 목록)는 요구에서 나왔다. 구현 중 결과가 다르면 시나리오를 바꾸지 말고 멈춰서 보고한다.
- **`>= 4` 교체의 의미**: 이 단언은 「v3 DB가 v4로 마이그레이션되었다」를 확인하던 시험이다. 최신 버전과 같다는 보장이 아니라 「최소 v4까지」로 읽는다. 최신 버전 단언은 시나리오 1·2·3이 맡는다.
- **상한·정제는 이 단계 밖**: 매우 긴 `argv`나 제어문자는 저장소가 막지 않는다. 사람에게 보이는 표시의 정제와 요청 상한은 020이다.
- **`pending` 행의 의미**: 묻는 도중 프로세스가 죽으면 영원히 `pending`으로 남는다. 이는 의도된 흔적이며 자동 정리는 하지 않는다(오래된 `pending`의 취급은 060 스모크 관찰 뒤에 판단).
