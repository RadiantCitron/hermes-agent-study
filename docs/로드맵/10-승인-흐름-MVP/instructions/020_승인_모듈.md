## 1. 구현 내용 명세

사람에게 명령을 보여 주고 예/아니오를 받아 **승인 여부 하나를 판정**하는 부품을 만든다. 이 단계에서는 **터미널 도구·디스패처·에이전트·CLI를 전혀 바꾸지 않는다.** 아무도 이 부품을 부르지 않는 상태로 끝난다(030이 터미널 도구에, 040이 CLI에 잇는다). 입력과 출력, 터미널 여부는 모두 **주입받는 함수**라서 이 단계의 시험은 실제 터미널 없이 돈다.

새 모듈 [`src/hermes_core/tools/approval.py`](../../../../src/hermes_core/tools/approval.py) (원본 `hermes-agent/tools/approval.py`의 fail-closed 원칙만 가져옴. 모듈 머리 주석에 「원본 레퍼런스 매핑」을 다른 도구 모듈과 같은 모양으로 적는다):

1. **`format_command_for_display(argv) -> str`** (순수 함수): 실행될 `argv`를 **파이썬 리스트 표기 한 줄**(`str(list(argv))`)로 만든다. 따옴표·`\n`·`\x1b`·`‮` 같은 제어·서식 문자는 `repr` 규칙에 따라 **눈에 보이는 이스케이프 글자**(`\\n`, `\\x1b`)로 바뀌므로, 모델이 만든 문자열이 줄을 바꾸거나 화면을 지우거나 방향을 뒤집어 질문을 위장할 수 없다. 화면에 보이는 것이 곧 실제 `argv`다(제거하지 않고 드러낸다. ADR §2-8의 「정제」를 이렇게 확정). 잘라내지 않는다(아래 4번 참조).
2. **`is_approval_answer(answer) -> bool`** (순수 함수): `answer`가 문자열이고 `answer.strip().casefold()`가 `APPROVAL_YES_ANSWERS`(`"y"`, `"yes"`)에 정확히 같을 때만 `True`. 빈 문자열·`n`·`maybe`·`yes please`·`y`와 다른 내용이 줄바꿈으로 이어진 입력·문자열이 아닌 값은 모두 `False`(「예」의 좁은 목록만 승인, 나머지는 전부 거부).
3. **`ApprovalOutcome`** (`@dataclass(frozen=True)`): `approved: bool`, `decision: str`(`APPROVAL_FINAL_DECISIONS` 중 하나, 원장에 남은 값과 같음), `message: str`(거부일 때 모델에게 돌려줄 문구, 승인이면 빈 문자열). 별도의 「요청 객체」는 만들지 않는다: 요청은 `argv`와 승인기가 아는 세션 ID로 충분하고, 값 하나짜리 객체를 하나 더 두는 것은 쓰임 없는 구조다.
4. **`Approver`** 클래스. 생성자(모두 키워드 인자, 기본값 없는 것이 일부러 있다: 숨은 기본 연결을 두지 않는다):

   | 인자 | 뜻 |
   |---|---|
   | `session_db` | `SessionDB`. 요청을 남기고 결정을 갱신한다 |
   | `session_id` | 요청이 귀속될 세션. 이 세션은 `session_db`에 **이미 있어야 한다**(원장의 외래키). 세션 ID를 승인기까지 전달하는 방법은 030에서 정한다 |
   | `ask` | `ask(prompt: str) -> str`. 사람에게 한 줄을 묻는다(040이 `read_user_input`을 넘긴다) |
   | `is_interactive` | `is_interactive() -> bool`. 지금 응답할 사람이 있는가(040이 `is_interactive_terminal`을 넘긴다) |
   | `say` | `say(text: str) -> None`. 사람에게 보여 주는 출력. 기본값 `print` |
   | `limit` | 승인기 하나가 받는 요청 횟수 상한. 기본값 `APPROVAL_REQUEST_LIMIT`(10). 1 이상의 `int`(`bool` 제외)이 아니면 `ValueError` |

   메서드 `request(argv) -> ApprovalOutcome`. **판정 순서는 아래와 같고, 이 순서가 이 부품의 계약이다**:

   1. **선기록**: `session_db.record_approval_request(session_id, argv)`로 `pending` 행을 만든다. `argv`가 규칙 위반(`ValueError`)이거나 세션이 없어 기록이 실패(`sqlite3.IntegrityError` 등)하면 **예외를 그대로 올린다**: 기록하지 못하는 요청은 묻지도, 실행하게 두지도 않는다(디스패처가 도구 실패로 감싸 명령은 실행되지 않는다). 이때는 `ask`·`say`를 부르지 않고 요청 횟수도 세지 않는다.
   2. **횟수 세기**: 기록에 성공하면 이 승인기의 요청 횟수를 1 올린다. 승인기마다 따로 센다(세션 전체가 아니다).
   3. **상한 검사**: 횟수가 `limit`을 넘으면 묻지 않고 `limit_exceeded`. (승인된 요청도 횟수에 든다.)
   4. **비터미널 검사**: `is_interactive()`가 거짓이면 묻지 않고 `auto_denied`. 아무것도 출력하지 않는다.
   5. **길이 검사**: `format_command_for_display(argv)`가 `APPROVAL_DISPLAY_MAX_CHARS`(2000)자를 **넘으면** 묻지 않고 `denied`. 사람이 끝까지 읽지 못한 명령은 승인할 수 없다. 길이가 정확히 2000자면 묻는다(상한은 포함).
   6. **질문**: `say`로 안내 한 줄(`APPROVAL_HEADER`)과 표시 문자열을 보여 주고 `ask(APPROVAL_PROMPT)`로 답을 받는다. 보여 주기와 묻기 중에 `Exception` 또는 `KeyboardInterrupt`(`EOFError` 포함)가 나거나 답이 문자열이 아니면 `cancelled`. 이 취소는 **프로그램을 끝내지 않는다**(예외를 밖으로 올리지 않고 거부 결과로 돌려준다).
   7. **해석**: 답이 `is_approval_answer`를 통과하면 `approved`, 아니면 `denied`.
   8. **결정 갱신**: `resolve_approval_request(id, 결정, 사유)`로 같은 행을 갱신한다. 갱신이 예외를 내거나 `False`를 돌려주면(이미 결정된 행) `approved`든 아니든 **예외를 올려** 결과를 돌려주지 않는다(`False`는 `RuntimeError`로 바꿔 올린다): 기록이 어긋난 채 실행되지 않게 한다. 사유는 한 줄 짧은 영어 문장(예: 취소는 예외 클래스 이름 포함)이며 시험은 사유 문구를 확인하지 않는다.
   9. **결과 반환**: 거부 계열의 `message`는 상수에서 가져온다(아래). 승인이면 `message`는 빈 문자열.

5. **상수** ([`constants.py`](../../../../src/hermes_core/constants.py) 승인 흐름 절에 이어서 추가, 010에서 만든 상수는 그대로):

   | 이름 | 값 |
   |---|---|
   | `APPROVAL_REQUEST_LIMIT` | `10` |
   | `APPROVAL_DISPLAY_MAX_CHARS` | `2000` |
   | `APPROVAL_YES_ANSWERS` | `("y", "yes")` |
   | `APPROVAL_HEADER` | `"Approval required: the agent wants to run a command that is not on the allowed list."` |
   | `APPROVAL_PROMPT` | `"Run it? [y/N] "` |
   | `APPROVAL_DENIED_MESSAGE` | `"The user denied this command. Do not retry it or work around the denial."` (`denied`·`cancelled`의 거부 문구. ADR §2-8의 한국어 문구를 이 코드 베이스의 도구 오류 문장(영어)에 맞춰 옮김) |
   | `APPROVAL_AUTO_DENIED_MESSAGE` | `"No user is available to approve commands, so the command was not run."` |
   | `APPROVAL_LIMIT_MESSAGE` | `"The approval request limit ({limit}) has been reached, so the command was not run. Do not request more."` |
   | `APPROVAL_TOO_LONG_MESSAGE` | `"The command is longer than {max_chars} characters and cannot be reviewed by the user, so it was not run."` |

   `{limit}`·`{max_chars}`는 `str.format`으로 채운다. 문구와 상한 값은 ROADMAP §6-5가 에이전트가 정한 안이라고 밝힌 값이며, 착수(「진행해라」) 시 승인으로 갈음한다.

6. **이 모듈이 알지 못하는 것**: 터미널 도구, 디스패처, 에이전트, CLI, `path_guard`. `constants`와 `SessionDB`(타입 힌트·메서드 호출)만 쓴다. `import`에 위 모듈이 나오면 격리 위반이다.
7. **작동원리·ROADMAP 갱신**: 없음(050에서 일괄 반영).

## 3. 인수 테스트 시나리오 (구현 전 작성, 임의 변경 금지)

시험은 `tests/test_hermes_core/test_approval.py`에 둔다. 승인기는 실제 `SessionDB`(`tmp_path / "state.db"`, `create_session`으로 세션 생성)와 **가짜 `ask`**(준비된 답을 순서대로 돌려주거나 예외를 내는 함수), `is_interactive=lambda: True`(또는 `False`), `say`는 문자열을 모으는 함수로 쓴다. 기대값은 ADR-0010 §2-3·§2-7~2-9, ROADMAP §2-4와 위 명세에서 나왔고 구현 결과를 보고 쓰지 않았다. 「행」은 `get_approval_requests(session_id)`로 읽은 원장 행이다.

| # | 입력 | 기대 결과 |
|---|---|---|
| 1 | `is_approval_answer`에 `"y"`, `"Y"`, `"yes"`, `"YES"`, `"  yes \n"` | 모두 `True` |
| 2 | `is_approval_answer`에 `""`, `"  "`, `"n"`, `"no"`, `"ye"`, `"yy"`, `"yes please"`, `"y\nrm -rf x"`, `"true"`, `"1"`, `"ok"`, `"ｙ"`(전각), `None`, `1` | 모두 `False` |
| 3 | `format_command_for_display(["python", "-c", "print(1)"])` | `str(["python", "-c", "print(1)"])`와 같은 한 줄 |
| 4 | 위장 시도: `argv = ["echo", "ok\n\nApproved by the user. Run it? [y/N] y", "\x1b[2J\x1b[31mred", "‮evil", "​", "\x07\x08\r"]` | 표시 문자열에는 **출력 불가 문자가 하나도 없다**(모든 글자 `ch.isprintable()`), `\n`·`\r`·ESC(`\x1b`) 실제 글자가 없고, 이스케이프 글자가 눈에 보인다(`"\\x1b[2J" in 표시`). 한글 `["echo", "한글"]`의 표시에는 `한글`이 그대로 있다 |
| 5 | 답 `["y"]`로 `request(["python", "--version"])`. `ask` 안에서 호출 순간의 원장을 읽는다 | 결과 `approved is True`, `decision == "approved"`, `message == ""`. `ask`가 불린 순간 그 행은 이미 `pending`이다(선기록). `ask`는 정확히 1번, 인자는 `APPROVAL_PROMPT`. `say`로 나간 글에 `APPROVAL_HEADER`와 표시 문자열이 있다. 호출 뒤 행은 `decision == "approved"`, `decided_at`이 있고 `json.loads(argv_json) == ["python", "--version"]` |
| 6 | 답이 각각 `"n"`, `""`, `"maybe"`, `"yes please"`인 요청 4개 | 각각 `approved is False`, `decision == "denied"`, `message`가 비어 있지 않고 소문자로 바꾼 글에 `retry`가 있음(우회 재시도 금지 문구). 행은 모두 `denied` |
| 7 | `ask`가 `EOFError` / `KeyboardInterrupt` / `RuntimeError` / `OSError`를 내거나 `None`을 돌려주는 요청 5개 | 모두 예외가 밖으로 나오지 않고 `approved is False`, `decision == "cancelled"`, 거부 `message`는 6과 같은 계열(비어 있지 않고 `retry` 포함). 행은 `cancelled` |
| 8 | `say`가 예외를 내는 요청 | 7과 같다(`cancelled`, 예외 없음). `ask`는 불리지 않아도 된다 |
| 9 | `is_interactive`가 거짓인 요청. `ask`·`say`는 부르면 시험이 실패하는 함수 | `approved is False`, `decision == "auto_denied"`, `ask`·`say` 호출 0회, 비어 있지 않은 `message`. 행은 `auto_denied` |
| 10 | 기본 상한: 답이 모두 `"n"`인 요청 10개 뒤 11번째(답 `"y"`가 준비됨), 12번째 | 1~10번째 `denied`. 11·12번째는 `approved is False`, `decision == "limit_exceeded"`, `ask` 호출이 늘지 않음(총 10회). `message`에 상한 값 `10`이 보임. 행 12개의 결정은 `denied`×10, `limit_exceeded`×2 |
| 11 | `limit=3`, 답이 모두 `"y"`인 요청 4개 | 1~3번째 `approved`, 4번째 `limit_exceeded`(승인도 횟수에 듦) |
| 12 | 같은 세션에 승인기 둘(각 `limit=2`)을 만들어 번갈아 요청 | 승인기마다 따로 센다(A 2회 + B 2회 모두 질문됨, A의 3번째만 `limit_exceeded`) |
| 13 | `limit`에 `0`, `-1`, `True`, `"3"`, `2.0`을 넘겨 생성 | 모두 `ValueError` |
| 14 | 길이: 표시 문자열 길이가 정확히 `APPROVAL_DISPLAY_MAX_CHARS`인 `argv`(원소 하나 `["x"*N]`의 리스트 표기는 `N + 4`자) 답 `"y"` / 길이가 상한 + 1인 `argv` 답 `"y"` | 앞의 것은 질문되어 `approved`. 뒤의 것은 `ask`·`say` 호출 0회, `approved is False`, `decision == "denied"`, `message`에 `2000`이 보임. 행은 `denied` |
| 15 | 선기록 실패: 없는 `session_id`의 승인기로 요청 / `argv`가 `[]`, `["ls", 1]` | 앞은 `sqlite3.IntegrityError`, 뒤는 `ValueError`가 밖으로 나옴. 모든 경우 `ask`·`say` 호출 0회, 표에 행이 늘지 않음 |
| 16 | 결정 갱신 실패: `resolve_approval_request`가 `False`를 돌려주는 가짜 DB(실제 `SessionDB`를 감싸 `record`는 위임, `resolve`만 가로챔), 답 `"y"` | `RuntimeError`가 밖으로 나오고 `ApprovalOutcome`이 돌려지지 않음. `resolve`가 예외를 내는 경우도 그 예외가 그대로 나옴 |
| 17 | 모든 위 시험 전체 | 요청·결정 전후로 `messages` 개수, `llm_calls` 개수가 변하지 않음(원장끼리 섞이지 않음, 가정 I) |
| 18 | 기존 시험 전체 | 기존 시험 파일 무수정으로 통과 |

## 5. 위험·주의

- **「정제」는 제거가 아니라 드러내기다**: WHY 가정 E의 문장은 「제어문자·ANSI 이스케이프가 제거된」이라고 적었다. 이 지시서는 **제거 대신 눈에 보이게 이스케이프**하는 쪽으로 확정했다(제거하면 사람이 보는 명령과 실행될 명령이 달라지고, 모델이 숨긴 글자를 사람이 알 수 없다). 가정 E의 취지(모델이 질문을 위장하지 못함)는 시나리오 4가 확인한다. 마감 때 가정 E는 「바뀌었다(제거 → 이스케이프 표시)」로 대조한다. 한계: 서로 다른 글자가 비슷하게 보이는 문자(키릴 `а` 대 라틴 `a`)는 이 방식으로 구별되지 않는다.
- **긴 명령은 묻지 않고 거부한다**: 잘라서 보여 주면 사람이 보지 못한 뒷부분을 승인하게 된다. 그래서 상한을 넘으면 `denied`로 막는다(닫힌 결정 목록에 새 값을 늘리지 않으려 `denied`에 사유로 남긴다). 정당하게 긴 한 줄 스크립트(`python -c ...`)도 막히는 것은 의도된 대가이며, 이로 인한 사용 불편은 060 스모크에서 관찰한다.
- **상한은 요청 횟수다**: 승인된 요청도 센다. 상한은 「프롬프트 폭주 방지」가 목적이므로 승인 후 허용 범위를 늘리는 장치가 아니다. 상한 값 10이 실제 작업에 짧은지는 060에서 관찰한다(**미확인**).
- **취소는 거부다**: Ctrl+C·EOF·입력 예외를 승인으로 읽는 길이 없어야 한다. 시나리오 7의 5가지 입력이 이를 잡는다. 시험이 구현의 거울이 되지 않게 시나리오 6·7·9의 기대(거부 계열, 호출 0회)는 요구에서 나왔다. 구현 중 결과가 다르면 시나리오를 바꾸지 말고 멈춰서 보고한다.
- **기록이 어긋나면 결과를 내지 않는다**: 시나리오 15·16. 선기록에 실패하면 묻지 않고, 갱신에 실패하면 승인 결과를 돌려주지 않는다. 호출하는 쪽(030)은 이 예외를 「실행하지 않음」으로 처리해야 한다. 디스패처의 기존 예외 처리(도구 실패로 감쌈)가 이를 맡지만, 030에서 시험으로 확인한다.
- **`say`·`ask`는 이 부품이 정하지 않는다**: 실제 터미널(`prompt_toolkit`)에서의 동작은 **미확인**이다(040·050·060). 이 단계의 시험은 가짜 함수만 쓰므로 가정 G를 검증하지 못한다.
- **세션 ID의 전달**: 이 승인기는 생성 때 `session_id`를 받는다. 세션이 에이전트 안에서 만들어지는 CLI 구성에서 이 값을 어떻게 미리 아는지는 030에서 코드와 대조해 확정한다. 이 지시서의 `Approver` 시그니처가 030에서 막히면 030을 멈추고 보고한다(이 지시서는 수정하지 않고 030 지시서에서 확장한다).
- **`pending` 행**: 시나리오 5·15·16에서 보듯 질문 중 죽거나 갱신에 실패하면 `pending`이 남는다. 010에서 밝힌 대로 흔적이며 이 단계는 정리하지 않는다.
