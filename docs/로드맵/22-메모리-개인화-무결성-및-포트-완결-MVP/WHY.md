# [의도와 가정] 22-메모리-개인화-무결성-및-포트-완결-MVP

> **문서 성격**: 왜 이 로드맵을 지금 진행하며, 왜 이 정도로만 범위를 한정하는지, 그리고 마감 시 어떤 가정을 검증할 것인지를 선언하는 문서입니다 ([ROADMAP_정책.md §3-2](docs/로드맵/ROADMAP_정책.md) 준수).

---

## 1. 왜 지금 이 로드맵인가

- 21번 로드맵까지 거쳐 프로그램의 전체 골격(31개 소스 파일, 6대 순수 도메인, 실행환경 포트)이 완성되었습니다.
- 이제 구조를 새로 뜯어고치거나 파일을 늘릴 것이 아니라, 이미 잡혀 있는 구조 위에서 **가장 중요한 개인화 기억 장치(`memory_tool.py`)와 과거 대화 찾기(`session_search`)에 남아 있는 5가지 내부 허점**을 메워야 합니다:
  1. 짧은 메모가 긴 메모의 일부분과 겹치면(예: `"맥북 사용"`과 `"맥북 사용 중이며 터미널 선호"`), 짧은 메모를 고치거나 지우려 할 때 항상 두 개가 함께 걸려 **짧은 메모를 영원히 지우지도 고치지도 못하는 함정**이 있습니다. 또한 바꾸기(`replace`)를 할 때 이미 있는 다른 메모와 똑같은 내용으로 바꿔도 중복으로 들어갑니다.
  2. 메모 파일에 실제로 저장하기 전에 프로그램 머릿속 목록을 먼저 고쳐서, 저장하다가 오류가 나면 파일과 머릿속 목록이 어긋납니다. 반대로 이미 있는 메모 파일을 읽다가 오류가 나면 프로그램이 「빈 메모장」으로 착각하고 다음 추가 때 옛날 기억 전체를 덮어써 날려버립니다.
  3. 대화가 열려 있는 동안 사람이 밖에서 메모장 파일을 직접 고치면, AI가 그 사실을 모르고 옛날 목록으로 덮어써 버립니다.
  4. 대화가 길어져 앞부분이 요약되거나 세션을 이어받았을 때(`--resume`), AI가 지금 메모장에 무엇이 적혀 있는지 고치지 않고 **그냥 눈으로 확인만(`list`) 할 방법**이 없고, 메모 항목 안에 칸막이 글자(`§`)가 들어가면 다음 대화에서 메모가 깨집니다.
  5. 과거 대화를 찾을 때(`session_search`) 파일 이름(`config.toml`)이나 하이픈(`deepseek-v4`)이 들어간 단어를 넣으면 검색 문법 오류가 나서 찾지 못합니다.

## 2. 왜 이 정도로만 하는가 (비목표)

| 하지 않는 것 | 이유 | 언제 하나 |
|---|---|---|
| 새로운 파이썬 파일(`memory_domain.py` 등)을 만들어 파일 개수 늘리기 | 기억 도구 파일(`memory_tool.py`)은 353줄로 이미 충분히 작습니다. 안에서 겹치는 코드만 합치면 한 파일 안에서 깔끔하게 정리되는데 굳이 파일을 쪼개는 것은 ‘원칙을 위한 원칙(안티패턴)’이며 21번에서 완성한 구조를 흔듭니다 | 하지 않음 (기존 31개 파일 구조 유지) |
| 아무 곳에서도 부르지 않는 검사용 함수 만들기 | 실제 대화 흐름에서 쓰이지 않고 시험 코드에서만 부르는 함수를 만드는 것은 불필요한 군더더기입니다 | 하지 않음 |
| 무거운 외부 검색 엔진(벡터 DB·임베딩 모델) 붙이기 | 개인용 메모장은 2,200자·1,375자로 작아서 한눈에 다 읽을 수 있고, 과거 대화 찾기는 내장 검색(SQLite FTS5)의 문법 오류만 고쳐도 충분합니다 | 기억 용량을 수만 자 이상으로 늘리는 별도 확장 프로젝트를 할 때 |
| 대화 도중 메모가 바뀔 때마다 맨 앞 안내서(시스템 프롬프트) 다시 고쳐 쓰기 | 안내서를 대화 도중에 바꾸면 AI 서비스의 앞부분 재사용 할인(Prefix Cache)이 깨집니다. 대신 AI가 언제든 최신 메모 목록을 읽어볼 수 있는 `list` 동작을 주는 편이 비용과 최신성을 모두 지키는 길입니다 | 바꾸지 않음 (불변 원칙 1번) |

## 3. 성공 판단 기준과 검증할 가정 목록 (A~H)

마감(050단계) 시 종합보고서(`결과정리및리뷰.md`)에서 하나씩 「이뤘다 / 못 이뤘다 / 바뀌었다」로 대조할 8개 가정입니다.

| 번호 | 검증할 가정 (Acceptance Hypotheses) |
|:---:|---|
| **A** | 새로운 소스 파일을 단 하나도 늘리지 않고(31개 파이썬 파일 유지), `memory_tool.py`와 `ledger_domain.py` 내부 통합만으로 모든 파일이 800줄 이하를 유지한다 |
| **B** | 메모 바꾸기(`replace`)나 지우기(`remove`)에서 찾을 글이 여러 항목에 부분 포함되더라도, 그중 문장 전체가 정확히 일치하는 항목이 있으면 거절하지 않고 그 항목을 정확히 찾아 고치거나 지운다 |
| **C** | 메모 추가(`add`)나 바꾸기(`replace`)에 칸막이 글자(`§`), 허용되지 않은 제어문자, 안내서 구획선 위조(`══════`), 또는 다른 항목과 똑같은 중복 내용이 들어오면 파일에 적지 않고 거절한다 |
| **D** | 메모 파일에 실제로 저장하는 단계가 실패하면 프로그램이 들고 있는 인메모리 항목 목록(`memory_entries`, `user_entries`)도 바뀌지 않고 원래 상태를 그대로 유지한다 |
| **E** | 이미 존재하는 메모 파일을 읽다가 오류(권한·인코딩 깨짐 등)가 나면 빈 메모장으로 덮어쓰지 않고 쓰기 요청을 막아 기존 파일을 보호하며, 세션 도중 사람이 밖에서 메모 파일을 직접 고치면 다음 기억 동작 때 그 변경을 먼저 읽어 들여 덮어쓰지 않는다 (단, 안내서 사본은 그대로 유지한다) |
| **F** | `memory` 도구의 `list` 동작을 부르면 파일이나 안내서 사본을 건드리지 않고 현재 항목 목록과 사용량(`usage`, `entry_count`)을 그대로 돌려주며, `MemoryStorePort` 약속을 통해 가짜 기억 저장소로도 도구를 시험할 수 있다 |
| **G** | 과거 대화 찾기(`session_search`)에 일반 단어(`error log`)를 넣으면 기존과 똑같이 동작하고, 하이픈(`-`), 점(`.`), 슬래시(`/`), 홀수 따옴표(`"`), 콜론(`:`)이 섞인 검색어를 넣어도 문법 오류 없이 안전하게 검색된다 |
| **H** | 한가운데(`kernel/`) 파일들은 단 한 줄도 바뀌지 않으며, 기존의 모든 시험(1,201개)은 한 줄도 고치지 않고 100% 통과하고 파이썬 3.12에서도 정상으로 켜진다 |
