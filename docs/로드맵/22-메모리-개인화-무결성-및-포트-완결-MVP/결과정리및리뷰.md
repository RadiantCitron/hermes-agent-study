## 2. 단계별 상세 (010~050, Why 중심 서술)

### 010단계: `MemoryStore` 내부구조 통합과 무결성 강화 (`664baba`)
- **Why**: 기존 `MemoryStore`(353줄)는 `add`, `replace`, `remove` 각 메서드마다 검증과 파일 읽기·쓰기가 흩어져 있었고, 부분 문자열이 겹칠 때 완전 일치하는 항목이 있어도 모호하다고 거절되는 Substring Shadowing(L-1), 디스크 쓰기 전에 인메모리 목록을 먼저 갱신하여 쓰기 실패 시 상태가 어긋나는 Split-Brain 및 읽기 실패 시 빈 파일로 덮어써 기존 기억이 증발하는 결함(L-2), `"§"` 구분자나 헤더 구분선 위조를 허용하는 파싱 오염 결함(L-3)이 존재했다.
- **What**:
  - `memory_tool.py`를 외부 파일로 분리하지 않고 모듈 내부에서 단일 매칭 관문(`_resolve_entry_index`)으로 완전 일치(`e == old_text`) 항목을 최우선 선택하도록 통합.
  - Write-First 원자적 커밋 함수(`_commit_entries`)를 도입하여 임시 파일 작성 및 `os.replace` 원자적 교체가 100% 성공한 직후에만 인메모리 목록(`memory_entries`, `user_entries`)과 SHA-256 해시를 갱신하도록 개편.

## 5. 미흡한 부분

1. **다중 프로세스 동시 파일 쓰기 분산 락 미구현**:
   - 현재 구현은 단일 CLI 인스턴스 전제로 `tempfile` 생성 및 `os.replace` 원자적 교체에 의존한다. 동일한 메모리 파일(`~/.hermes/memories/memory.txt`)을 서로 다른 프로세스나 터미널에서 동시에 마이크로초 단위로 경합하며 수정할 경우, 마지막에 교체된 파일 내용이 남게 된다. 완벽한 다중 프로세스 정합성을 위해서는 OS 파일 락(`fcntl.flock`) 또는 SQLite 기반 공유 원장으로의 확장이 장기적으로 고려될 수 있다.
2. **하드웨어 전원 강제 차단 스모크 시험 미실시**:
   - `_commit_entries`에서 `os.fsync` 및 `os.replace`를 호출하여 OS 커널에 플러시를 위임하나, 물리적 전원 강제 차단 상황을 모의하는 하드웨어 폴트 주입 시험은 자동 테스트에 포함되지 않았다 (OS 파일시스템의 저널링 성질에 의존).
3. **AI 모델의 기억 선별 판단 품질**:
   - 프로그램 코드는 글자 수 제한, 포맷 검증, 트랜잭션 무결성만을 보장할 뿐, 사용자의 어떤 발언이 장기 기억에 저장할 가치가 있는지를 판단하는 지능 자체는 프롬프트와 LLM 모델의 판단에 전적으로 의존한다.

## 6. 새로 발견한 부분

1. **단 3줄의 순수 일치 확인이 복잡한 파서를 압도함**:
   - Substring Shadowing 문제를 해결하기 위해 형태소 분석기나 퍼지 매칭(Fuzzy Matching)을 도입할 필요 없이, 부분 일치 항목들 중 `e == old_text`인 항목이 단 하나 존재하는지만 우선 확인하는 단 3줄의 조건문으로 완벽하게 해결할 수 있음을 입증하였다.
2. **Write-First 트랜잭션과 Fail-Closed 잠금의 상호 보완성**:
   - 디스크 쓰기 성공 후에만 인메모리를 갱신하는 Write-First 트랜잭션과, 읽기 실패 시 쓰기 권한을 잠그는 Fail-Closed 정책이 결합될 때 비로소 덮어쓰기 증발 및 상태 불일치 사고가 100% 원천 차단됨을 확인하였다.
3. **FTS5 토큰 안전화에서 평문 원형 보존의 중요성**:
   - SQLite FTS5 검색 쿼리에서 모든 단어를 무조건 따옴표로 감싸면 접두사 검색(`*`)이나 공백 분할 검색의 유연성이 저하되고 기존 하위 호환 단언(`test_ledger_domain.py:159`)이 깨진다. 알파벳·숫자·언더스코어로 이루어진 평문 토큰은 원형 그대로 두고, 특수문자와 예약어만 선별적으로 감싸는 방식이 안전성과 호환성을 동시에 만족하는 최선의 해법임을 확인하였다.

## 7. 트러블슈팅과 교훈

1. **010 단계 동일 내용 치환 시 조기 반환(`early return`)**:
   - `replace` 호출 시 `new_text`가 `old_text`와 완전히 동일한 경우, 불필요한 디스크 I/O를 수행하지 않고 조기 반환하도록 처리함으로써 동일 항목 중복 검사 오류를 방지하고 성능을 최적화하였다.
2. **020 단계 스키마 Enum 확장 시 필수 필드 규칙 준수**:
   - `MEMORY_SCHEMA`에 `action="list"`를 추가할 때, `text`, `old_text` 등이 필수 필드(`required`)에 묶여 있으면 `list` 호출 시 유효성 검증 실패가 발생할 수 있으므로, 필수 속성은 `action`만으로 유지하고 각 액션별 파라미터 유효성 검증은 `MemoryStore` 내부 관문에서 엄격히 수행하도록 설계하였다.
3. **030 단계 도구 포트 시그니처 바인딩의 미니멀리즘**:
   - `MemoryStorePort` 정의 시 런타임에 디스패처 및 코어가 실제로 호출하는 6대 공개 메서드(`load_from_disk`, `add`, `replace`, `remove`, `list_entries`, `format_for_system_prompt`)만을 프로토콜 계약으로 잠그고, 인프라 내부 헬퍼(`_commit_entries` 등)는 비공개로 은닉하여 구현 자유도를 보장하였다.

  - 향후 신규 기능이나 도구가 추가되더라도 `src/hermes_core/kernel/` 디렉터리는 불변을 유지해야 하며, 모든 도구는 `tools/ports.py`의 프로토콜 계약을 통해 결합되어야 한다.
  - 단일 파일 800줄 상한선(`test_scenario_r21_file_size_limits`)과 6대 순수 도메인 모듈의 인프라 무참조 원칙은 항상 영구 불변식으로 유지되어야 한다.
