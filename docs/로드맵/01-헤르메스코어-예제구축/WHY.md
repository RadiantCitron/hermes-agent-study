# [WHY] 01-헤르메스코어-예제구축 — 왜 이 로드맵을, 왜 이 정도로만 하는가

> **성격**: 이 로드맵의 의도를 적은 문서다 ([ROADMAP_정책 §3-2](../ROADMAP_정책.md)).  
> **사후 작성 (2026-10-29)**: 01번은 `WHY.md`를 두는 규칙이 생기기 전에 마감되었다. 이 문서는 마감 후에 [ROADMAP.md](ROADMAP.md)(마스터 설계도), [ADR-0001](../../adr/0001-src_레이아웃_채택.md), [대시보드](README.md)의 결정 표, [결과정리및리뷰.md](결과정리및리뷰.md)에 **이미 적혀 있는 내용만** 모아 재구성했다. 착수 전에 쓴 의도의 원본이 아니며, 당시 기록에 없는 가정이나 판정은 새로 만들지 않았다.

---

## 1. 왜 지금 이 로드맵인가

이 레포는 Hermes Agent 같은 AI 코딩 에이전트가 어떻게 돌아가는지 연구하고, 그 원리를 직접 만들어 보며 배우는 곳이다. 그런데 원본(`hermes-agent`)은 데스크톱 앱, 여러 메신저 봇 연결, 수백 개의 작은 모듈이 얽힌 큰 시스템이라, 「에이전트의 핵심이 무엇인가」를 읽기만 해서는 붙잡기 어렵다. 직접 만들어 돌려 보지 않으면 **이 시스템이 무엇을 하는지 모르는 채로** 남는다.

그래서 01번은 원본에서 에이전트의 뼈대 세 가지만 뽑아 작게 직접 만든다. ([ROADMAP.md §1](ROADMAP.md))

1. **시스템 지시문 조립**: 에이전트의 정체성, 프로젝트 지시 파일(`AGENTS.md` 등), 기억을 한 덩어리 지시문으로 엮는 방식.
2. **크기가 정해진 기억**: 에이전트가 스스로 정리하는, 글자 수 상한이 있는 영구 기억.
3. **대화 기록 보관소**: 대화와 도구 실행 결과를 검색 가능하게 남기는 저장소.

이 로드맵이 없으면 이후 모든 로드맵(안전 강화, 도구 추가, 모델 연결)이 올라설 「돌아가는 코어」 자체가 없다.

## 2. 왜 이 정도로만 하는가

[ROADMAP.md §1·§2](ROADMAP.md)에 적힌 범위 제한이다.

| 하지 않는 것 | 이유 (기록에 있는 것) | 이후 |
|---|---|---|
| 데스크톱 앱, 메신저 봇 연결, 게이트웨이 등 플랫폼 인프라 | 목적이 「에이전트의 핵심 메커니즘 학습」이고, 부가 기능은 핵심을 가린다. 원본을 줄여 복사하는 것(Cargo Cult)이 아니라 정제해서 만드는 것이 목표다 | 해당 없음(기록 없음) |
| 실제 언어 모델 연결 | 키·비용·네트워크 실패에 시험이 흔들리지 않게 한다. 가짜 모델(`MockLLMClient`)로 도구 호출 시나리오와 반복 루프를 자동 검증한다 ([ROADMAP.md §4](ROADMAP.md) 위험 1) | [로드맵 04](../04-실제모델-연결-MVP/WHY.md)에서 연결 |
| 코드 분량 | 「핵심 메커니즘 정제, 총 1,500줄 내외」를 목표로 둠 ([ROADMAP.md §2](ROADMAP.md)). 결과는 약 1,300줄 ([결과문서 §2](결과정리및리뷰.md)) | — |
| 파일 읽기·쓰기 도구, 터미널 안전 장치 | 01의 범위 밖. 01 결과문서는 다음 로드맵으로 파일 조작 도구를 꼽았으나, 마감 후 점검에서 안전 공백이 확인되어 [02](../02-코어-안전강화/WHY.md)가 먼저 되었다 ([ADR-0002](../../adr/0002-코어_안전_강화_범위와_터미널_가드_방식.md) §1) | 02(안전 강화), 03(파일 도구) |

## 3. 왜 이 순서, 왜 이 단계 수인가

다섯 단계다. ([대시보드 §2](README.md))

| 순서 | 단계 | 하는 일 |
|---|---|---|
| 010 | 패키지 골격 | 코드를 담을 자리와 상태 폴더의 규칙부터 정한다 |
| 020 | 지시문 조립 | 뼈대 ① |
| 030 | 바운디드 기억 | 뼈대 ② |
| 040 | 대화 기록 보관소 | 뼈대 ③ |
| 050 | 반복 루프, 도구 통로, 명령줄 화면 | 앞의 부품을 하나로 조립 |

- 이 순서에 대한 **명시된 근거는 기록에 없다**(미확인). 앞 세 부품이 서로 독립이고 마지막 단계가 그 셋을 쓰는 구조라서, 조립을 마지막에 둔 것으로 읽힌다(해석).
- 단계 수가 왜 5개인지도 기록에 적혀 있지 않다(미확인). 뼈대 3개에 골격과 조립을 더한 수와 같다.

## 4. 왜 이 방식을 택하고 무엇을 배척했나

([ADR-0001](../../adr/0001-src_레이아웃_채택.md), [대시보드 §4](README.md), [ROADMAP.md §1·§2](ROADMAP.md))

| 선택 | 배척한 것 | 이유 (기록에 있는 것) |
|---|---|---|
| 코드를 `src/` 아래 한 패키지(`hermes_core`)로 격리 (D-01, ADR-0001) | 코드를 레포 루트나 다른 곳에 둠 | 원본·문서·스크립트가 한 레포에 있어 이름 충돌, 의존성 충돌, 패키지 경계 모호함 위험 |
| 원본의 핵심을 정제해 다시 구성, 원본과의 개념 대조표 제공 (D-02) | 원본을 줄여서 그대로 복사 | 복사로는 원리를 배우기 어렵다 |
| 모델 연결 부분은 인터페이스 + 가짜 모델 (D-03) | 처음부터 실제 모델 연결 | 키 없이도 전부 자동 검증 가능하게 |
| 원본의 거대한 중심 클래스를 반복 루프·도구 통로·기록 보관소로 분리 | 하나의 큰 클래스 | 책임을 나누어 이후 수정을 쉽게 ([결과문서 §3](결과정리및리뷰.md)) |
| 모든 도구 호출이 지나는 문이 하나인 도구 통로 | 전역 함수로 도구를 직접 호출 | 이후 보안 장치를 한 곳에 달 수 있게 ([결과문서 §3](결과정리및리뷰.md)) |
| 시험 속의 상태 보관소는 메모리 위 데이터베이스 | 파일 데이터베이스를 시험에서도 사용 | 시험끼리 상태가 섞이거나 잠금이 충돌하는 것을 막기 위해 ([ROADMAP.md §4](ROADMAP.md) 위험 3) |

## 5. 성공 판단 기준과 당시의 위험 가정

01에는 `WHY.md의 가정 목록`이 없었다. 아래는 [ROADMAP.md](ROADMAP.md)에 적혀 있던 목표와 사전 점검(Pre-Mortem)을 가정 형태로 옮긴 것이다. **이 문서에서 새로 판정하지 않으며**, 결과는 [결과문서](결과정리및리뷰.md)를 따른다.

**성공 기준 (ROADMAP §1·§5)**: 뼈대 세 가지가 동작하고, 가짜 모델로 「사용자 입력 → 도구 실행(기억·터미널) → 최종 답변 → 대화 기록 저장」 전체가 자동으로 검증된다.

| 번호 | 당시의 위험 가정 (ROADMAP §4) | 틀렸다면 | 당시 방어책 |
|---|---|---|---|
| R1 | 실제 모델 없이도 도구 호출과 반복 루프를 자동 검증할 수 있다 | 키·네트워크 없이 시험이 돌지 않는다 | 가짜 모델 내장 |
| R2 | 기억 파일 형식(`§` 구분자)과 크기 상한을 안전하게 다룰 수 있다 | 기억이 깨지거나 무한 반복 | 엄격한 파서, 초과 시 오류 |
| R3 | 시험을 병렬로 돌려도 데이터베이스 잠금 충돌이 없다 | 시험이 불안정해진다 | 세션별 연결 분리, 메모리 위 데이터베이스 |

결과문서는 19개 시험이 모두 통과했다고 적는다([결과문서 §2](결과정리및리뷰.md)).

## 6. 알려진 위험과 아직 확인하지 못한 것

- **안전 장치는 의도적으로 범위 밖이었다.** 01 마감 시점에 터미널 도구는 모델이 낸 명령을 셸로 그대로 실행했고, 도구 인자는 검증하지 않았다. 이는 마감 후 점검에서 확인되어 [로드맵 02](../02-코어-안전강화/WHY.md)로 이어졌다 ([ADR-0002](../../adr/0002-코어_안전_강화_범위와_터미널_가드_방식.md) §1).
- **실제 모델과의 호환**: 01은 가짜 모델로만 시험했다. 실제 모델이 보내는 형식은 이 시점에 미확인이었다(이후 04에서 다룸).
- **원본과의 대응 범위**: 원본 대조표는 만들었으나([결과문서 §3](결과정리및리뷰.md)) 원본 전체를 대조한 것은 아니다. 대조의 완전성은 미확인.
- **이 문서 자체의 한계**: 사후 재구성이라서, 3절의 순서·단계 수 근거처럼 당시 기록에 없는 이유는 「미확인」으로 남겼다.
