# [WHY] 04-실제모델-연결-MVP — 왜 이 로드맵을, 왜 이 정도로만 하는가

> **성격**: 이 로드맵의 의도를 적은 문서다 (ROADMAP_정책 §3-2). 마감 때 종합보고서(`결과정리및리뷰.md`, 마감 시 작성)가 이 문서의 「검증할 가정」을 하나씩 대조한다. 4단계 착수 후에는 본문을 고치지 않고 맨 끝 「변경 기록」에만 덧붙인다.

## 1. 왜 지금 이 로드맵인가

지금까지 만든 것은 「차」의 뼈대와 안전장치다. 핸들(대화를 이어 가는 반복), 기어(도구를 한 통로로 실행하는 장치), 좌석(기억과 대화 기록), 계기판(종료 사유와 경고)이 있고, 브레이크와 안전벨트에 해당하는 안전 규칙도 두 번의 로드맵으로 쌓았다. 시험도 211개가 모두 통과한다.

그런데 이 모든 것은 **연료가 연결되지 않은 채**, 정해진 대사를 읽는 가짜 모델로만 시험되었다. 사람이 이 시스템을 맡았을 때 가장 먼저 묻는 질문은 이렇다.

- *"진짜 모델이 붙어도 이 안전 규칙이 그대로 통하는가?"*
- *"실제 모델이 엉뚱한 요청을 하거나 통신이 끊기면 어떻게 되는가?"*
- *"나중에 문제가 생겼을 때, 그 모델이 정확히 무엇을 받고 무엇을 답했는지 볼 수 있는가?"*

세 질문에 지금은 「모른다」가 정직한 답이다. 이 로드맵은 새 기능을 크게 얹는 일이 아니라, **지금까지 쌓은 것이 실제로 달리는지 확인할 수 있는 최소한의 차를 만드는 일**이다. 라디오, 에어컨, 차체는 필요 없다. 시동이 걸리고 굴러가는지만 본다.

그리고 시동을 걸기 전에 한 가지를 짚어야 했다. 지금 상태로 진짜 모델을 켜면, 모델이 **이 레포의 비밀번호 파일(`.env`)과 깃(버전 관리) 설정 폴더를 읽고 고칠 수 있다.** 키가 모델의 입력으로 읽히면 모델 제공자의 서버와 우리의 대화 기록에 남는다. 연료를 붙이기 전에 연료통 뚜껑부터 잠가야 한다.

## 2. 왜 이 정도로만 하는가

이 로드맵이 **일부러 하지 않는 것**과 그 이유다.

| 하지 않는 것 | 이유 | 언제 하는가 |
|---|---|---|
| 서브에이전트(에이전트가 다른 에이전트에게 일을 맡기는 기능) | 진짜 모델 연결이 안정되기 전에 변수를 늘리면, 문제가 났을 때 원인이 연결인지 위임인지 구분할 수 없다. 원본의 같은 기능은 구현이 매우 커서 개념만 참고해야 한다. | 05번. 모델 연결 종합보고서에서 연결이 안정적이라고 확인된 뒤 |
| 실시간으로 글자가 흘러나오는 응답(스트리밍) | 한 번에 받는 방식이 훨씬 단순하고, 기록·시험이 쉽다. MVP의 목적은 「달리는지」이지 「매끄러운지」가 아니다. | 필요가 생겼을 때 별도 결정 |
| 파일 검색 도구 | 다른 주제(파일을 훑는 범위, 링크 처리)이고 모델 연결과 상관이 없다. | 별도 로드맵 |
| 운영체제 수준의 격리 상자(샌드박스) | 지금 모델이 쓰는 도구는 허용된 8개 프로그램과 작업 폴더 안의 파일뿐이라, 작업 폴더를 한정하고 비밀 파일을 막는 것으로 위험이 충분히 줄어든다. 컨테이너 등은 운영체제에 의존하게 만들어 이 레포가 목표로 하는 「순수 파이썬 코어」와 맞지 않는다. | 모델에게 쉘이나 파이썬 같은 강력한 도구를 줄 때 |
| 비밀 파일(`.env`)을 읽어 들이는 기능 | 편하지만 「비밀 파일을 여는 코드」를 우리가 만드는 셈이고, 모델이 쓰는 파일 도구와의 방어 경계가 흐려진다. 키는 사용자가 터미널에서 직접 넘겨주면 된다. | 필요가 커지면 별도 결정 |
| 여러 모델 제공자 지원, 자동 재시도, 대화가 길어졌을 때 요약 | 모두 「정상적으로 한 번 달리는지」를 확인한 뒤의 문제다. 한 번의 시도를 정직하게 보고하는 것으로 충분하다. | 필요가 생겼을 때 |
| 실행 기록을 레포(깃)에 올리기 | 기록에는 모델과 주고받은 모든 내용이 들어가 민감하다. 기록 보관 방식은 별도 판단이 필요하다. | 별도 결정 |

한마디로, **「한 번 실제로 달려 본다」와 「그 기록을 남긴다」까지만** 한다. 그 이상은 달려 보고 나서 필요한지 판단한다.

## 3. 왜 이 순서, 왜 이 단계 수인가

단계는 여섯 개이고, **위험이 큰 것부터 막고 연료는 맨 마지막에** 붙인다.

| 순서 | 하는 일 | 왜 이 자리인가 |
|---|---|---|
| 1 | 모델이 일할 전용 작업 폴더를 정하고 비밀 파일·깃 폴더를 막는다 | 연료를 붙이기 전에 가장 큰 구멍부터 닫는다. 03번에서 「쓰기 금지 정책을 쓰기 도구보다 먼저」 만든 것과 같은 원칙이다. |
| 2 | 진짜 모델과 통신하는 부분을 만든다 | 구멍이 닫힌 뒤에야 연결해도 안전하다. 통신은 가짜 통신 장치로 시험하므로 이 단계까지 진짜 키가 필요 없다. |
| 3 | 모델과 주고받은 내용·비용·시간을 기록하고, 통신이 실패해도 멈추지 않게 한다 | 나중에 문제를 되짚으려면 처음부터 기록이 남아야 한다. 실패 처리도 연결이 생긴 이 시점에 필요하다. |
| 4 | 사용자가 명령으로 실제 모드를 켜게 한다 | 통신과 기록이 준비된 뒤에 사용자 접점을 만든다. |
| 5 | 가짜 통신으로 「모델이 도구를 부르고 → 결과를 받고 → 답한다」 전체를 한 번에 시험한다 | 부품별 시험이 아니라 합쳐졌을 때도 되는지 확인한다. 키가 새어 나가지 않았는지도 여기서 본다. |
| 6 | 진짜 키로 딱 한 번 달려 본다 | 비용과 재현성 때문에 가장 마지막에, 그리고 사용자가 지시할 때만 한다. |

여섯 단계는 03번과 같은 규모다. 더 쪼개면 단계가 형식에 그치고, 더 합치면 사고가 났을 때 원인을 찾기 어렵다.

## 4. 왜 이 방식을 택하고 무엇을 배척했나

| 선택 | 배척한 대안 | 이유 |
|---|---|---|
| 전용 작업 폴더(`.hermes/workspace`) | 레포 루트에서 그대로 실행 | 루트에서는 비밀 파일과 깃 설정을 읽고 고칠 수 있다. |
| 비밀 파일과 깃 폴더를 **한 곳**에서 한 번 더 막는다 | 곳곳에 검사를 흩뿌림 / 작업 폴더 격리만 믿음 | 작업 폴더가 바뀌는 경우의 안전망이 필요하지만, 검사를 여러 곳에 두면 어긋난다. |
| 키는 터미널 환경변수로만 전달 | 비밀 파일을 읽는 기능 추가 | 위 2절 참조. |
| 모델과 주고받은 내용을 기존 대화 기록 데이터베이스의 새 표에 남김 | 별도 텍스트 파일로 저장 | 같은 데이터베이스면 대화 기록과 이어서 되짚을 수 있다. |
| 진짜 키는 맨 마지막에 한 번 | 개발 내내 진짜 키 사용 | 비용, 재현성, 키 노출 위험. |
| 통신 실패는 「실패했다」고 정직하게 보고 | 자동 재시도로 감춤 | 처음에는 무슨 일이 일어나는지 그대로 보는 것이 포스트모템에 낫다. |

## 5. 성공 판단 기준과 검증할 가정

**성공 기준**: 가짜 통신으로 모든 시험이 통과하고, 사용자가 지시하면 진짜 키로 도구를 한 번 쓰고 돌아오는 한 번의 대화가 성공하며, 그 대화의 요청·응답·비용이 기록에 남아 있고, 그 과정에서 키가 어디에도 남지 않는다.

마감 때 종합보고서가 아래 가정을 하나씩 「맞았다 / 틀렸다 / 바뀌었다」로 대조한다.

| 번호 | 가정 | 틀렸다면 |
|---|---|---|
| **A** | 모델과 닿는 곳이 하나뿐이라, 통신 부분만 새로 만들면 기존 코드는 거의 건드리지 않아도 된다. | 반복·기록 쪽 수정 범위가 커진다. |
| **B** | 전용 작업 폴더와 비밀·깃 폴더 차단만으로 키와 깃 설정이 모델에게 노출되지 않는다. | 격리 방식을 다시 정해야 하고 샌드박스 도입이 앞당겨진다. |
| **C** | 이 모델이 도구를 부를 때 보내는 형식이 지금의 해석 방식과 호환된다. (**미확인**: 한 번도 본 적이 없다.) | 변환 계층이 필요하고 기존 해석 방식을 손봐야 한다. |
| **D** | 호출 기록만으로 나중에 한 대화를 처음부터 끝까지 재구성할 수 있다. | 기록 항목이 부족한 것이므로 보강한다. |
| **E** | 스모크 한 번의 비용은 사실상 무시할 수준이다. (공개 단가로 계산하면 수천 토큰에 1센트 미만.) | 비용 상한을 별도로 설계한다. |
| **F** | 통신이 실패(제한, 시간 초과, 이상한 응답)해도 프로그램이 죽지 않고 실패로 기록된다. | 실패 처리 범위를 넓힌다. |
| **G** | 같은 코어가 가짜 모델과 진짜 모델 양쪽에서 같은 규칙(도구 통로, 쓰기 금지, 원장)으로 동작한다. | 두 모드의 차이를 정리해야 한다. |

## 6. 알려진 위험과 아직 확인하지 못한 것

- **키의 유효성**: 사용자의 비밀 파일을 열지 않았으므로 확인하지 못했다. (키 변수 이름 `OPENROUTER_API_KEY`는 사용자가 확인했다. 아래 변경 기록 참조.)
- **진짜 모델이 도구를 부를 때 보내는 인자의 실제 모양**: 가정 C. 한 번도 본 적이 없다.
- **제공자의 오류 형식(제한 등)의 세부**: 가짜 통신으로 우리가 상상한 오류를 시험하지만 실제 오류와 같은지는 모른다.
- **모델이 작업 폴더 안에서 만들 수 있는 파일의 양**: 크기 상한만 있고 개수 상한은 없다(03번의 알려진 한계). 작업 폴더가 `.hermes/` 안이라 레포의 코드를 건드리지는 못하지만 디스크를 채울 수는 있다.
- **이 MVP로는 레포의 코드를 에이전트가 직접 고치는 일을 하지 못한다.** 일부러 감수한 제약이다.

## 변경 기록

(4단계 착수 후 계획이 바뀌면 여기에 날짜와 이유를 덧붙인다.)

- **2026-10-28 (4단계 착수 전)**: 사용자가 키 변수 이름이 `OPENROUTER_API_KEY`가 맞다고 확인했다. 이에 따라 6절의 「키 변수 이름」 미확인 항목을 본문에서 정정했다. 착수 전의 정정이라 본문을 고쳤고, 이후 변경은 이 절에만 덧붙인다. 가정 A~G는 바뀌지 않았다.
