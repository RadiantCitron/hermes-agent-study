## 1. 왜 지금 이 로드맵인가

11번 로드맵으로 사람은 `/rollback` 한 번으로 에이전트가 바꾼 파일을 직전 요청 전 모습으로 돌릴 수 있게 됐다. 그런데 실제 모델로 돌려 보니 되돌린 직후 이런 일이 일어났다.

> 사람이 「HELLO로 바꾼 것」을 되돌린 뒤, 「파일을 읽어서 보여줘」라고 **읽기만** 부탁했다. 모델은 「바꿨다고 기억하는데 파일은 그대로다. 반영이 늦었나 보다」라고 생각하고 **스스로 다시 HELLO로 고쳤다.** 사람이 되돌린 것이 사람 모르게 다시 뒤집혔다.

화면에는 「모델은 이 되돌림을 모릅니다. 다시 읽으라고 알려 주세요」라는 안내가 떴지만 막지 못했다. 사람이 안내를 보고도 읽기만 부탁했기 때문이다.

사람이 묻는 질문은 이렇다.

- *"되돌렸는데 에이전트가 몰래 다시 고치면, 되돌리기가 무슨 소용인가?"*
- *"에이전트가 되돌린 사실을 알게 하려면 내가 매번 설명해야 하는가?"*
- *"에이전트에게 무엇이 전달됐는지 나중에 확인할 수 있는가?"*

지금은 첫 질문에 「막을 방법이 없다」, 둘째에 「그렇다, 그래도 소용없을 수 있다」, 셋째에 「전달된 것이 없다」가 답이다. 이 로드맵은 **「되돌린 사실을 사람이 다음에 말할 때 에이전트에게 자동으로 함께 전하고, 무엇을 전했는지 기록에 남긴다」** 하나만 만든다.

## 2. 왜 이 정도로만 하는가

이 로드맵이 **일부러 하지 않는 것**과 그 이유다.

| 하지 않는 것 | 이유 | 언제 하는가 |
|---|---|---|
| 되돌린 요청의 대화를 기록에서 지우기 (원본 방식) | 되돌리는 요청이 대화 중간에 있을 수 있어서, 뒤의 대화를 남긴 채 중간을 도려내야 한다. 어느 대화가 어느 요청인지 잇는 표시도 없다. 과거 대화를 바꾸면 「앞부분은 바꾸지 않는다」는 규칙도 깨진다 | 알림만으로는 모델이 계속 다시 고친다는 증거가 쌓일 때 |
| 되돌리자마자 에이전트를 불러 알리기 | 사람이 원하지 않은 응답과 비용이 생긴다. 되돌리기는 사람의 명령이고 에이전트를 부르지 않는다는 11번 결정을 지킨다 | 바꾸지 않는다 |
| 대화를 요약(압축)한 뒤에도 알림을 지키기 | 알림은 바로 다음 요청에서 효과를 내면 된다. 오래 지키려면 요약 규칙을 바꿔야 한다 | 요약 뒤에 다시 고치는 일이 관찰될 때 |
| 처리 중 Ctrl+C 처리, 대화가 끝난 이유 기록 | 다른 문제다. 중단된 요청의 짝 맞추기, 남은 기록 처리, 종료 사유 기록이 필요하다 | 13번 후보 「중단·종료 정합」 |
| 다른 대화에서 한 되돌리기 알리기 | 대화가 끝나면 기억도 함께 끝난다 | 대화를 이어 여는 기능이 생길 때 |
| 실제 터미널 창을 띄우는 새 시험 | 알림은 순수한 글 만들기와 넘기기라서 터미널 경계에서만 드러나는 동작이 없다(계획 015의 기준) | 해당 없음 |

**한마디로**: 지우지도, 바로 부르지도 않는다. 사람이 다음에 말할 때 「사람이 이것을 일부러 되돌렸다」를 함께 보낸다.

## 3. 왜 이 순서, 왜 이 단계 수인가

| 순서 | 하는 일 | 왜 이 자리인가 |
|---|---|---|
| 0 | 계획 015(시험 코드 정리)를 먼저 끝낸다 | 같은 시험 파일(되돌리기 CLI 시험)을 015가 먼저 정리한다. 두 번 손대지 않는다 |
| 010 | 알림 글을 만드는 부분 | 무엇을 보낼지가 먼저 정해져야 언제 보낼지를 시험할 수 있다. 다른 부분에 기대지 않는 순수한 일이라 따로 확인하기 쉽다 |
| 020 | CLI에 잇기(쌓아 두기, 다음 메시지에 붙이기, 끝낼 때 버리기, 화면 안내) | 사람이 실제로 쓰는 길이다. 010의 결과를 그대로 쓴다 |
| 030 | 통합 확인과 작동원리 문서 갱신 | 작동원리 01편에 「모델은 되돌림을 모름」이라고 적혀 있다. 동작이 바뀌면 문서도 같이 바뀌어야 한다 |
| 040 | 실제 모델로 다시 돌려 보기와 마감 | 이 로드맵은 실제 모델의 행동에서 시작했다. 같은 상황을 같은 모델로 다시 돌려 봐야 끝났다고 말할 수 있다 |

## 4. 왜 이 방식을 택하고 무엇을 배척했나

| 선택 | 배척한 대안 | 이유 |
|---|---|---|
| 다음 사람 메시지 앞에 알림 붙이기 | 대화 중간에 「시스템」 역할 글 넣기 | 기록에는 남지 않는데 모델에게는 가는 글이 생긴다. 프로그램 규칙도 금지한다 |
| 〃 | 도구 결과로 알리기 | 도구 결과는 에이전트가 부른 도구의 답이다. 에이전트가 부르지 않은 사건을 실을 자리가 없다 |
| 알림을 기록에도 그대로 남기기 | 보낼 때만 붙이고 기록에는 사람 말만 남기기(원본 방식) | 에이전트가 실제로 받은 글과 기록이 달라진다. 「보이지 않으면 믿을 수 없다」에 맞지 않는다 |
| 건너뛴 파일도 알림에 넣기 | 되돌린 파일만 알리기 | 건너뛴 파일에는 에이전트의 변경이 그대로 남아 있다. 알리지 않으면 에이전트가 반대로 오판한다 |
| 실제로 되돌린 것이 있을 때만 알리기 | `/rollback`을 칠 때마다 알리기 | 파일이 그대로면 에이전트의 기억과 어긋날 것이 없다 |

## 5. 성공 판단 기준과 검증할 가정

**성공 기준**: 11번 060과 같은 상황(만들기 → 고치기 → 되돌리기 → 「읽어서 보여줘」)을 같은 모델로 3번 돌려서, 되돌린 뒤 읽기 요청에 에이전트가 **파일을 고치는 도구를 한 번도 부르지 않는다.** 그리고 에이전트에게 보낸 알림이 기록에 그대로 남아 있다.

| 번호 | 가정 | 틀렸다면 |
|---|---|---|
| **A** | 알림을 받으면 060에서 본 「다시 고치기」가 멈춘다. (**미확인**: 모델 1종) | 알림 문구를 바꿔 다시 시험한다. 그래도 안 되면 「대화에서 지우기」를 후속 후보로 올린다 |
| **B** | 사람 메시지 앞에 알림을 붙여도 에이전트가 사람의 실제 요청을 흐리지 않는다. 알림을 지시로 오해해 엉뚱한 일(예: 시키지 않은 다시 읽기)을 하지 않는다 | 알림 위치를 메시지 뒤로 옮기거나 문구를 바꾼다 |
| **C** | 건너뛴 파일을 함께 알리면 「되돌렸는데 왜 그대로지」 같은 오판이 줄어든다 | 건너뛴 파일 안내 문구를 고친다 |
| **D** | 알림이 대화 요약(압축)의 표지와 섞이지 않는다 | 표지를 바꾼다(시험으로 확인) |
| **E** | 요약 뒤 오래된 알림이 흐려져도 실제 피해는 작다. 바로 다음 요청에서 이미 효과를 냈기 때문이다 | 요약 뒤 보존을 후속 후보로 올린다 |
| **F** | 알림 길이(경로 수 상한)가 실제 사용에서 문맥을 크게 쓰지 않는다 | 상한을 줄인다 |

## 6. 알려진 위험과 아직 확인하지 못한 것

- **되돌린 요청의 대화는 기록에 그대로 남는다.** 에이전트는 「HELLO로 바꿨습니다」와 「사람이 되돌렸다」를 함께 본다. 알림을 무시하는 모델에는 효과가 없다(가정 A).
- 되돌린 뒤 사람이 아무 말 없이 끝내면 알림은 보내지지 않는다. 되돌린 사실은 기록 장부에 남는다.
- 제공자나 다른 모델이 알림을 어떻게 받아들이는지는 **미확인**이다. 실제로 돌려 보는 모델은 1종이다.
