# [구현지시서 060] 실제 키 스모크 1회 (사용자 지시가 있을 때만 실행)

> **상위 대시보드**: [06-README.md](../README.md)  
> **선행 조건**: 050 단계 완료 (`Done`) **그리고 사용자의 명시적 실행 지시**  
> **근거**: [WHY.md](../WHY.md) 가정 B·D·G, [ADR-0006](../../../adr/0006-스킬_시스템_MVP_범위와_로딩_방식.md) §2-2  
> **성격**: 코드를 바꾸지 않는 **실행·검증 단계**다. 지시서는 절차와 기대 결과만 정한다. 실행 결과는 대시보드와 종합보고서에 기록한다.

---

## 1. 목적

가짜 통신으로 모든 시험이 통과한 상태에서, **실제 모델이 안내문만으로 스스로 스킬 목록을 보고 본문을 읽어 그 절차대로 답하는지**, 그 과정에서 스킬 폴더가 변하지 않고 키가 어디에도 남지 않는지를 확인한다. 가정 B(안내문만으로 스킬을 부름)는 가짜 모델로는 검증할 수 없어 이 단계에서만 판정한다.

## 2. 사전 조건 (사용자가 확인)

1. 키 변수 이름은 `OPENROUTER_API_KEY`다. 사용자의 셸에서 이 이름으로 내보냈는지만 확인한다. 에이전트는 `.env`를 열지 않는다.
2. **별도 터미널**(에이전트 세션이 아닌 사용자의 터미널)에서 직접 환경변수로 키를 내보낸다. **키는 에이전트와의 대화·명령줄·프롬프트에 절대 쓰지 않는다** ([AGENTS.md](../../../../AGENTS.md) §3).
3. `pytest tests -q`가 모두 통과한다.
4. **임시 상태 폴더**: 실제 `.hermes`를 쓰지 않고 레포 밖 임시 폴더(세션 scratchpad 등)를 `HERMES_HOME`으로 쓴다. 에이전트가 그 경로를 사용자에게 알려 주며, 레포의 문서·대시보드에는 로컬 경로 대신 `<임시>`로 적는다([AGENTS.md](../../../../AGENTS.md) §3). 에이전트가 키가 없는 **가짜 스킬 파일만** 그 폴더에 만든다: `skills/release/SKILL.md` — 머리말 `name: release-procedure`, `description: Team release procedure for this project`, 본문은 모델이 사전 지식으로 알 수 없는 **고유 절차**(예: 「1) 브랜치 이름은 `rel-PELICAN`으로 만든다 2) 마지막에 `PELICAN-7`이라고 보고한다」). 이 마커가 답에 나오면 모델이 본문을 읽은 것이다.
5. 비용 상한: 질문 1~2턴, 호출 몇 회(목록·본문·최종). 공개 단가로 1센트 미만 예상(실제 청구는 확인하지 못함).

## 3. 절차

| 순서 | 동작 |
|---|---|
| 1 | 에이전트가 임시 `HERMES_HOME`에 위 가짜 스킬을 만들고, 만든 직후 스킬 폴더의 파일 해시를 기록 |
| 2 | **사용자가 별도 터미널에서 직접** 레포 루트에서 `HERMES_HOME=<임시 폴더> python -m hermes_core.cli` 실행. 에이전트는 이 실행을 대신하지 않는다 |
| 3 | 시작 안내에서 모드(실제), 모델, 작업 폴더를 확인 |
| 4 | 입력 1: `우리 팀의 릴리스 절차를 순서대로 알려줘.` (**「스킬」이라는 단어를 쓰지 않는다** — 안내문만으로 부르는지 보려는 것이다) |
| 5 | 응답을 확인하고 `exit` |
| 6 | 사용자가 결과를 확인하고 비밀을 뺀 출력을 에이전트에게 전달. 에이전트는 원장 조회(읽기 전용)와 기록 정리를 한다 |

실패(오류 종료, 스킬을 부르지 않음, 이상한 응답)하면 **자동으로 다시 시도하거나 코드·안내문을 고치지 않는다.** 원인을 기록하고 멈춰서 보고한다. 같은 스모크를 다시 하려면 사용자의 새 지시가 필요하다.

## 4. 기대 결과와 확인 항목

| # | 확인 | 기대 결과 |
|---|---|---|
| 1 | **가정 B**: 목록 조회 | 세션 `messages`에 `tool_name == "skills_list"`인 tool 행이 있고 그 내용에 `"success": true`와 `release-procedure`가 있다 |
| 2 | **가정 B**: 본문 읽기 | 앞 행보다 뒤에 `tool_name == "skill_view"`인 tool 행이 있고 내용에 `PELICAN-7`이 있다(본문을 실제로 받았다). 그 호출의 인자는 assistant 행의 `tool_calls` JSON에서 읽으며 `release-procedure` 또는 `release`다 |
| 2b | 안내문 외 경로 없음 | 첫 모델 호출의 `llm_calls.request_json`에 `PELICAN`이 **없다**(스킬 본문이 지시문에 들어가지 않았고, 모델은 도구로만 읽었다) |
| 3 | 절차 반영 | 최종 응답에 `PELICAN-7`(또는 본문의 고유 절차)이 나온다 |
| 4 | 모든 호출 정상 | `llm_calls`의 모든 행 `error_kind` NULL |
| 5 | **가정 D**: 헤드 | `sessions.system_prompt`에 `SKILLS_GUIDANCE`가 있고, 첫 호출과 마지막 호출의 `llm_calls.request_json` 속 첫 system 메시지가 동일 |
| 6 | 읽기 전용 | 스킬 폴더의 파일 해시와 `HERMES_HOME` 직하위 항목이 실행 전과 같다 |
| 7 | **키 미저장** | 키가 원장 덤프에 없다. **사용자가 별도 터미널에서** 키 값을 출력하지 않고 확인하고 결과(`True`/`False`)만 전달한다 |
| 8 | 비용 | `llm_calls` 토큰으로 계산한 비용이 1센트 미만 |
| 9 | 출력·로그 | 키 값이 화면·로그에 없다 |

## 5. 결과 기록

- 대시보드 실행 기록에 날짜, 지시 문구, 통과/실패, 호출 수, 도구 호출 순서, 토큰, 계산한 비용을 적는다.
- 확인 항목 1~3의 관찰을 **그대로** 종합보고서의 「목표와 결과」·「새로 발견한 부분」에 옮긴다. 모델이 스킬을 부르지 않았다면 가정 B는 「이번 1회 관찰에서는 틀렸다」로 적고, 지시문 인덱스 주입(후속 후보)을 근거와 함께 제안한다.
- **판정의 한계**: 표본이 1회이고 모델 응답은 매번 다를 수 있다. 성공해도 「안내문만으로 부른다」가 이 1회에서 확인된 것이지 보장이 아니며, 실패해도 우연일 수 있다. 종합보고서에 이 한계를 함께 적는다. 다시 해 보려면 사용자의 새 지시가 필요하다.
