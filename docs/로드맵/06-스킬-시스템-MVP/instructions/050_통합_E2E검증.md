## 1. 구현 내용 명세

1. **통합 E2E 시험** ([`test_agent_e2e.py`](../../../../tests/test_hermes_core/test_agent_e2e.py)에 추가): 기존 `r05_e2e_env` 픽스처(임시 `HERMES_HOME`, 실제 `state.db`, 기억 파일, 실제 디스패처), `OpenRouterClient`(가짜 키)와 `SequentialMockTransport`로 대화 전체를 재생한다. 코드 변경 없음(시험과 문서만).
   - **호출별 messages는 전송 요청에서 읽는다**: `json.loads(transport.captured_requests[i].content)["messages"]`. `MockLLMClient.call_history`는 에이전트가 이후 메시지를 덧붙이는 **같은 리스트 객체**를 참조해 호출 시점의 스냅샷이 아니므로(`agent.py`가 `messages`를 복사 없이 넘김) 순서 단언에 쓰지 않는다.
2. **전수 검사 도우미**: DB 전체(`messages`, `llm_calls`, `sessions`)를 직렬화해 가짜 키 문자열이 없음을 확인하는 기존 방식([`test_060_scenario_10_zero_leakage_in_db`](../../../../tests/test_hermes_core/test_agent_e2e.py))을 재사용한다. 가짜 키는 실제 클라이언트가 요청에 실어 보내는 값이므로 이 검사가 의미를 가진다(`MockLLMClient`는 키를 쓰지 않아 동어반복이 된다).
3. **작동원리 01편 동기화** ([`01-헤르메스코어-작동원리.md`](../../../작동원리/01-헤르메스코어-작동원리.md)): 코드로 확인된 **영구 사실만** 반영한다 — 스킬 도구 2종의 위치, 읽기 전용(폴더도 만들지 않음), 점진 공개 3단계, 스킬 폴더가 작업 폴더 밖이라 파일·터미널 도구가 닿지 못하고 스킬 도구가 같은 경로 안전 기준을 쓴다는 점, 안내문이 헤드에 있고 스킬 목록은 지시문에 없다는 점, 스킬 본문은 신뢰하지 않은 텍스트가 문맥에 들어오는 길이라는 한계. 작동원리 README의 규칙(로드맵 서사 금지, 테스트 개수 기재 금지, 5부 구조, 사실 검증 4축·「미확인」 표기)을 따른다.

## 3. 인수 테스트 시나리오 (구현 전 작성, 임의 변경 금지)

공통 준비: `r05_e2e_env` + 가짜 키(`"sk-or-v1-" + "…"`처럼 런타임에 결합) 클라이언트. `<HERMES_HOME>/skills/release-checklist/SKILL.md`(본문에 `STEP-7: tag the build`)와 `references/notes.md`(내용 `NOTE-ALPHA`). 스킬 루트 **밖**의 보호 대상은 픽스처가 이미 만든 `<HERMES_HOME>/state.db`(실제 SQLite)와 `<HERMES_HOME>/memories/MEMORY.md`(`Known Fact: Initial Memory Item`)다. `tool_calls` 인자는 시험이 직접 쓴다(요구사항의 호출 순서: 목록 → 본문). 아래 「tool 메시지」는 해당 도구 호출의 `tool_call_id`에 대응하는 `role == "tool"` 메시지를 뜻한다.

| # | 입력 | 기대 결과 |
|---|---|---|
| 1 | 응답 순서: `skills_list` 호출 → `skill_view(name="release-checklist")` 호출 → 최종 텍스트 | `stopped_reason == "completed"`, `iterations == 3`. 2번째 요청에 `skills_list` tool 메시지(내용에 `release-checklist`)가 있고 `STEP-7`은 **없음**, 3번째 요청에 `skill_view` tool 메시지(내용에 `STEP-7`)가 있음(순서 확인). 각 `tool_call_id`가 짝을 이룸 |
| 2 | 위 흐름에 `skill_view(name="release-checklist", file_path="references/notes.md")` 호출을 더함 | 그 tool 메시지 `content`에 `NOTE-ALPHA` |
| 3 | 모델이 `skill_view(name="../state.db")`, `skill_view(name="../memories/MEMORY.md")`, `skill_view(name="release-checklist", file_path="../../../state.db")`를 차례로 호출한 뒤 최종 텍스트 | 세 tool 메시지 모두 `success false`이고 내용에 `SQLite format 3`·`Known Fact: Initial Memory Item`이 **없음**(기억 내용은 시스템 메시지에는 원래 있으므로 tool 메시지만 본다). 루프는 계속되어 `stopped_reason == "completed"` |
| 4 | 스킬 폴더 자체가 없는 상태에서 `skills_list` 호출 후 최종 텍스트 | 정상 종료, 빈 목록 결과가 tool 메시지로 전달됨, 대화 뒤에도 `skills/` 폴더가 **없음** |
| 5 | 시나리오 1~3 실행 전후 스킬 폴더(경로+내용 해시)와 `<HERMES_HOME>` 직하위 항목 이름 집합 | 동일 (읽기 전용) |
| 6 | 시나리오 1 대화 전체의 모든 요청 | 각 요청의 첫 메시지가 `role == "system"`이고 서로 바이트 동일, `SKILLS_GUIDANCE`를 포함하며 `sessions.system_prompt`와 같음 (도구를 쓰는 실제 대화 안에서의 불변. 압축과 결합한 불변은 7) |
| 7 | `context_window_tokens=600` 등 05 060 시나리오 1~7과 같은 방식으로 압축이 발동하는 긴 대화에, 헤드(처음 3개 메시지)와 꼬리(최근 6개 이상 메시지) **사이**에 놓이도록 `skill_view` 호출(본문 약 19,000자, ASCII)을 포함 | 결과에 `compression["count"] >= 1`, 압축 뒤 요청들이 오류 없이 이어지고, 압축 뒤 요청의 어떤 tool 메시지도 19,000자 본문을 그대로 갖지 않으며(표지 `[Old tool output cleared:` 또는 요약으로 대체), 첫 시스템 메시지는 바이트 동일. (`skill_view`가 헤드나 꼬리에 들어가면 보호되어 시험이 무효이므로, 놓을 수 없으면 임의로 바꾸지 않고 멈춰서 보고한다) |
| 8 | 시나리오 1~7을 실행한 뒤 DB 전체(`messages`, `llm_calls`, `sessions`)와 `captured_requests` 본문을 직렬화해 가짜 키 문자열 검색 | DB에는 없음 (클라이언트가 실제로 가짜 키를 헤더에 실어 보낸 상태에서의 확인) |
