## 1. 왜 지금 이 로드맵인가

05번으로 에이전트는 긴 대화에서도 앞선 사실을 요약으로 이어갈 수 있게 되었다. 그런데 에이전트가 **「어떻게 하는지」를 아는 방법**은 아직 하나밖에 없다. 시스템 지시문에 적어 두는 것이다. 지시문은 매 호출마다 통째로 전송되므로 절차가 늘수록 모든 대화의 짐이 된다. 반대로 절차를 아예 적지 않으면 에이전트는 같은 일을 할 때마다 처음부터 다시 궁리한다.

사람이 이 시스템을 맡았을 때 묻는 질문은 이렇다.

- *"에이전트에게 반복되는 작업 절차(배포 순서, 리뷰 체크리스트)를 가르치려면 어디에 적어야 하는가? 지시문에 계속 쌓아도 되는가?"*
- *"절차가 수십 개가 되어도 대화마다 그 전부를 짊어지지 않고, 필요할 때만 꺼내 쓰는가?"*
- *"에이전트가 절차 문서를 읽다가 문서 밖의 파일(비밀 파일 등)까지 읽게 되지는 않는가?"*

지금은 세 질문에 「모른다」가 정직한 답이다. 원본 Hermes Agent는 기억을 「장기 기억(파일), 과거 대화 검색, 대화 기억의 압축, **절차 기억(스킬)**」으로 나눈다. 우리에게는 앞의 셋이 있고 마지막 하나가 비어 있다. 이 로드맵은 그 넷째 기둥을 **읽기 중심으로** 세운다. 절차는 파일로 두고, 에이전트는 먼저 이름과 설명만 보고, 필요할 때만 본문을 읽는다(점진 공개).

## 2. 왜 이 정도로만 하는가

이 로드맵이 **일부러 하지 않는 것**과 그 이유다.

| 하지 않는 것 | 이유 | 언제 하는가 |
|---|---|---|
| 에이전트가 스킬을 직접 만들고 고치는 기능 | 쓰기가 들어오면 03에서 한 쓰기 안전 정책을 스킬 폴더에 다시 적용하고 내용 검사도 필요해 범위가 크게 늘어난다. 합의한 대로 06은 읽기 중심이다. 스킬은 사용자가 파일을 직접 둔다. | 읽기 구조가 안정되고 스킬 변경 안전 정책을 정할 때 |
| 시스템 프롬프트에 스킬 목록(인덱스)을 넣기 | 원본의 기준 시점에도 없던 기능이다. 스킬이 늘수록 프롬프트가 길어지고, 스킬 추가가 「세션 중 지시문은 변하지 않는다」는 전제와 부딪힌다. 도구로 목록을 보는 방식으로 점진 공개의 핵심을 먼저 익힌다. | 모델이 도구만으로는 스킬을 잘 못 찾는다는 증거가 스모크에서 나올 때 |
| 스킬 설치·동기화·허브, 보안 검사, `/스킬이름` 슬래시 명령 | 원본 현행 버전의 확장 기능이고 절차 기억의 기본 구조 이해와 무관하다. 억지 이식은 안티패턴이다. | 필요가 생겼을 때 |
| 스킬 머리말의 중첩 항목(태그, 관련 스킬, 호환성 메타데이터) | 읽으려면 YAML 파서 의존성이 필요하다. 이름과 설명만으로 점진 공개의 1단계가 성립한다. | 이 항목이 실제로 필요해질 때 의존성 추가와 함께 |
| 스킬 내용의 보안 검사 | 06은 사용자가 직접 둔 스킬만 읽는다고 가정한다. 검사 규칙을 만드는 일이 별도의 큰 주제다. | 외부 스킬을 받아 오는 기능이 생길 때 |
| 플랫폼·조건별 스킬 활성화, 사용 통계 | 스킬이 많아져 걸러야 할 때의 문제다. | 스킬 수가 문제가 될 때 |

한마디로, **「스킬이 어디 있는지 보고, 필요한 것을 안전하게 읽는다」까지만** 한다. 스킬을 잘 쓰게 만드는 일은 그 이후의 문제다.

## 3. 왜 이 순서, 왜 이 단계 수인가

단계는 여섯 개이고, **파일을 읽는 순수한 부분부터, 안전이 걸린 부분은 따로, 에이전트 연결은 뒤에, 실제 키는 맨 마지막에** 둔다.

| 순서 | 하는 일 | 왜 이 자리인가 |
|---|---|---|
| 1 (010) | 스킬 파일의 머리말을 읽고, 스킬 폴더에서 스킬을 찾는다 | 모델도 도구 통로도 필요 없는 파일 처리다. 뒤 단계가 모두 이 위에 선다. |
| 2 (020) | 「스킬 목록 보기」 도구를 만들어 도구 통로에 등록한다 | 가장 단순한 도구다. 도구가 통로에 올라가는 방식을 먼저 확인한다. |
| 3 (030) | 「스킬 본문 읽기」 도구를 만든다 | 이 로드맵에서 **가장 위험한 단계**다. 이름이나 파일 경로를 모델이 정하므로 스킬 폴더 밖을 읽으려는 시도를 막아야 한다. 따로 떼어 안전 시험을 집중한다. |
| 4 (040) | 에이전트의 시스템 지시문에 「스킬 도구를 이렇게 써라」는 안내 한 덩어리를 더한다 | 지시문은 모든 대화의 앞부분이라 건드리면 파급이 크다. 도구가 검증된 뒤 한 번만 건드린다. |
| 5 (050) | 가짜 통신으로 「목록 보기 → 본문 읽기 → 답하기」 전체를 시험한다 | 부품별 시험이 아니라 합쳐졌을 때도 되는지 확인한다. |
| 6 (060) | 진짜 키로 딱 한 번, 모델이 스스로 스킬을 찾아 쓰는지 본다 | 모델이 실제로 목록을 부르는지는 가짜 모델로는 알 수 없다. 비용 때문에 마지막에, 사용자가 지시할 때만 한다. |

05번(일곱 단계)보다 하나 적은 이유는 「턴 간 문맥」 같은 바닥 단계가 따로 필요 없기 때문이다. 020과 030을 합치면 쉬운 도구와 위험한 도구가 한 단계에 섞여 안전 시험이 묻힌다.

## 4. 왜 이 방식을 택하고 무엇을 배척했나

| 선택 | 배척한 대안 | 이유 |
|---|---|---|
| 스킬은 도구로만 꺼내 읽는다 (이름·설명 → 본문 → 부속 파일 순) | 스킬 목록을 시스템 지시문에 넣기 / 스킬 전체를 항상 넣기 | 절차가 늘어도 대화의 기본 짐이 늘지 않는다. 지시문이 세션 동안 변하지 않는다는 전제도 지킨다. |
| 스킬은 읽기 전용이고, 도구는 스킬 폴더를 건드리지 않는다 (폴더가 없어도 만들지 않음) | 목록 도구가 폴더를 만들어 주기 (원본 방식) | 읽기 도구가 쓰기를 하면 「읽기는 안전하다」는 믿음이 깨진다. |
| 스킬 폴더는 작업 폴더 **밖**에 둔다 | 작업 폴더 안에 두기 | 작업 폴더는 모델이 파일 도구로 쓰는 영역이다. 안에 두면 모델이 절차 문서를 몰래 고칠 수 있다. 밖에 두면 쓰기 도구가 아예 닿지 못한다. |
| 스킬 안에서 읽을 파일 경로는 기존 경로 안전 기준(폴더 이탈·심볼릭 링크·비밀 파일 이름 거부)을 그대로 쓴다 | 새 검사 규칙을 따로 만들기 / 원본처럼 검사 없이 읽기 | 안전 기준이 둘이면 서로 어긋난다. 원본은 `../`로 폴더 밖을 읽을 수 있는 구멍이 있었다. 같은 입력이 거부되는지 시험으로 고정한다. |
| 이름이 겹치면 조용히 하나를 고르지 않고 오류와 후보를 준다 | 첫 번째 것을 고르기 | 엉뚱한 절차를 따르게 되는 것이 모른 채 실패하는 것보다 나쁘다. |
| 머리말은 이름과 설명만 읽는 작은 파서 | YAML 라이브러리 추가 | 새 의존성은 설치·버전 불확실성을 들인다. 원본 번들 스킬 47개를 확인하니 이름과 설명은 모두 첫 줄 형식이었고, 중첩 항목은 44개가 갖고 있었다. 중첩은 읽지 않고 건너뛰어도 1단계가 성립한다(가정 A). |
| 본문에는 크기 상한을 둔다 | 전부 반환 (원본 방식) | 스킬 하나가 한 번에 문맥을 크게 키우는 것을 막는다. 05의 압축은 사후 완화일 뿐이다. |
| 원본에서 구조(목록 → 본문 → 부속 파일)만 참고한다 | 원본 이식 | 원본 현행 버전은 허브·검사·동기화 등으로 크게 늘었다. 억지 모방은 안티패턴이다. |

## 5. 성공 판단 기준과 검증할 가정

**성공 기준**: 가짜 통신으로 모든 시험이 통과하고, 에이전트가 스킬 목록을 보고 본문을 읽어 그 절차대로 답하는 대화가 재현되며, 스킬 폴더 밖이나 비밀 파일을 읽으려는 시도가 모두 거부되고, 도구가 스킬 폴더를 바꾸지 않으며, 기존 테스트가 한 줄도 바뀌지 않고 통과하고, 사용자가 지시하면 진짜 키로도 모델이 스킬을 찾아 쓰는 것이 관찰되며, 그 과정에서 키가 어디에도 남지 않는다.

마감 때 종합보고서가 아래 가정을 하나씩 「맞았다 / 틀렸다 / 바뀌었다」로 대조한다.

| 번호 | 가정 | 틀렸다면 |
|---|---|---|
| **A** | 작은 머리말 파서로 이름·설명을 읽는 데 충분하다. (근거: 원본 기준 커밋 번들 스킬 47개 중 머리말이 없는 것 0개, 중첩 항목 보유 44개. 이름·설명이 한 줄 형식이 아닌 스킬이 있는지는 **미확인**) | 파서 범위를 넓히거나 YAML 의존성 도입을 새 ADR로 결정한다. |
| **B** | 안내문 한 덩어리만으로 모델이 필요할 때 스킬 목록을 부르고 본문을 읽는다. (**미확인**: 이 모델로 해 본 적이 없다.) | 안내문을 고치거나, 지시문 인덱스 주입을 후속으로 검토한다. |
| **C** | 기존 경로 안전 기준을 스킬 폴더에 그대로 적용하는 것만으로 폴더 이탈·심볼릭 링크 이탈·비밀 파일 접근이 모두 막힌다. | 스킬용 검사를 추가하되 기준선과의 어긋남을 문서화한다. |
| **D** | 안내문 추가는 시스템 지시문의 불변성, 압축의 헤드 보존, 기존 지시문 시험과 충돌하지 않는다. | 안내문 위치나 주입 방식을 바꾼다. |
| **E** | 본문 상한(20,000자 후보)이 일반 스킬에 충분하고 잘림이 드물다. (**미확인**: 원본 번들 스킬 크기 분포를 착수 전에 재본다.) | 상한을 조정하거나 부분 읽기 인자를 후속으로 검토한다. |
| **F** | 기존 테스트가 한 줄도 바뀌지 않고 통과한다. 새 도구 2종과 안내문 추가가 기존 도구·압축·DB에 영향을 주지 않는다. | 결합이 있다는 뜻이므로 원인을 찾아 분리한다. |
| **G** | 스킬 도구로는 상태 폴더의 비밀 파일·세션 DB·기억 파일이 읽히지 않는다. | 경로 판정을 고친다. |

## 6. 알려진 위험과 아직 확인하지 못한 것

- **모델이 스킬을 안 부를 수 있다**: 안내문이 약하면 목록을 한 번도 부르지 않는다(가정 B). 06은 스모크에서 한 번 관찰할 뿐 체계적으로 평가하지 않는다.
- **스킬 본문은 신뢰하지 않은 텍스트가 모델 문맥에 들어오는 길이다**: 문서 안의 문장이 지시처럼 읽혀 모델을 다른 방향으로 이끌 수 있다(프롬프트 주입). 06은 보안 검사를 하지 않고 **사용자가 직접 둔 스킬만 읽는다고 가정**한다. 외부에서 받아 온 스킬에는 쓸 수 없는 전제다.
- **작은 파서의 한계**: 여러 줄 값이나 중첩 항목은 읽지 않는다. 이름·설명이 여러 줄로 쓰인 스킬은 설명이 비거나 본문 첫 줄로 대체된다.
- **심볼릭 링크와 `rglob`의 동작**: 파이썬 버전에 따라 링크된 폴더를 따라가는 정도가 다를 수 있다(**미확인**). 결과의 실제 경로가 스킬 폴더 안인지 항상 다시 확인해 어느 쪽이든 안전하게 한다.
- **원본의 구멍은 원본에 남는다**: 원본의 `file_path` 이탈과 `skills_list`의 폴더 생성은 읽기 전용 규칙에 따라 고치지 않고 보고만 한다.
- **이 MVP는 스킬의 존재만 안다**: 스킬을 만들거나 고치거나 설치하는 일은 사용자가 파일로 한다.
