## 1. 구현 내용 명세

이 단계는 ① 턴 훅 장치(`before_llm`, `after_tool_calls` 두 지점)를 만들고 ② `run_conversation` 안의 압축 블록(`agent.py:378-468`)을 `before_llm` 훅으로 **동작 변경 없이** 옮긴다. 이 로드맵에서 위험이 가장 큰 단계다.

### 1-0. 착수 첫 작업: 이관 전 골든 고정 (코드 변경 전)

동어반복 시험을 막기 위해, `agent.py`를 고치기 **전에** 현재 코드로 아래 시나리오 G1~G3의 결과를 먼저 뽑아 골든 파일로 고정한다.

- 골든 파일: `tests/test_hermes_core/golden/compression_before.json`. 항목은 시나리오별로 `messages`(각 메시지의 `role`·`content`·`tool_calls`·`tool_call_id`), 원장 행(`role`·`active`·`compacted`·`content`를 `id` 순으로, `id`·시각 제외), `result["compression"]`(있으면)이다.
- 시나리오 구성은 [`test_compression_agent.py`](../../../../tests/test_hermes_core/test_compression_agent.py)(작은 `context_window_tokens`, 긴 도구 결과, 요약용 Mock 응답)를 참고하되, 도구 호출 id와 Mock 응답을 모두 고정해 결과가 결정적이도록 한다.
- 골든은 이관 코드가 생기기 전 `HEAD`에서 만든 것임을 커밋 메시지에 적는다. 골든 값을 이관 후 코드에 맞춰 다시 쓰지 않는다. 불일치가 나오면 멈추고 보고한다.

### 1-1. 훅 장치 신설 (`src/hermes_core/agent/turn_hooks.py`)

```python
BEFORE_LLM = "before_llm"
AFTER_TOOL_CALLS = "after_tool_calls"
HOOK_POINTS = (BEFORE_LLM, AFTER_TOOL_CALLS)

@dataclass
class TurnContext:
    messages: list[dict[str, Any]]          # run_conversation이 쓰는 같은 리스트 객체
    tools_schema: Optional[list[dict[str, Any]]]
    iteration: int
    session_id: str
    run_state: dict[str, Any] = field(default_factory=dict)
    stop_reason: Optional[str] = None
    def request_stop(self, reason: str) -> None: ...   # 먼저 요청한 이유가 유지된다

TurnHook = Callable[[TurnContext], None]

class HookRegistry:
    def register(self, point: str, hook: TurnHook) -> None: ...   # 모르는 지점이면 ValueError
    def run(self, point: str, ctx: TurnContext, on_error=None) -> None: ...
```

- `run`은 등록 순서대로 훅을 실행한다. 훅이 `Exception`을 던지면 삼키고 `on_error(point, hook, exc)`를 부른 뒤 다음 훅을 계속 실행한다(`BaseException`은 삼키지 않는다).
- 각 훅 실행 전후로 `ctx.messages[0]`이 시스템 메시지(`role == "system"`)이면 그 `role`·`content`를 비교한다(객체 동일성은 보지 않는다). 달라졌으면 실행 전 시스템 메시지의 사본으로 되돌리고(맨 앞이 시스템 메시지가 아니게 되었으면 맨 앞에 다시 넣는다) `on_error`를 `ValueError("system message modified by hook")`로 부른다.
- 훅이 `messages`를 바꾸면 **원장과의 일치는 그 훅의 책임**이다(압축 훅은 `archive_and_compact`로 맞춘다). 레지스트리는 이를 검사하지 않는다.
- 모듈 독스트링에 원본 매핑을 적는다: 원본 `hermes-agent/hermes_cli/plugins.py`의 `VALID_HOOKS`(`pre_llm_call`·`post_tool_call` 등)에 대응하며, 지점을 2개로 줄이고 차단은 도구 미들웨어에 맡긴 점이 다르다.

### 1-2. 압축 훅 신설 (`src/hermes_core/agent/compression_hook.py`)

- `CompressionHook(agent)`는 호출 가능 객체다. `agent.py:378-468`의 블록을 **그대로** 옮긴다: 판정(`compression_threshold`·`estimate_current_tokens`·`should_compress`·`may_retry_after_reject`) → `find_previous_summary`·`split_for_compression`로 `can_split` 계산 → `compress_messages` → 성공이면 `archive_and_compact`, **성공한 경우에만** `messages[:] = comp_res.messages`와 상태 초기화 → 사용량 반영(`update_token_counts`) → 실패/거부 처리(`_rejected_at_tokens`).
- 호출 시점에 `agent`의 `llm_client`, `context_window_tokens`, `compression_threshold_ratio`, `compression_enabled`, `session_db`, `session_id`와 토큰 추정 상태(`_last_input_tokens`, `_last_message_count`, `_rejected_at_tokens`)를 **읽고 쓴다**(시험이 생성 뒤 `agent.llm_client`를 바꾸므로). 속성 이름과 의미는 바꾸지 않는다.
- 시도·성공·폴백 횟수는 `ctx.run_state["compression"] = {"attempts": n, "count": n, "fallback": n}`에 쌓는다. `COMPRESSION_MAX_PER_RUN` 상한 비교는 `attempts`로 한다. 로그 문구(`[Compression] ...`)는 그대로 둔다(로거 이름만 이 모듈이 된다).
- `compression_enabled`가 `False`면 아무것도 하지 않고 돌아온다.

### 1-3. 에이전트 연결 ([`agent.py`](../../../../src/hermes_core/agent/agent.py))

- `__init__`에서 `self.hooks = HookRegistry()`를 만들고 `CompressionHook(self)`를 `BEFORE_LLM`에 **가장 먼저** 등록한다. 생성자 인자로 레지스트리를 받지 않는다.
- `run_conversation`에서 루프 전에 `ctx = TurnContext(messages=messages, tools_schema=None, iteration=0, session_id=self.session_id)`를 만든다. 반복마다 `ctx.iteration`, `ctx.tools_schema`(= `schema_list`)를 갱신한 뒤 `self.hooks.run(BEFORE_LLM, ctx, on_error=self._on_hook_error)`를 부른다. `ctx.stop_reason`이 있으면 `stopped_reason = ctx.stop_reason`, `final_response = ""`로 하고 반복을 끝낸다(LLM은 부르지 않는다).
- 도구 실행(`self._execute_tool_calls(...)`) 직후 `self.hooks.run(AFTER_TOOL_CALLS, ctx, on_error=...)`를 부르고, `ctx.stop_reason`이 있으면 같은 방식으로 끝낸다. 이 시점에는 모든 `tool` 메시지가 이미 `messages`와 원장에 적혀 있으므로 도구 쌍이 깨지지 않는다.
- 압축 블록(`378-468`)을 삭제한다. 결과 조립에서 `compression_count`·`compression_fallback_count` 대신 `ctx.run_state.get("compression")`을 읽어 `count > 0`일 때만 현재와 같은 형식 `{"count": n, "fallback": m}`으로 `result["compression"]`을 만든다.
- `_on_hook_error(point, hook, exc)`는 `logger.warning`을 남기고 `self._emit(EVENT_HOOK_ERROR, point=point, hook=<훅 이름>, error=str(exc))`를 부른다. `events.py`에 `EVENT_HOOK_ERROR = "hook_error"`를 추가한다(`ConsoleEventSink`는 이 종류를 무시한다).
- 토큰 사용량 처리(`usage` → `_last_input_tokens` 등), `llm_error` 처리, `max_iterations` 처리는 바꾸지 않는다.

## 3. 인수 테스트 시나리오 (구현 전 작성, 임의 변경 금지)

### 3-1. 훅 장치 (H)

| # | 입력 | 기대 결과 |
|---|---|---|
| H1 | `HookRegistry().register("after_llm", f)` | `ValueError`. `HOOK_POINTS == ("before_llm", "after_tool_calls")` |
| H2 | `before_llm`에 훅 h1, h2를 이 순서로 등록해 턴 실행 | 기록이 `["h1", "h2"]`이다 (압축 훅이 먼저 등록되어 있어도 사용자 훅의 상대 순서는 h1, h2) |
| H3 | 훅이 `ctx.messages.append({"role": "user", "content": "hint"})` | 같은 반복의 `MockLLMClient.call_history[-1]["messages"]` 끝에 그 메시지가 있다 (제자리 변형이 LLM 입력에 반영됨) |
| H4 | 훅이 `ctx.messages[0]["content"] = "HACK"` | 실행 뒤 시스템 메시지 내용이 원래대로이고, LLM에 전달된 시스템 메시지도 원래 내용이다. `caplog`에 경고가 남고 `hook_error` 이벤트가 방출된다 (가정 D) |
| H5 | 훅이 `ctx.messages.pop(0)`으로 시스템 메시지를 제거 | 시스템 메시지가 맨 앞에 복구된다 (가정 D) |
| H6 | 훅이 `RuntimeError("boom")`을 던짐, `event_sink=events.append` | 턴이 `stopped_reason == "completed"`로 끝나고, `kind == "hook_error"` 이벤트의 `data`에 `point`, `hook`, `error`(`"boom"` 포함)가 있다. `caplog`에 경고가 남는다 (가정 E) |
| H7 | `after_tool_calls` 훅이 첫 도구 호출 직후 `ctx.request_stop("budget")` (Mock은 도구 호출 응답 뒤 텍스트 응답을 대기) | `stopped_reason == "budget"`, `iterations == 1`, `final_response == ""`, LLM 호출 1회, `messages` 마지막이 `tool` 메시지이고 원장에도 같은 `tool` 행이 있다 (assistant `tool_calls`와 `tool` 결과 쌍 보존) |
| H8 | `before_llm` 훅이 `ctx.request_stop("halt")` | LLM 호출 0회, `stopped_reason == "halt"`, `iterations == 1`, `messages`는 `[system, user]`다 |
| H9 | 두 훅이 같은 지점에서 각각 `request_stop("first")`, `request_stop("second")` | `stopped_reason == "first"` (먼저 요청한 이유가 이긴다) |
| H10 | 훅 하나가 `ctx.iteration`과 `ctx.tools_schema`를 기록, 도구 호출 1건이 있는 2회 반복 턴 | `iteration`이 1, 2로 기록되고 `tools_schema`는 디스패처의 등록 스키마 목록과 같다 |

### 3-2. 압축 이관 동일성 (G)

| # | 입력 | 기대 결과 |
|---|---|---|
| G1 | 압축이 1회 일어나는 골든 시나리오(요약 성공) | `messages`, 원장 행(`active`·`compacted` 포함), `result["compression"] == {"count": 1, "fallback": 0}`가 **이관 전 골든과 동일**하다 (가정 A) |
| G2 | 요약이 실패해 폴백 요약이 쓰이는 골든 시나리오 | 위와 같은 항목이 골든과 동일하고 `result["compression"]["fallback"] == 1` |
