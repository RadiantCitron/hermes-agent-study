# [WHY] 09-CLI-입력-안정화 — 왜 이 로드맵을, 왜 이 정도로만 하는가

> **성격**: 이 로드맵의 의도를 적은 문서다 (ROADMAP_정책 §3-2). 마감 때 종합보고서(`결과정리및리뷰.md`, 마감 시 작성)가 이 문서의 「검증할 가정」을 하나씩 대조한다. 4단계 착수 후에는 본문을 고치지 않고 맨 끝 「변경 기록」에만 덧붙인다.  
> **작성일**: 2026-10-29 · **함께 보는 문서**: [PLAN.md](PLAN.md)(무엇을 하기로 승인했나), [ROADMAP.md](ROADMAP.md)(설계), [ADR-0009](../../adr/0009-CLI_입력_안정화_범위와_prompt_toolkit_도입.md)(결정 근거)

---

## 1. 왜 지금 이 로드맵인가

에이전트에게 말을 거는 유일한 문은 터미널의 입력 한 줄이다. 그런데 이 문이 불안정하다. 05번과 07번 실제 모델 시험에서 사람이 한글을 치다 고치려고 편집 키를 누르면 프로그램이 오류로 꺼진 일이 기록됐고, 08번 보고서도 같은 문제를 후속 과제로 다시 올렸다. 대화 내용은 이미 저장된 뒤라 데이터는 잃지 않았지만, 에이전트가 아무리 안전해도 **말을 거는 순간 꺼지면** 그 안전을 쓸 수 없다. 사용자는 입력 줄의 `User >` 표시가 지워지는 것도 겪었다고 했다.

사람이 이 시스템을 쓸 때 묻는 질문은 이렇다.

- *"한글을 치다 틀려서 지우면 프로그램이 죽지 않는가?"*
- *"긴 문장이나 여러 줄을 붙여넣으면 한 번에 들어가는가, 줄마다 따로 전송되어 에이전트가 엉뚱하게 답하지 않는가?"*
- *"입력창이 이상해졌을 때, 시스템의 나머지(저장된 대화, 도구 실행)가 영향을 받지 않는가?"*

지금은 첫 질문에 「터미널 설정에 따라 죽는다」(실험으로 재현함), 둘째에 「확인해 보지 않았다」, 셋째에 「받는 쪽은 안전하다」가 답이다. 다음 10번 로드맵(승인 흐름)은 사람에게 「이 명령을 실행해도 됩니까?」를 묻고 답을 받는 일이 핵심이므로, 그 답을 받는 문이 먼저 단단해야 한다. 이 로드맵은 **말을 거는 문 하나를 단단하게** 한다.

## 2. 왜 이 정도로만 하는가

이 로드맵이 **일부러 하지 않는 것**과 그 이유다.

| 하지 않는 것 | 이유 | 언제 하는가 |
|---|---|---|
| 출력(응답 표시, 실시간 출력, 색) 손보기 | 사용자가 입력만 하기로 정했다. 입력과 출력을 한 번에 고치면 어느 쪽 효과인지 가려진다. | 필요가 생길 때 별도 로드맵으로 |
| 이전에 입력한 문장을 위아래 키로 불러오기, 자동 완성 | 안정화가 아니라 새 기능이다. | 필요가 생길 때 |
| Ctrl+Enter로 전송하기 | 대부분의 터미널은 Enter와 Ctrl+Enter를 같은 신호로 보내서 프로그램이 구별할 수 없다. 되는 터미널과 안 되는 터미널이 갈린다. | 하지 않는다. 대신 널리 쓰이는 Ctrl+J를 줄바꿈에 쓴다 |
| 원본의 입력 처리 전체를 옮기기 | 원본은 에이전트가 일하는 중에도 입력을 받는 등 훨씬 크다. 읽은 범위는 키 설정까지다. 억지 모방은 안티패턴이다. | 필요가 실제로 생길 때 |
| 일시적인 통신 오류 재시도, 너무 긴 대화 거절 복구 | 입력과 무관한 안정화다. | 별도 로드맵 후보 |

한마디로, **「말을 거는 문이 한글과 편집 키에 죽지 않고, 여러 줄을 한 번에 받는다」까지만** 한다.

## 3. 왜 이 순서, 왜 이 단계 수인가

단계는 다섯 개(010·020·030·040·050)이고, **기존 동작을 그대로 보존하는 정리부터, 새 부품은 그다음, 앱에 붙이는 일은 그 뒤, 실제 터미널은 맨 마지막에** 둔다.

| 순서 | 하는 일 | 왜 이 자리인가 |
|---|---|---|
| 1 (010) | 입력을 읽는 일을 한 곳으로 모으고, 잘못된 글자 바이트가 와도 그 줄만 버리고 계속하게 한다. 동작은 그대로 | 새 라이브러리 없이 되는 일이다. 가장 흔한 사고(오류로 꺼짐)를 먼저 막고, 이후 단계가 붙을 자리를 만든다. |
| 2 (020) | 진짜 터미널일 때만 쓰는 새 입력 방식을 만든다. Enter 전송, Ctrl+J 줄바꿈, 붙여넣기 | 새 외부 부품이 들어오는 유일한 단계라 따로 둔다. 앱에는 아직 붙이지 않는다. |
| 3 (030) | 앱이 이 입력 방식을 쓰게 하고 안내 한 줄을 보인다 | 사용자에게 보이는 동작이 바뀌는 지점을 한 단계로 둔다. |
| 4 (040) | 실제 터미널과 같은 환경을 흉내 내 재현된 결함이 사라졌는지 확인하고, 시스템 설명서를 사실에 맞춘다 | 사람 없이 할 수 있는 확인을 먼저 끝낸다. |
| 5 (050) | 사용자가 실제 터미널 앱에서 직접 확인하고 마감한다 | 흉내로는 볼 수 없는 화면 모양과 `User >` 사라짐은 사람이 봐야 한다. 비용이 드는 키는 필요 없다. |

## 4. 왜 이 방식을 택하고 무엇을 배척했나

| 선택 | 배척한 대안 | 이유 |
|---|---|---|
| 입력 읽는 일을 한 함수로 모은다 | 지금처럼 여러 곳에서 직접 읽기 | 판단과 예외 처리가 한 곳에 모이고, 10번 승인 질문이 같은 문을 쓸 수 있다. |
| 진짜 터미널일 때만 새 방식, 아니면 기존 방식 | 항상 새 방식 | 기존 시험이 가짜 입력을 주입하는 방식에 기대고 있어 모두 고쳐야 하고, 파이프 사용에서 동작이 달라질 위험이 생긴다. |
| 새 입력 라이브러리를 쓴다 | 표준 편집 모듈만 추가 | 표준 모듈은 죽는 문제는 막았지만 여러 줄과 붙여넣기는 풀지 못한다. 한글처럼 폭이 넓은 글자의 화면 처리도 라이브러리 몫이다. |
| 줄바꿈은 Ctrl+J | Ctrl+Enter | 위 2번 표. |
| 잘못된 바이트는 안내하고 다시 읽는다 (터미널에서는 그 줄만 버려짐) | 오류로 종료하거나 조용히 무시 | 종료는 지금의 결함이다. 조용한 무시는 사용자가 왜 응답이 없는지 모르게 한다. |

## 5. 성공 판단 기준과 검증할 가정

**성공 기준**: 가짜 입력으로 모든 시험이 통과하고, 기존 시험이 한 줄도 바뀌지 않고 통과하며, 터미널이 아닌 입력의 동작이 이전과 같고, 재현된 결함(한글 입력 후 백스페이스로 꺼짐)을 흉내 낸 터미널에서 더 이상 만나지 않으며, 사용자가 실제 터미널 앱에서 한글 편집과 여러 줄 붙여넣기를 시험해 보고, 입력 외의 부분(에이전트, 도구, 저장, 압축, 위임, 출력)이 바뀌지 않는다.

마감 때 종합보고서가 아래 가정을 하나씩 「맞았다 / 틀렸다 / 바뀌었다」로 대조한다.

| 번호 | 가정 | 틀렸다면 |
|---|---|---|
| **A** | 새 입력 방식에서 한글을 치고 백스페이스로 지워도 프로그램이 꺼지지 않는다. (흉내 낸 터미널에서는 확인 가능, **미확인**: 실제 터미널 앱) | 입력 방식이나 설정을 고친다. 이 로드맵의 핵심 목표가 틀렸다는 뜻이다. |
| **B** | 입력 읽기 중 잘못된 바이트가 와도 프로그램이 오류로 꺼지지 않고 안내 후 다시 읽으며, 대화 기록과 저장소는 바뀌지 않는다. 터미널에서는 잘못된 줄 하나만 버려지지만, 파이프·가짜 입력에서는 같은 덩어리의 정상 줄도 함께 사라질 수 있다(실험으로 확인, 이 경우 입력이 끝나면 정상 종료). | 예외 처리 위치를 고친다. |
| **C** | 터미널이 아닌 입력의 동작은 이전과 같고, 기존 시험이 한 줄도 바뀌지 않고 통과한다. | 판단 조건을 고친다. 기존 사용에 영향이 있다는 뜻이다. |
| **D** | Enter는 전송, Ctrl+J는 줄바꿈이고, Ctrl+C와 Ctrl+D는 지금과 같은 종료 경로를 탄다. | 키 설정을 고친다. |
| **E** | 여러 줄을 붙여넣으면 한 번의 입력으로 들어간다. (**미확인**: 지금 방식에서 줄마다 따로 전송되는지부터 아직 실험하지 않았다.) | 붙여넣기 설정을 고친다. 현재 문제가 실재하지 않았다면 「문제가 없었음」으로 기록한다. |
| **F** | 사용자가 겪은 `User >` 사라짐이 사라진다. (**미확인**: 원인을 재현하지 못했다. 사라지지 않으면 구조를 되돌리지 않고 「원인 미상, 후속 조사」로 기록하고 멈춘다.) | 원인 조사를 후속 로드맵 후보로 올린다. |
| **G** | 새 입력 부품 하나를 추가해도 설치와 실행에 문제가 없다. 입력 외의 부분(에이전트, 도구, 저장, 압축, 위임, 출력)에는 변경이 없다. | 의존성 선언이나 결합을 고친다. |

## 6. 알려진 위험과 아직 확인하지 못한 것

- **원인 미상의 증상**: `User >` 사라짐은 재현하지 못했다. 이 로드맵이 그것을 없애리라는 보장은 없다. 050 단계에서 사용자가 직접 확인한다.
- **터미널 앱마다 다름**: 흉내 낸 터미널과 실제 앱(Terminal.app, iTerm2 등)은 같지 않다. 화면 모양은 사람 눈으로만 확인된다.
- **새 외부 부품**: 설치가 안 되거나 이 환경에서 다르게 동작할 수 있다. 부품이 없을 때 기존 방식으로 되돌아가게 할지는 020 지시서에서 코드와 대조해 정한다(**미확인**, 열린 항목).
- **터미널이 아닌 입력**은 여전히 기존 방식이라 화면 편집 문제는 풀리지 않는다. 꺼지지만 않게 막는다.
- **원본의 전체 입력 처리는 읽지 않았다**: 「미확인」이다. 우리 구현은 원본을 따라가지 않는다.

## 변경 기록

- **2026-10-29 (040 pty 통합 검증 및 문서 동기화)**:
  1. **030 범위 축소와 단계명 정정**: REPL의 `read_user_input` 연동은 이미 010에서 완료되었으므로, 030 단계명을 「배너 안내와 CLI 통합 검증」으로 정정하고 배너 힌트(`CLI_MULTILINE_HINT`) 연동 및 플래그 독립성·DB 줄바꿈 보존 검증으로 범위를 명확히 축소함.
  2. **`prompt_toolkit` 미설치 폴백 결정 (020)**: ROADMAP 위험 6의 열린 항목에 대해, 라이브러리를 지연(lazy) import하고 미설치 시 프로세스당 1회 안내 문구 출력 후 `input()`으로 안전하게 폴백하도록 확정함.
  3. **지시서 작성 및 pty 시험 중 확인한 사실 반영**:
     - 폴백 경로에서 `UnicodeDecodeError` 발생 시 깨진 바이트 줄 하나만 버려지고 안내 후 살아 있음을 pty 회귀 시험으로 고정함 (단, 가짜/파이프 입력 스트림은 한 덩어리가 버려짐).
     - 가상 터미널(pty)이 커서 위치 요청(CPR, `ESC[6n`)에 응답하지 않을 때 `prompt_toolkit`이 경고 문구를 출력하는 것을 관찰함 (시험 환경 탓으로 추정, 실제 터미널 앱에서의 실재 여부는 050 확인 과제로 유지).
