# [WHY] 19-단일-제어판-MVP — 왜 이 정도로만 하는가

> 사람의 말로, 코드 용어 없이 적는다([ROADMAP_정책 §3-2](../ROADMAP_정책.md)). 마감 때 종합보고서가 이 문서의 가정을 하나씩 대조한다.

## 1. 왜 지금 이 로드맵인가

- 이 프로그램을 어떻게 움직일지 정하는 값들이 여러 곳에 흩어져 있다.
  - 고정된 숫자 목록
  - 실행할 때 붙이는 옵션
  - 컴퓨터 환경에 적어 둔 값
  - 에이전트를 만들 때 넘기는 스무 개 남짓한 값
- 그래서 「지금 이 에이전트는 어떤 값으로 돌고 있나」를 한 번에 볼 수 없다. 값이 어디서 왔는지도 알 수 없다.
- 덧붙인 기능이 실패해도 대화는 멈추지 않는다. 하지만 같은 실패가 매 턴 되풀이되고 경고만 쌓인다. 실패하는 기능을 끌 방법이 없다.
- 실행 중에는 아무것도 바꿀 수 없다. 바꾸려면 프로그램을 다시 켜야 한다. 바꿨다는 기록도 남지 않는다.
- 사용자는 「자동차 하네스 같은 단일 제어판」을 원했다. 리모컨으로 조종할 수 있고, 내부 설정과 상황을 모두 모아 쥐고 있는 판이다.
- 18번에서 한가운데의 울타리와 「조립하는 곳」을 만들었다. 그래서 이제 제어판을 붙일 자리가 있다. 울타리가 생기기 전에 만들었다면 제어판이 한가운데를 직접 만졌을 것이다.

## 2. 왜 이 정도로만 하는가 (비목표)

| 하지 않는 것 | 이유 | 언제 하나 |
|---|---|---|
| 웹 관리 화면·원격 서버 | 지금은 쓸 사람이 없다. 이번에는 제어판에 「명령을 넣고 상태를 받는」 입구만 만든다. 원격은 그 입구를 다른 말로 옮기는 층이다 | 원격 조종이 실제로 필요해질 때 |
| 설정 파일을 고치면 자동으로 다시 읽기 | 바꾸는 길이 둘이 되면 기록과 순서가 갈라진다. 바꾸기는 「명령 → 기록 → 다음 턴 시작 때 반영」 한 길로만 한다 | 필요가 생기면 그 한 길 위에 얹는다 |
| 꺼진 기능을 시간이 지나면 저절로 다시 켜기 | 원인을 고치지 않았는데 다시 켜지면 실패가 되풀이된다. 다시 켜는 것은 사람이 한다 | 자동 복구가 안전한 기능이 생길 때 |
| 보안 설정(명령 승인, 파일 되돌리기 기록) 바꾸기 | 원격에서 보안을 낮출 수 있으면 리모컨이 곧 뚫린 문이 된다. 이번에는 보여 주기만 한다 | 보안 설정을 바꾸는 별도의 엄격한 절차를 설계할 때 |
| 대화 중 모델이나 기능 안내 목록 바꾸기 | 대화 첫머리 안내문이 바뀌면 이전 대화와 어긋나고 비용 절감(캐시)도 깨진다. 시작할 때만 정한다 | 세션을 새로 여는 기능과 함께 |
| 숫자 목록 파일 쪼개기, 옛 이름 호환 장치 없애기, 하위 에이전트 만드는 방식 정리 | 제어판과 따로 할 수 있는 정리다. 한 로드맵에 섞으면 무엇이 무엇을 깨뜨렸는지 가를 수 없다 | 이후 정리 로드맵 |

## 3. 왜 이 순서, 왜 이 단계 수인가

1. **설정 하나로 모으기(010)**: 제어판이 보여 주고 바꾸는 대상이 설정이다. 먼저 설정이 한 덩어리로 있어야 한다. 제어판을 아무나 꺼내 쓰지 못하게 하는 울타리 시험도 여기서 함께 세운다. 나중에 세우면 그사이 이미 더럽혀진다.
2. **상태 보기(020)**: 읽기는 아무것도 바꾸지 않는다. 그래서 위험이 가장 작다. 쓰기 전에 「지금 상태」를 볼 수 있어야 바꾼 결과도 확인할 수 있다.
3. **기능을 끄는 문과 자동 차단기(030)**: 「끄기」라는 수단이 먼저 있어야 사람이 끄는 명령(040)도, 자동으로 끄는 차단기도 만들 수 있다. 차단기는 그 문을 쓰는 첫 사용자다.
4. **바꾸기 명령과 기록(040)**: 수단(문)과 보기(상태)가 생긴 뒤에야 「검증하고, 먼저 기록하고, 턴 경계에서 반영하는」 쓰기를 붙인다. 장부에 표를 새로 만드는 일도 이 단계에 몰아서 한 번만 한다.
5. **명령창 연결(050)**: 사람이 실제로 쓰는 입구다. 안쪽이 다 검증된 뒤 겉에 붙인다.
6. **해설서 동기화(060)**, **마감(070)**: 18번처럼 해설서 개정과 마감을 나눈다. 해설서 분량이 크면 마감이 밀리기 때문이다.

## 4. 왜 이 방식을 택하고 무엇을 배척했나

- **택한 것**:
  - 제어판을 「조립하는 곳」 바깥에 둔다. 제어판을 아는 곳은 조립하는 곳과 명령창 두 곳뿐이고, 이것을 시험으로 지킨다.
  - 설정은 한 번 만들면 고칠 수 없는 사진 한 장으로 둔다. 바꿀 때는 새 사진을 만든다.
  - 기능을 끄는 문은 기능을 끼워 넣는 쪽이 건다.
  - 바꾸기는 기록을 먼저 쓴다.
  - 에이전트를 만드는 방법(겉모습)은 바꾸지 않는다.
- **배척한 것**:
  - 에이전트가 제어판을 품는 방식: 모든 부품이 에이전트를 통해 제어판을 꺼내 쓰게 되어, 다시 떼어낼 수 없는 중심이 생긴다.
  - 에이전트를 만드는 방법을 「설정 한 덩어리」로 바꾸는 방식: 이미 검증된 수많은 시험과 쓰는 사람이 한꺼번에 흔들린다.
  - 한가운데에 「턴 시작」 지점을 새로 만들어 반영하는 방식: 한가운데의 약속을 바꾸게 된다. 턴을 부르는 쪽(명령창)이 그 직전에 반영하면 충분하다.
  - 차단기를 한가운데나 도구 관문 안에 두는 방식: 한가운데에 정책이 들어간다.
  - 기록을 화면 출력 장치로 남기는 방식: 출력 장치는 실패해도 조용히 넘어간다. 그래서 「기록을 못 하면 바꾸지 않는다」를 보장할 수 없다.

## 5. 성공 판단 기준과 검증할 가정 목록

| 번호 | 가정 |
|---|---|
| **A** | 설정 파일과 환경 값과 옵션을 하나도 주지 않으면, 에이전트는 이 로드맵 전과 똑같은 값으로 만들어지고 똑같이 움직인다 |
| **B** | 에이전트를 만드는 방법(넘기는 값의 이름과 순서)은 바뀌지 않고, 기존 시험은 한 줄도 고치지 않고 모든 단계에서 통과한다 |
| **C** | 한가운데(되풀이와 약속)와 도구 관문 파일은 이 로드맵 동안 바뀌지 않는다 |
| **D** | 제어판을 아는 곳은 조립하는 곳과 명령창 두 곳뿐이다. 다른 부품이 제어판을 부르면 시험이 즉시 실패한다 |
| **E** | 같은 기능이 정해진 횟수만큼 잇달아 실패하면 그 기능은 저절로 꺼진다. 그 뒤로는 그 기능 때문에 생기는 실패가 대화에 더는 나타나지 않는다 |
| **F** | 보안 설정과 대화 중 바꾸면 안 되는 설정은 제어판 명령으로 바꿀 수 없다. 거절했다는 사실과 이유는 기록에 남는다 |
| **G** | 모든 바꾸기는 반영되기 전에 장부에 기록된다. 기록에 실패하면 반영되지 않는다. 바꾼 내용은 다음 턴이 시작될 때 반영되고, 턴 도중에는 반영되지 않는다 |
| **H** | 상태를 보기만 해서는 아무것도 바뀌지 않는다. 보이는 내용에 비밀값(열쇠)이 나타나지 않는다 |
| **I** | 한 단계 낮은 파이썬 버전(3.12)에서도 프로그램이 켜진다 |

## 6. 알려진 위험과 아직 확인하지 못한 것

- 기능을 끄는 문이 「성공」을 판정하는 방식이 문제가 될 수 있다. 도구 관문에는 단계별 실패 정책이 있다(앞 단계는 실패해도 계속, 뒷 단계는 실패하면 멈춤). 이와 어긋나 성공을 잘못 셀 수 있는지는 **미확인**이다. 030 지시서를 쓰기 전에 코드로 확인한다.
- 기능 하나가 여러 자리에 끼어 있을 때, 한 자리의 실패와 다른 자리의 성공을 「잇달아」로 어떻게 셀지 정해야 한다. 지금은 기능 단위로 하나의 수를 세는 것이 제안이다. 확정은 ROADMAP §6-3에서 한다.
- 장부에 표를 하나 더하는 변경이다. 이전 판의 장부 파일을 열 때 안전하게 바뀌는지 시험으로 확인해야 한다. 지난 판 올림의 방식은 ROADMAP 작성 때 코드로 확인한다.
- 명령창은 지금 입력을 문자열로 나눠 처리한다. 명령 하나를 더할 때 기존 명령(되돌리기)과 섞이지 않는지는 050에서 시험한다.
- 설정 파일 형식(TOML)을 표준 라이브러리로 읽는 기능이 3.12에서 문제없는지는 이론상 맞다(3.11부터 있음). 그러나 실행 확인은 **미확인**이다.
